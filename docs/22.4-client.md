# 22.4. Client

Back to [22](22-ownership.md).

`client.js` keeps separate live, dev-feed and replay display descriptors and
passes the shown one explicitly to the HUD and vocabulary helpers; a live
envelope without a valid descriptor is refused before anything is installed.
Deploy-form options and limits come from `GET /api/client-config`, which only
form creation and matchmaking wait for. The contract is
[22.7](22.7-content-and-presentation.md).

## Client

`public/input-controller.js` owns keyboard, pointer-fire state, touch sticks, inventory selection/rearrangement and one-shot intents. It exposes intent collection, selection/aim reads, reset, action consumption and listener cleanup. The application calculates pointer world aim through the renderer, assigns sequence numbers, sends packets, maintains pending history and predicts movement. Action consumption remains after sending/prediction. Existing application reset call sites (connect/disconnect, new-arena/archive dialogs, replay entry), plus input-owned blur/visibility handlers, retain their prior behavior.

`public/hud-controller.js` owns inventory/status/objective display, tooltips and minimap drawing. Each render receives authoritative state, map, player/replay context, local selection, explicit visibility polygon/eye/viewport/directed inputs, and discovery memory. Contestant minimap drawing clips playable area terrain to discovered coarse cells, and shows stations, chargers, and exits only when their coarse cell is discovered (`shared/discovery.ts`), while gladiators and directed views keep the full map (#274). It emits selection/action callbacks; it never sends commands or mutates authoritative objects. The application connects these callbacks to input intents. Controllers can release their listeners independently. The renderer's injected API and internals are unchanged. `tests/client-controllers.mjs`, run by the browser suite, exercises frozen HUD inputs, concealment, discovery feature and terrain clipping, callbacks, one-shot consumption, blocked input, blur/visibility resets and cleanup without a running game client.

Inventory pointer capture, drag threshold and DOM destination hit testing belong
to the HUD controller. It emits source/destination indices for swaps, or a source
index for a canvas drop. The input controller translates these to existing
`moveSlot` or `slot` + `drop` commands; a pending drag drop pins its source and
discards competing rearrangement until that intent is collected. The application
cancels gestures with input resets and supplies current live-player eligibility.
World drops retain authoritative nearby placement, not the pointer's coordinates.
No simulation, projection or recording fields changed for this gesture feature;
it landed under `last-exit-0.6` without changing that version (the current
version is in [26](26-recording-contract.md)).

The six-slot inventory stores ammo on weapons and charge on cells. Validated moveSlot input is queued and applied authoritatively; compatible utility stacks merge and other slots swap. Recording copies each sanitized input as it is accepted, so a command is preserved exactly as the client sent it rather than as some later tick left it, and commands survive alongside outcome frames. The icon HUD supports keyboard and touch rearrangement without client authority over inventory.

`public/replay-controller.js` owns recorded-match playback: opening an archive by id, the timeline it builds, the wall-clock-anchored playhead, the replay's focus select and the rest of the `#replay-*` DOM. Three replay features landing in `client.js` in a row (camera/follow, wall-clock timing, schema compatibility) was the repetition that justified pulling this cluster out. It never sends a command or reads the socket; the application supplies map/state swap, full live-state reconciliation for closing back to a live match, the scene (for camera framing and cuts), and the shared toast/connection-label/HUD-refresh functions, the same narrow-dependency shape `input-controller.js` and `hud-controller.js` already use. `client.js` still decides *when* a replay opens (the "Watch match" button, an archive row, a resumed session) and still owns the generic "fetch and save this replay id as a file" download helper shared by the archive browser and the open replay's own download button. Only the latest archive load may install (#387): opening another, closing or resetting the replay, connecting to a room and stepping out to the dev view each abandon a load still in flight, so a response that settles late, in any order, changes neither the view nor the toast a failure would raise.

`public/camera-director.js` owns where a directed camera points, for replays, spectators and the dev view alike: the followed player, the free view's pan and zoom, whether a followed player is shown in their own sight, and the keys that steer it while a directed view is showing. The scene asks it for a centre and zoom each frame, and for the player whose sight to fog by (`viewer()`), and applies the shared sight rule from there; it decides nothing about a player's own camera. Follow moved here from the replay controller when the dev view needed the same thing live, rather than being copied. `fillFollowOptions` in `ui.js` builds both focus selects. `client.js` owns the dev view's second socket when a player steps out to it (24): it routes that socket's frames to the renderer and the player socket's frames only to `liveState`, the same swap a replay makes, and restores the live map and state when the player steps back. The profiler's `net.stateGap` is timed where the player socket receives a frame, not where a frame is drawn, so live gaps keep their ordinary interval behind a replay and the dev feed's frames never stand in for the player socket's (#387); a new connection starts it afresh. A directed view's eye is only ever the followed player, never the viewer's own, so a replay of your own match is not culled around you.

`client.js` coordinates distinct client view modes (`lobby`, `play`, `outcome`, `dev`, `replay`, `spectator`) where GUI overlays are bound to view state (#277). Stepping out to the dev view or opening a replay hides the `#outcome` modal dialogue and play equipment, while maintaining outcome data and dev camera settings. Stepping back (via the leave button or shortcut) or closing a replay restores the player's underlying view, returning an eliminated player to their death screen and its modal controls.

For F-19, the director separates the follow vision preference from the current
subject: a null `viewer()` can mean an absent subject in player-vision mode.
`reset()` installs fresh-session defaults; `snapshot()`/`restore()` explicitly
carry dev framing and preferences across a roundtrip. Live authoritative frames
populate position memory, cleared on map/connection changes. The replay timeline
instead indexes positions by player and tick, so the controller can query history
without borrowing camera state from a later seek. The scene clears sight and gate
memory on cuts and refreshes the directed minimap after computing current sight,
including while playback is paused. [24](24-networking-privacy.md) owns the mode
policy and [25](25-pacing-and-rendering.md) owns absence and seek semantics.

Presentation smoothing, shading and the replay playhead are in
[25](25-pacing-and-rendering.md). What each view is permitted to contain is in
[24](24-networking-privacy.md).
