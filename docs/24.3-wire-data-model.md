# 24.3. Engine data model for the wire (#1139)

Up: [24](24-networking-privacy.md). Encoding direction: [24.1](24.1-wire-encoding-design.md).
Codec evidence: [42.49](42.49-wire-codec-selection.md), 42.51 (PR #1138).
**Facts and proposals; nothing here is implemented or decided.** The live protocol is still
JSON (24). No engine, protocol, `WIRE_VERSION`, simulation, recording or fixture change is made
here.

Corey, 2026-11-16 ([17.4](17.4-live-service.md) #17), verbatim: "It sounds like for us to truly
assess the wire model, we have to visit the engine's data model." The codec studies typed every
number as a generic `num`, because the projections declare nothing more specific. This record gives
every field of the live `state` message a type taken from what the engine produces, and lists the
engine-side choices that shape the wire, for Corey's decision.

## Summary

The engine's data is far more regular than its JSON suggests. Typing it field by field needs no
engine change for most fields; a handful of choices are Corey's.

- **Rapier values are float32.** Every player, body and effect position, and every body velocity,
  is exactly a Rapier float32 metre times `SCALE` = 40 (`shared/physics/world.ts`). None needs
  float64 on the wire. Sent as float32 metres, each takes 4 bytes instead of a float64's 8 and
  decodes exactly.
- **Every counter is an integer.** Health, shields, ammo, cooldowns, ticks, serials and counts were
  integers in every sample, although the types say `number`.
- **Genuine float64 values are few.** They are heading (copied from the client's aim), projectile
  position and velocity (JS trigonometry), some body radii (content arithmetic) and a few item drop
  points.
- **Match constants travel every tick.** `version` and `physicsProfile` are the same 21-character
  string, sent twice per frame. `duration`, `cellChargeTicks` and the four prediction-motor values
  are content constants.
- **IDs are serial numbers wearing strings.** Examples are `item-3506`, `door-10`, `building-4`,
  `c0`, and node IDs like `charging@198,162`. Body IDs repeat their actor or item ID with a prefix.
  Effects, projectiles and events already use numeric serials.
- **Enums are closed unions sent as strings.** Event text is a formatted sentence.
- **Some fields have no reader or no writer.** No client code reads 10 projected fields. Two own
  fields are declared in the projection but exist nowhere on `Player`. `cloak` is never set above 0.
  No production code places traps.
- **"None" has two spellings** (absent and `null`). The player list is a union chosen by whose view
  it is.

## Method

- **Runtime probe** (`tools/perf/wire-data-model.mjs`). It runs the production match on 42.47's
  retained tuned caches (seed 4217, content-7, 12x6 and 36x18) for 1,200 ticks. Each tick it calls
  production `match.project` for every player's own view and for the directed (dev) view: 14,412
  projections per size. It walks every projected record and reports, per field and per record path:
  - value kinds and presence (absent, `null`);
  - for numbers: the share that are integers, float32-exact, **scaled float32** (a Rapier float32
    metre times `SCALE` = 40, so `fround(x / 40) * 40 === x`) and genuine float64, with ranges;
  - for strings: cardinality, length and sample values;
  - coverage against the projection declarations (`projection-contract.ts`, `visibility.ts`).

  Frame layers and the discovery encoder are a transport detail on top of the projection and are
  not walked. Delayed spectators receive the dev view's records later, so they add no fields.
- **Static inventory.** For each declared field: its TypeScript type, its producer and whether
  client prediction reads it, from the source.
- **Unobserved families.** The bot traces produced no traps, heard cues, tethers, hook flights,
  reloads, carried cells, or box and convex shapes. Content-7 has traps and the hook kit, but the
  bots never used them. Those fields are typed from the source alone and marked unobserved.

## Findings

**Numbers.**
- **Scaled float32.** Rapier stores metres as float32, and the engine multiplies by 40, which is not
  a power of two, so a position reaches the projection as a float64 such as 9820.670166015625. Of the
  non-integer player, body and effect coordinates, 100% satisfy `fround(x / 40) * 40 === x`. The
  rest are integers or float32 values outright. Body velocities behave the same way. A codec that
  sends `fround(x / 40)` and multiplies by 40 on decode is exact, because IEEE multiplication is
  deterministic in Node and Chrome alike. 24.1 requires that exactness for prediction.
- **Genuine float64:**
  - `heading`, copied from the client's `input.aim`;
  - projectile `x`, `y`, `dx` and `dy`, from `cos`/`sin` times speed;
  - 28–38% of shape radii, content-derived per kit, such as 11.2875;
  - 0.3% (12x6) and 3.7% (36x18) of ground-item coordinates, from drop points (`loot.ts`).
- **Integers.** Every other number observed was an integer. Negative values occur only in
  `hazardX` (−80) and `lastSeq` (−1 for none).
- **Large integers.** Body `generation` reaches about 32,000 by tick 1,200, because it is a world
  serial. Discovery cell indices run to about 21,600.

**Identifiers.**
- **Strings around serials:** players `c<i>`/`g<i>`; items and gates `item-<n>`/`door-<n>`; buildings
  `building-<n>`; map nodes `<kind>@<x>,<y>`.
- **Body IDs** are always `actor:<actorId>` or `item:<itemId>`. In every frame checked, the ID was
  derivable from the other field.
- **Numeric serials:** effects, projectiles and events use the game serial.
- **Mixed declarations:** `itemId` on a body is declared `string | number`.

**Constants and slow data.**
- **Content and match constants** sent every tick: `version`, `physicsProfile` (equal to `version`
  once physics attaches, `game.ts:111`), `duration`, `cellChargeTicks` and `predictionMotor`.
- **Roster data** sent in every player record: `name`, `role`, `kit` and `seat`.
- **Map placement** sent with every gate record: gate geometry and `buildingId`. Frame layers already
  send gates as a keyframe plus changes, so the steady cost is small, but each keyframe resends all
  of it. A 36x18 dev view holds 787 gates.

**Presence.**
- **Two spellings of none.** `reload`, `charging` and `respawnAt` are `null` when present and
  missing otherwise. Empty inventory slots are `null` (84% of slots), which is positional and
  meaningful.
- **Kind-dependent fields.** `weaponType`, `ammo`, `charge`, `count` and `family` depend on the
  item's `kind`, which already serves as a discriminant.
- **The player list** holds the viewer's own record, with 35 possible fields, among observed
  records with 15. Which is which follows from the viewer's ID, not from the record.

**Dead or unread fields**, verified by search:
- **No client reader:**
  - item `droppedBy`, `pickupAfter`, `nodeId`, `tier`, `instanceId`, `lineageId` and `quality`;
  - own `attackCd`;
  - body `omega`;
  - header `directed` (the client derives its own, `public/client.js:79`).

  The map lab reads `tier` from map data, not from state.
- **No declaration or writer:** own `cell` and `nodeId` are in `OWN_FIELDS` but are neither declared
  on `Player` nor written. The HUD finds the carried cell from the inventory.
- **No writer above zero:** `cloak` (declared, read, never set above 0).
- **No producer:** traps. `map.traps` starts empty and only tests and tools fill it.

**Prediction.** Client prediction (`public/physics-prediction.js`, `input-prediction.js`) reads:
- the tick, the motor, the tether flag and `physicsProfile`;
- each player's `id`, `lastSeq`, `status`, `boost`, `stun`, `x`, `y` and `role`;
- each gate's `id`, `x`, `y`, `w`, `h` and `open`;
- each body's `id`, `x`, `y`, `angle`, `vx`, `vy`, `generation`, `actorId`, `itemId`,
  `discontinuity` and shape;
- each tether's `a` and `b`.

It also copies the whole own record into its predicted state. These are the fields 24.1 keeps
exact, and every one has an exact wire type below.

**Limits.**
- **Bot traces.** 1,200 ticks of a 12,000-tick match, played by bots. The phase never reached
  `finished`, the hazard had not advanced, and no client sent input sequences, so `lastSeq` stayed
  −1.
- **Unexercised content.** Traps, hook flights, tethers, heard cues, reloads, box and convex shapes
  and stack items never occurred. Those rows are typed from the source.
- **What the probe can't see.** It reads projected values, not the engine's intent: an
  integer-valued field may still be meant as a fraction in future content. Declaring the types
  (proposal 2) is what would make that a contract.

## Per-field inventory

"Prediction" marks fields read by client prediction, which must stay exact (24.1, 29.2). "Proposed
wire type" is a proposal for #1131's schema, not a decision. "float32 metres" means
`fround(value / 40)`, multiplied by 40 on decode. Fields not listed here are the frame-layer and
discovery encodings (24), which wrap these records unchanged. Inventory entries and the carried
cell use the item record. A reload is `{slot, instanceId, until}`, and a heard cue is
`{x, y, tick, until}`, all integers or tick values by source; neither was observed. Tethers
(`id`, `a`, `b`) and hook flights (`id`, `a`, `x`, `y`) carry body and hook IDs and a JS-math
position. They were unobserved, because the bots never used the hook kit.

## Proposals for Corey

Each proposal is independent. Each needs a decision before #1131 closes its schema. Proposals 1 and 2
change no behaviour. The others change the projection, the client or both, and so the wire
contract (`WIRE_VERSION`).

1. **Send Rapier values as float32 metres** (player, body and effect positions; body velocities;
   physical item poses). Wire only, no engine change, exact.
   - **Not proposed:** making `SCALE` a power of two or using metres as the world unit. Either would
     make these values float32 in world units, but would change Rapier's inputs and so the physics
     fixture.
2. **Declare the integers.** Give counters, hit points, ammo, ticks and serials integer types in
   `shared/types.ts`, with a debug assertion at projection, so the wire can use varints safely.
   - **Affects:** types and projection only.
3. **Move match constants out of the per-tick state** into the welcome or ready message: `version`,
   `physicsProfile`, `duration`, `cellChargeTicks` and the prediction motor.
   - **Roster data:** a further step would send `name`, `role`, `kit` and `seat` in a roster
     message when it changes, and identify players by index in each tick.
   - **Affects:** welcome handling, the HUD and prediction's reads.
4. **Number the identifiers.** Two options:
   - **(a) Wire only.** The wire codec maps each family's `prefix-<serial>` to its number and refuses
     any other form, so a nonconforming ID fails loudly. The body ID is dropped and rebuilt from
     `actorId` or `itemId`.
   - **(b) Engine.** The engine itself moves to numeric IDs per family. That reaches map
     generation's shared serial, the fixture, recordings and many tests.

   Option (a) is the smaller step and keeps the engine unchanged.
5. **Enum tables.** Give every closed union an ordered runtime table in its owner (as `JOIN_MODES`
   already is), and send indices. `weapon` is already an index, into the weapon table's key order,
   so a content reorder silently changes its meaning; it should index a declared table.
   - **Events:** sending events as structured records (kind, subject, object) for the client to
     format would replace free-text sentences. That affects the event producers, the HUD and
     recordings.
6. **One spelling of "none".** Optional values are absent rather than `null` (`reload`, `charging`,
   `respawnAt`). Inventory slots stay positional.
   - **Affects:** those types, their writers and their few readers.
7. **Separate the viewer's own record.** Send it as its own field, `self`, with `players` holding
   observed records only, so the player list is no longer a union.
   - **Affects:** the projection (`visibility.ts`), the client's `me()` lookups, and the discovery
     delta wiring in `room-views.js`.
8. **Remove dead and unread fields from the projection.** That serves privacy minimization (24) as
   well as size.
   - **Clear cases:** own `cell` and `nodeId`, gate `kind` and header `directed`.
   - **Needs a product answer:** `cloak` (fix or remove) and the item fields with no reader. `tier`
     and `quality` may be meant for future UI.
9. **Send static geometry once.** Gate placement belongs with map delivery, and only `open` and
   `locked` change during a match. A body's shape is constant for its generation, so it could
   travel only when the body appears or changes.
10. **Leave the genuine float64 values to their owners.** Heading, from client aim, could be
    quantized where input enters (#1096); that would change the authoritative shot direction, a
    gameplay change. Projectiles move in straight lines from spawn and could be sent once.
    - **Recommendation:** neither here. Keep them float64 on the wire until #1096 and #1094 decide.

**Recommended order.**
- **Without behaviour change:** 1 and 2 can start now.
- **Wire-contract changes:** 3, 4(a), 5, 6, 7 and the clear cases of 8 could land together in
  #1131's schema closure under one `WIRE_VERSION` bump.
- **Waiting on product or later work:** 9 and the rest of 8.

**What this enables.** With these types, the field-typed codec comparison on #1130 can be run fairly.
D and protobuf would both be built from the same per-field types, measured on bytes, Chrome decode
and a deployable bundle (42.51, review 866).

```powershell
node tools/perf/wire-data-model.mjs --maps-cache=test-results/wire-1093-tuned-12x6.v8 --out=test-results/wire-dm-12x6.json
node tools/perf/wire-data-model.mjs --maps-cache=test-results/wire-1093-tuned-36x18.v8 --out=test-results/wire-dm-36x18.json
```

Each run takes 10–25 s under the shared lock. The caches are 42.47's retained files, and the
probe refuses a cache whose map, simulation or server sources have changed, apart from
declaration-only exports. It is an opt-in witness outside the test tiers.
