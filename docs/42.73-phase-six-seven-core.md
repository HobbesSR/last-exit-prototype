- **The budget.** Without traps the crossing is about 6–7 times the TypeScript's 2.3 µs, which was two comparisons per
  actor. It meets the [state-flip exception](42.58-sight-core-adapter.md#the-budget): the packed state is the game's own
  records (the roster, the hazard areas, the traps), and the overhead is well under 1% of the tick. With traps, which
  no production map places yet (24.3), the phase costs less than the TypeScript did.
- **Where it goes.** Called alone 20,000 times on a warmed game (the same map, 11 players, outside the tick), the whole
  call cost 3.7 µs: packing the rows about 1.1 µs, the ID ranks (`ordered(s)`) about 0.8 µs, applying the output about
  0.55 µs, the core about 0.5 µs, and the rest under 0.3 µs each. Inside the tick the same call reads about four
  times that, the core's own run included (1.9 µs against 0.5 µs). That is read as the phase running cold after the
  rest of the tick, not as one segment to trim; no segment is large enough to be worth more trimming.
- **Phase 7.** `recordRewind` is a little cheaper than the TypeScript, since the frames stay in the core and no caster
  run packs them. `finishMatch` costs about 0.35–0.45 µs a call against the TypeScript's 0.01–0.03 µs, measured
  alone on a live game: about 0.01% of the tick, the floor of one crossing.
- **The whole tick.** The runs spread from 4.62 to 5.03 ms, the baseline between them, in labels this change does not
  reach. It is read as run-to-run variation, as 42.71 and 42.72 read theirs; it was not proven to be.

## What brought it down

The first working version's crossing was about 14 µs without traps, and the trap case read 145 µs. One segment
profile, then three changes:

| Change | Effect |
| --- | --- |
| **The gates' open mask is written only when the call runs traps.** The environment reads no gate; only line of sight and a spider's step do. On this map the mask is a pass over 421 gates | The trap case fell from about 145 µs to 79 µs; without traps, within noise |
| **The input is written straight into the core's buffer**, sized first, instead of a growing array copied in | Within noise without traps |
| **The output is read in place**, since nothing calls the core before it is applied | Within noise |

## Method

- **Environment.** The development machine (Windows 11), Node v24.15.0, the core built with `npm run core:build` in both
  checkouts. 2026-11-21. Under the exclusive bench lock; other busy share was 4.8–7.7%, below the 25% threshold.
- **The script** was `tests/bench-phase-three.mjs`, changed ad hoc and not committed: it reports `sim.environment`,
  `sim.environment.core` and `sim.rewind`, optionally places the traps, and times `finishMatch` alone after the run.
  It uses the same map cache, warm-up (300 ticks) and timed span (600 ticks of `step` plus `snapshot`) as 42.69. The
  baseline was `git archive 1ec791bf` (main after #1246), with its `node_modules` a junction to the current checkout's.
  Run order: current, baseline, current, then current and baseline with traps.
- **Limits.** Node only, with one map and content. Bots rarely die to the hazard wall or a trap here, so the kill and
  explosion stops are barely exercised; `tests/physics-explosion.test.js` witnesses both in one run, and
  `tools/trap-continuity.mjs` exercises them in bot matches. Remeasure with the whole tick at #1214.
- **Test cost.** `tests/physics-explosion.test.js` gains one real-game case (a mine that kills, then resumes) and
  loses the bare-record case; `tests/rewind.test.js` loses the bounded-history case, now a Rust test;
  `tests/player-relations.test.js` loses its bare-record rewind case. The new case takes about 3 ms on the game the
  file already builds, and the file stays at about 0.5 s isolated.
  `tools/trap-continuity.mjs` is not in the suite: about 1 min a side, run when a change can reach a trap or a hazard
  area (31).
