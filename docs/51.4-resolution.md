### 2. Resolution: Layout + library → **ResolvedLayout** (view)

This is the knowledge layer: what the solved placement means.

### Passability design note (#286)

The authored value is `not-passable-hint`: architectural guidance to occupy a
stretch, never a requirement to block it. The table is symmetric; `P` means a
guarantee, `H` means the hint survives without a guarantee, and `—` means neither.

| Side / other side | `passable` | `any` | `not-passable-hint` | unstated |
| --- | --- | --- | --- | --- |
| `passable` | P | P | P | P |
| `any` | P | P | H | — |
| `not-passable-hint` | P | H | H | H |
| unstated | P | — | H | — |

### Matched rules (#849)

Corey, 2026-11-06 (17.2.2), superseding the table above for libraries that opt in. A library
states `passabilityRules: "matched"` at its top level to use them; without it the table above
applies unchanged, and the library keeps its fingerprint. Every bundled library states it
since the #849 adoption (`common-primitives@6`, [42.37](42.37-matched-adoption.md)); the
experiment that led there is [42.36](42.36-matched-library-experiment.md).

| Side / other side | `passable` | `any` | `not-passable-hint` | unstated |
| --- | --- | --- | --- | --- |
| `passable` | P | P | refused | P |
| `any` | P | P* | H | P* |
| `not-passable-hint` | refused | H | H | H |
| unstated | P | P* | H | P* |

- **Matching.** Where two tiles meet, `any` (or unstated) fits anything and other values
  match like with like. Placement refuses the pairs marked "refused" while it solves
  (`passabilityFits`, 51.3), so resolution never sees one.
- **Unstated reads as `any`.** On a tile edge that is Corey's default. Inside a tile it gives
  his other default too: a class boundary nobody stated is passable.
- **`P*` is decided after aggregation:** passable between two regions, and nothing inside one
  region. Regions are maximal groups of one class (51.5), so resolution decides this from
  the two cells' resolved classes. An explicit `passable` inside a region is still an internal
  guaranteed run (20.6).
- **Emergent portal demotion (#893):** An emergent crossing between two regions
  where neither side explicitly authored `passable` resolves to `guarantee: "guaranteed"`
  only when it forms a contiguous run of length >= `MIN_PORTAL_LENGTH` (2 segments).
  Emergent runs shorter than 2 segments demote to `guarantee: "none"`, preventing
  incidental 1-cell notches from becoming illegal portals that abort the solve. Explicitly
  authored `passable` segments continue to be guaranteed regardless of run length.
- **A set piece whose own slots can't meet** is a library error under these rules
  (`setPieceSeamProblems`, run by the game's `validateLibrary` and by placement). A rule or
  tile change can invalidate a set piece that was valid when saved.
- One function, `guaranteesPassability(lower, upper, rules, sameClass)`, serves resolution and
  the open-face rule.
  The partial placement view (Map Lab, 53.1) uses it too. The solver and that view
  share `resolveSettledClass`: an `any` cell takes a placed neighbour's class ask,
  otherwise waits while a neighbour is unplaced, otherwise defaults to `open`.
  The view retains both authored sides and distinguishes an internal hint from a
  boundary without a guarantee; it does not promote unknown neighbours to guarantees.

Outside the map there is never a guarantee. Both authored values remain in
`stated`; hints reach builders through the brief (#287, [51.7](51.7-briefs.md)). On an internal tile
segment, the design states the same prescription for both sides.

Every `H` is the same guarantee, but not the same suggestion. The brief carries
both stated values with each hint, unchanged, so `hint`+`hint` stays
distinguishable from `hint`+`any`, `hint`+unstated and a hint facing the map's
outside (#406). `hintStrength` (20.1) is the one function that ranks them: a
hint is `mutual` when both sides hint and `one-sided` otherwise. Neither is a
requirement.

Placement uses this same derived guarantee before checking connectivity or
portal width. It may prune a sealed component or a settled short portal, never
because a builder might ignore a hint. Unplaced options and unresolved cell
classes are upper bounds on possible connectivity, not additional guarantees.

Library schema 3 and module schema 1 remain: the optional enum extension changes
no fields or existing tile data. Fingerprints still hash the complete authored
content, so adding a hint changes the fingerprint, while untouched content keeps
its fingerprint. Macro stages advance to version 2 because `any`+`any` now
changes a saved layout's derived guarantees; wire version 8 explicitly retires
version 7 rather than silently reinterpreting its views. Builder versions stay
unchanged. The content authoring pass and brief/SDK hint channel are separate.

- **Resolved classes:** a declared class stands. An `any` cell takes the class
  its neighbours' adjacency prescriptions require, and otherwise `open`.
- **Passability guarantees:** a segment between two cells on the map is
  `guaranteed` if either side prescribes `passable` or both prescribe `any`,
  and otherwise `none`. A
  segment facing the map's outside is always `none`, whatever its design
  prescribes: nothing is across it. So a design placed at the map's edge is
  valid, and its outward prescription just doesn't become a guarantee. What
  each side stated (`passable`, `any`, `not-passable-hint`, unstated) is kept alongside, as
  provenance for later steps and open questions.
- **Why it's a view:** nothing is decided here, so there's nothing to save.
