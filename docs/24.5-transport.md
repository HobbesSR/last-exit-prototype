# 24.5. Transport: WebTransport from a Rust edge, with a WebSocket fallback (#1095)

Up: [24](24-networking-privacy.md). The split it carries: [24.2](24.2-lossy-transport-deltas.md). Evidence:
[42.56](42.56-transport-probe.md). The Rust direction: [27](27-rust-path.md), tracker #1173.

**Status.** The direction is decided, and stages 1 and 2 are built (#1095). Stage 2's contract is
[below](#stage-2s-contracts).
- **Opt-in.** The edge runs only when Node is given `EDGE_LINK_PORT` and an edge is started against it (`npm run
  edge -- --link 127.0.0.1:<port>`). Without one, every connection is a WebSocket, as before.
- **Evidence.** `tests/edge.browser.mjs` runs a match over the edge in Chrome, its inputs on datagrams. It reaches
  the edge through a UDP relay (`tests/helpers/lossy-relay.js`) that then loses a fifth of the packets and stops
  everything for longer than the 32-tick history; the page keeps drawing, and recovers with whole frames and then
  deltas. The edge's CPU is [42.57](42.57-edge-cpu.md); the split delivery under 42.48's profiles is
  [42.59](42.59-split-delivery-under-loss.md).
- **Known limits of stage 1.**
  - **The link is unauthenticated.** It binds to loopback only, so any local process could pose as the edge.
    That is acceptable while hosts are single-user LAN machines; a shared host needs a token.
  - **Restarts.** The edge must be started beside Node by hand. A dev cert lives 13 days, so a long-running edge
    relies on its rotation, which only its integration test has exercised.
- **Decided (2026-11-17, [17.4](17.4-live-service.md) #18).** The network edge moves to Rust as a full conversion.
- **Agent recommendations, not Corey's words.** `wtransport`, the stages and the channel map below.
- **Not proposed.** No simulation, input order, recording or fixture change.

## Decision

A Rust process terminates WebTransport (HTTP/3 over QUIC) and forwards sessions to the room host's Node process
over one local framed connection.
- **Rooms see no difference.** They stay behind the session seam (`deliver(payload, droppable, binary)`, `close`;
  `server/room-service.js`).
- **WebSocket.** It stays in Node at first, as the fallback, and moves to the edge afterwards (27).
- **Library:** `wtransport` 0.7.2, built on `quinn` (QUIC), `rustls` and `tokio`. All are MIT or Apache-2.0. The
  full crate tree, including its crypto provider, was checked under #1174
  ([21.1](21.1-third-party-licenses.md#the-rust-workspace)). The recommended crypto provider is `ring`, `wtransport`'s
  default.

Corey's lean (17.4 #14) was WebTransport over ENet or LiteNetLib. That stands:
- **Browsers cannot open raw UDP sockets.** ENet and LiteNetLib run over plain UDP, and LiteNetLib is C#, so
  neither can serve the browser client. ENet would matter only for a future native client.
- **WebRTC data channels** are the other browser option. They are the named fallback below.

## What the evaluation found

Checked 2026-11-17. The prototype is `tools/perf/transport-1095-probe.mjs`, which runs the Node addon below
against Chrome. Its results are 42.56.

- **Browsers.** WebTransport is Baseline: Chrome 97+, Firefox 114+ and, since March 2026, Safari 26.4+. The
  Safari date comes from MDN's Baseline status and secondary reports of Apple's release notes, which were not read
  directly. Older Safari, and networks that block UDP, still need the WebSocket fallback.
- **It works end to end.** Headless Chrome opened sessions accepted by a short-lived certificate's hash. Datagrams,
  a server-opened reliable stream and client-to-server datagrams all worked through a lossy UDP relay.
- **Under loss it behaves as 24.2 modelled.** Datagrams lose frames but their staleness tail stays short. The
  reliable stream delivers everything but stalls behind each loss. 42.56 has the numbers per profile.
- **The datagram cap.** Chrome reported `maxDatagramSize` 1,211 bytes on loopback, against 24.2's conservative
  1,200. It is path-dependent: read it per session, never assume it.
- **An oversized datagram vanishes silently.** A 1,300-byte datagram resolved without an error and never arrived,
  in both directions. The edge must enforce the cap itself (24.2's fragmentation and reliable-stream fallback).
- **API drift.** In the Node addon, `datagrams.writable` is deprecated in favour of `datagrams.createWritable()`.

### Is WebTransport the right technology?

Yes. The risk sits in one layer, and the design does not depend on it:

| Layer | Assessment |
| --- | --- |
| Browser API | Solid: Baseline in all three engines, W3C-specified |
| Protocol | Still an IETF draft (draft-ietf-webtrans-http3-16, July 2026). Every server must track draft versions as browsers update. That risk is the same in every language |
| QUIC underneath | Solid: Chromium's quiche and Rust's `quinn` are production-grade |
| Server bindings | The shaky layer: one-maintainer projects in Node and Rust, and an unfunded one in Go. In Rust, `wtransport` is thin over mainstream crates, so forking it or moving to `h3`'s WebTransport support stays feasible |

**Fallback technology: WebRTC data channels.** Unordered, unreliable data channels have worked in every browser for
years.
- **Costs:** signalling, ICE/STUN and DTLS over SCTP make connecting heavier.
- **Server side:** Rust's `str0m` (MIT or Apache-2.0) is the cleaner option. Node's `node-datachannel` wraps
  libdatachannel, believed to be MPL-2.0, which would escalate to Corey under AGENTS.md.
- **Transport-agnostic.** 24.2's split (acknowledgements, history, deltas, the reliable/unreliable division)
  works the same over either, so only the edge is bet on WebTransport.

**Staying on WebSocket only** remains the cheapest option, and many browser games ship that way. Its cost is the
head-of-line stalls 42.56 measured: staleness p95 1,463 ms against 345 on poor, 300 against 174 on wifi. 24.2's
decision 1 already rejected it as the target.

### Certificates and reachability

- **Development.** `serverCertificateHashes` accepts a self-signed ECDSA P-256 certificate valid for under 14
  days. The edge generates one at start and rotates it before expiry, and the client learns its hash from
  `/api/client-config` before opening the session. That needs no CA or browser flag.
- **Production.** A certificate from a public CA for each room host's name. With direct connect (28.1), each room
  host terminates its own sessions, so each needs its own name and certificate.
- **UDP.** The room host needs a UDP port open through the NAS, VPS and any firewall (#907). Where UDP is blocked,
  the client falls back to the WebSocket.
  - **Today's hosts (Corey, 2026-11-17, verbatim):** "The host for the time being is office, home LANs, and maybe
    Tailscale VPN setups. So UDP should be fine there I would think." Tailscale tunnels UDP, so stage 1 was built
    without a separate reachability check.
  - **Still open.** A public host's reachability is checked when #907 chooses one.

## Stages

Each stage is one PR or a few, with its own checks and a `WIRE_VERSION` bump where the wire changes. All of them
depend on #1174's toolchain, CI and licence audit.

1. **The Rust edge, with the same messages on a reliable stream.**
   - **Connection.** The edge accepts WebTransport sessions and carries each over the local framed connection to
     Node, where it becomes a peer behind the session seam.
   - **Framing.** Every message travels on one bidirectional stream, length-prefixed with a text/binary flag, so a
     room cannot tell which transport a session uses.
   - **Fallback.** The client tries WebTransport and falls back to the WebSocket on failure or timeout; a dev flag
     forces either.
   - **The local contract.** It carries each session's backlog to Node, so `deliver` can still report a skipped
     state frame and `buffered()` stays true to the edge. It also carries the current certificate hash and edge
     URL for `/api/client-config`. The edge checks `Origin` against the HTTP origin, as `server/websocket.js`
     does ([27](27-rust-path.md#the-edge)).
   - **What it lands.** No staleness gain. It lands the edge process, the local framing contract, certificates,
     the fallback, reconnection and browser tests, and it measures the edge's CPU.
2. **Inputs on datagrams,** with redundancy. Lost input packets stop costing the stalls a reliable stream adds, and
   the tick stamps of #1096 already order them.
3. **24.2's split.**
   - **Delivery.** Fast state on datagrams, with acknowledgements riding the input datagrams.
   - **Recovery.** A 32-tick history, whole-frame recovery, the item-body hold and the version stamps 24.2 lists.
   - **Codec.** It needs the codec's changed-field masks. They have landed, with the `fast` message (["Stage
     3's contracts"](#stage-3s-contracts)).
   - **Roster revisions.** Compared for equality only: a revision identifies a roster's content, not its order (24
     "Schema closure").
   - **Ownership.** Datagram size enforcement and fragmentation live in the edge. Acknowledgements, history and
     deltas stay with the projection's owner (27).
   - **WebSocket sessions use the shared views' delivery.** A session without datagrams gets exactly what
     24.2 decision 2 already gives the dev view and delayed spectators: today's keyframe layers on the reliable
     stream. Choosing a session's delivery is then one condition ("a shared view, or no datagrams"), not a
     second protocol.
     - **Why.** It keeps the fallback cheap. Corey agreed on 2026-11-17 to keep the fallback.
     - **Do not** design a WebSocket-specific delta path.
4. **The WebSocket moves to the edge,** so Node has one peer type: the full conversion (27).

## Stage 1's contracts

These are agent decisions made under #1095. Two contracts carry stage 1: the client stream between the browser
and the edge, and the link between the edge and Node.

### The client stream

- **The session.** The browser opens `https://<page host>:<edge port>/arena`. Any other path is refused (404).
- **The stream.** After the session is ready, the client opens one bidirectional stream. Every message, in both
  directions, travels on it.
- **Framing.** Each message is a frame:
  - a `u32` big-endian length of what follows;
  - a `u8` flag, 0 for text (UTF-8) and 1 for binary;
  - the payload.
- **Messages.** They are today's messages, unchanged: JSON text, and the codec's binary `state` (24.1), with stage 3's
  `slow` and an overflowing `fast`.
- **Inbound limit.** A client frame whose payload exceeds `MAX_MESSAGE_BYTES` closes the session with 1008. Node
  supplies that limit over the link.
- **Closing.** A close carries the WebSocket's code (1000, 1008) as the session's application error code, and
  its reason as UTF-8.
- **Origin.** The edge refuses a session request (403) whose `Origin` names a different host or port from the
  page's: the request authority's host name with Node's HTTP port. A request without `Origin` is allowed, as
  `server/websocket.js` allows it.

### The link

One TCP connection on loopback. Node listens on it, and the edge connects and reconnects if it drops. Node accepts
one edge at a time. When the link drops, Node disconnects every session it carried and the edge closes them.

**Frames.** Each is a `u32` big-endian length of what follows, a `u8` type, then the body. A control body is UTF-8
JSON. A session id is a `u32`, assigned by the edge and never reused while its link lives.

| Type | Direction | Body | Meaning |
| --- | --- | --- | --- |
| `0x01` EDGE | edge → Node | JSON `{ link, port, certificateHash, validUntil }` | Sent first, and again after each certificate rotation. `port` is the UDP port bound. `certificateHash` is the hex SHA-256 of the DER certificate, or null for a CA-issued one. `validUntil` is in Unix milliseconds, 0 for a CA-issued one |
| `0x81` ACCEPT | Node → edge | JSON `{ link, httpPort, maxMessageBytes }` | Node's answer to the first EDGE. A different `link` version closes the link |
| `0x02` OPEN | edge → Node | `u32` session | A session passed the origin check and opened its stream |
| `0x03` MESSAGE | edge → Node | `u32` session, `u8` flag, payload | One client message |
| `0x82` DELIVER | Node → edge | `u32` session, `u8` flag, payload | One message to write to the session's stream |
| `0x04` WRITTEN | edge → Node | `u32` session, `u64` bytes | Cumulative payload bytes of DELIVER frames written into the session's QUIC stream |
| `0x83` CLOSE | Node → edge | `u32` session, `u16` code, UTF-8 reason | Close the session |
| `0x05` CLOSED | edge → Node | `u32` session | The session ended. Node disconnects it, and sends nothing more for it |
| `0x06` DATAGRAM | edge → Node | `u32` session, payload | One client datagram, unparsed ([stage 2](#stage-2s-contracts)) |
| `0x84` SEND | Node → edge | `u32` session, payload | One message to send to the session as datagrams ([stage 3](#stage-3s-contracts)) |

The link version is 4. Stage 2 added DATAGRAM. Stage 3 changed what a DATAGRAM's payload holds (the envelope
below, with its acknowledgement), which took it to 3 although no frame changed, and then added SEND.

The frame types live once on the Rust side, in `rust/edge/src/frame.rs`'s `link` module. In the fast tier,
`tests/edge-contract.test.js` reads them, the link version, the message flags and the edge's close codes from
the Rust source. It holds to them Node's `FRAME`, `LINK_VERSION` and `FLAG` (`server/edge-link.js`), the
client's `FLAG` (`public/arena-socket.js`), the protocol's 1000 and 1008, and this document: the table above, the
version, the client stream's flags and the edge's own closes below. Change them together.

**The edge's own closes,** beside Node's CLOSE:
- **1008** for an oversized or malformed client frame (a flag above 1, or a zero length), and for a session that
  opens no stream within 10 s.
- **1001, "link lost"** for every session when the link drops.
- **While no link is accepted,** the edge refuses new connections, before or during their handshake.

**Backlog.** A session's backlog, as `buffered()` reports it, is the payload bytes Node has sent in DELIVER frames
minus the session's latest WRITTEN.
- **Why that is true.** The edge caps QUIC's unacknowledged bytes per connection (`send_window`, 256 KiB), so a
  write completes only when the client is keeping up. The backlog then sits where Node can count it, and `deliver`
  skips droppable frames against it as it does for a WebSocket (`deliverable`).
- **Rate limits** stay in Node, per session, as for a WebSocket.

**Certificates.** Without a certificate file the edge makes a self-signed ECDSA P-256 certificate valid for under
14 days, and rotates it after 10. Each new one goes to Node in an EDGE frame. `--cert` and `--key` load a
CA-issued one instead.

**What the browser learns.** `/api/client-config` carries `webTransport`: null when no edge is linked, otherwise
`{ port, certificateHash }`.

**Fallback.** The client tries WebTransport when the config offers it and the browser has it.
- **The 3 s budget.** One 3 s budget covers fetching the config and opening the session and its stream. If it runs
  out, or the attempt fails, the client falls back to the WebSocket and uses it for the rest of the page's life.
- **Forcing.** `?transport=ws` forces the WebSocket. `?transport=wt` forces WebTransport with no fallback.
- **Refreshing the offer.** The page fetches the config once. After a failed or abandoned WebTransport attempt it
  forgets that answer, so a forced page learns a restarted edge's new certificate. A page that has fallen back
  never asks again.
- **Closing early.** Closing a socket while WebTransport is still opening closes that session at once.
- **Binary messages** arrive as a `Blob` unless the caller sets `binaryType` to `arraybuffer`, as on a WebSocket.

## Stage 2's contracts

These are agent decisions made under #1095. Inputs move to datagrams. Everything else stays on the stream, and
the room still cannot tell the transport.

**The client.** `sendInput` (`public/arena-socket.js`) sends `input` messages only; every other message uses
`send`.
- **On a session with datagrams,** each input goes as one datagram: a UTF-8 JSON object `{ ack?, inputs }`,
  whose `inputs` are input messages, oldest first, and whose `ack` is stage 3's acknowledgement. It carries the
  new input and the two sent before it (`INPUT_DATAGRAM_INPUTS`, 3, in
  `shared/protocol.ts`), so a lost datagram's input arrives with the next.
- **The size.** The client reads the session's `maxDatagramSize` at every send and drops the oldest copies until
  the datagram fits. An input that does not fit alone goes on the stream, and later datagrams do not repeat it.
- **Without datagrams,** and on a WebSocket, `sendInput` is `send`.
- **The messages are unchanged.** Each is today's `input`, with its `seq` and tick stamp (#1096). The stamps
  order inputs at the tick, so arriving out of order costs nothing. Adding the path took `WIRE_VERSION` 7 → 8.

**The edge** forwards each datagram to Node as DATAGRAM, without reading it. It drops an empty one, or one longer
than `maxMessageBytes`, as if lost; the session stays open.

**Node** (`server/edge-link.js`) turns datagrams back into what a WebSocket would have given the room.
- **The envelope.** A datagram must be an object `{ ack?, inputs }` (`parseInputDatagram`). `inputs` holds up to
  three `input` messages whose `seq` values are non-negative safe integers and strictly increase. It may be
  empty only beside an `ack`. `ack`, when present, is a non-negative safe integer. No other key is allowed. Anything else closes the session with 1008, "Invalid
  message". Each input is then validated like any client message.
- **Once each, in order.** An input passes to the room only when its `seq` is newer than every valid input passed
  on before for that session, from either the stream or a datagram. The repeated copies, and a late datagram, pass
  nothing on. An invalid input still goes to the service to be refused, but its `seq` does not count, so it cannot
  hold back the valid inputs after it.
- **The rate limit** counts inputs, as on a WebSocket. A datagram costs one message, and each new input in it past
  the first costs one more. A datagram of repeats alone still costs one.
- **The size.** The client caps a datagram at `MAX_MESSAGE_BYTES` as well as `maxDatagramSize`, since the edge
  drops anything longer.

**Not in stage 2.**
- **Loss under real conditions is not measured.** No check drops datagrams between Chrome and the edge. The
  redundancy covers losing up to two datagrams in a row, by construction; a burst of three or more loses the
  inputs in it.
- **Acknowledgements** ride the input datagrams since stage 3. The redundancy is still fixed, not driven by what
  the server has received.

## Stage 3's contracts

These are agent decisions made under #1095. Stage 3 lands in several PRs, and this section grows with them.

**The fast part** (`shared/fast-state.ts`) is a player view without its slow fields: `items`, `gates` and
`self.discovered` (24.2). Everything else in the view is fast state.

**The `fast` message** (`shared/wire-schema.ts`) carries a match frame's fast part, `live` or `finished`, with
its `rosterRevision`. The waiting yard's frames stay `state` messages on the stream. The message is either:
- **whole:** the fast part as `state` would carry it, with the slow fields left out; or
- **a delta:** the changes from a baseline the reader holds, named by a number. That number is the baseline's
  tick. The writer chooses it; the reader looks it up.

**Deltas** are the codec's (`shared/wire-codec.ts`, "Deltas"). They are typed by the schema, so they need no
dictionary and no message but their baseline.
- **Records:** a changed-field mask, a removed-field mask when a field went, then each changed field. A field
  the baseline also holds travels as its own delta (the viewer's own record, for example), otherwise whole.
- **Unions** (`phase`, a body's `shape` and `owner`): the variant's delta when the tag is unchanged, else whole.
- **Keyed lists** (players by `playerIdx`; bodies, tethers, hook flights, traps, projectiles, effects and events
  by `id`): additions, changed entries as deltas, dropped keys, and the full key order only when the shared
  rebuild rule (`shared/keyed-list.ts`) would not give it.
- **Exactness:** the rebuilt fast part equals the one written (deep equality, absent and undefined alike).
  Unchanged records keep the reader's objects.
- **Refusals:** malformed changes are refused as any malformed message is. A delta whose baseline the reader
  does not hold is refused with `MissingBaseline`, so the client can discard it and keep acknowledging its
  newest frame (24.2 "Recovery").

**Delivery** (`server/room-views.js`, behind the session seam). It took `WIRE_VERSION` 8 → 9 and the link 2 → 3; making it live (the edge's send and the client's apply) took them to 10 and 4.
- **One condition** (`deliversFast`). A player session whose transport has datagrams, and whose state is binary,
  gets the split. A shared view (dev, delayed spectators), a session without datagrams, or a JSON session gets
  today's `state` on the stream, as 24.2 decision 2 gives the shared views. There is no second delta path.
- **The seam.** A session that has datagrams supplies `datagram(bytes)` beside `deliver`. The room learns it at
  join from the host (`onJoin`'s `transport`), never from the client. The waiting yard is unchanged.
- **Fast state** goes as a `fast` message on a datagram, every tick. It is a delta against the session's newest
  acknowledged frame while the history holds that frame, and whole otherwise. A session that has acknowledged
  nothing, or only frames the history has dropped, is sent whole frames every tick until it acknowledges one.
- **The history** (`createFastHistory`, `shared/fast-state.ts`) is per player session. Since a player view has one
  session, that is per view. It keeps the fast frames sent, as `fastFrame` returns them, for the last 32 ticks.
  A tick recorded twice is never a baseline: a paused room re-sends its tick after a dev teleport, and the reader
  could hold either frame.
- **Acknowledgements** ride the input datagrams (`ack`, the tick of the newest fast frame the client holds). An
  idle client may send one with no inputs. The link drops a repeat and passes the rest on (`acknowledge`). The
  room keeps the newest that is no later than the match's tick. A late, older one changes nothing, and a future
  one is ignored, so a stray value cannot outrank the true acknowledgements after it.
- **The edge's send.** Node sends each `fast` message for a session as one SEND frame. The edge splits it into
  datagrams, each a `u16` big-endian message number (per session, from 0, wrapping), a `u8` index and a `u8` count,
  then at most 1,100 bytes of the message, in at most 4 datagrams (`frame::datagram` in `rust/edge/src/frame.rs`).
  - **Why 1,100.** A datagram is then at most 1,104 bytes, which fits the smallest WebTransport datagram QUIC
    allows at its minimum 1,200-byte path MTU (about 1,146 bytes), so the limit holds on any path without
    MTU discovery. On loopback the session's limit was 1,381 (2026-11-18).
  - **Size enforcement.** The edge sends nothing for an empty message or one over 4,400 bytes; its number is
    still spent. Send errors are ignored, as loss is. Datagrams go straight to the connection, never queued
    behind the stream's writes.
  - **The client** (`createDatagramAssembler`, `public/arena-socket.js`) dispatches a message as a binary
    `message` event once all its fragments have arrived, as if it came on the stream. A message that lost a
    fragment is forgotten (see "Reassembly" below).
- **The slow layers** (items, gates, own discovery) go on the stream as a `slow` message. It holds the keyframe
  layers exactly as `state` carries them, whole to a session that lacks a keyframe. It is sent only when the
  session does not hold the current version, so a tick that changes no slow layer sends none. Like `state`, it
  can be skipped under backlog and is then sent again.
- **Version stamps.** `slowVersion` numbers a view's slow layers from 1, and changes whenever what they say
  changes (compared by content). `slow` carries it, and each `fast` names the one its frame was projected with,
  so a reader knows when its slow layers lag its fast state.
- **The item-body hold** (`holdItemBodies`, `shared/fast-state.ts`). A reader draws a fast frame without any item
  body whose item it does not hold, and without any tether to such a body, as the projection leaves out a body
  whose item the view is not shown. It keeps the rebuilt frame itself as its baseline. The client's apply calls
  it.
- **Events** (24.2 "Message and coverage"). A match keeps its newest six events (`KEPT_EVENTS`,
  `shared/simulation/rules.ts`), so over datagrams an event would reach a client only if a frame holding it
  arrived before six newer ones pushed it out.
  - **The window** (`createEventWindow`, `shared/fast-state.ts`). Each fast view's frames also carry every event
    from the last 32 ticks (`FAST_HISTORY_TICKS`), the history's span, before the six the projection gives, in
    the order they happened. A client that keeps any frame within 32 ticks of an event receives it. The room keeps
    one window per fast view, beside its slow versions. `state` sessions, recordings, the simulation and the frozen
    fixture are unchanged: the window belongs to the split delivery alone.
  - **De-duplication is the reader's** (`keptEvents` and `arrived()` in `createFastReader`). Only the client knows
    which frames arrived; the server never assumes one did (24.2 "Recovery"). The drawn frame carries the newest
    six of the events held and those the frame carries, so it is what a `state` of the same tick would show, and
    the HUD needs no change. `arrived()` gives the events first held with the newest frame, each once and in order,
    including those a burst pushed past the six. An event is in the window for one unbroken run of ticks, so
    comparing with the frame kept before is enough. It is per call: empty after an ignored (older) frame, and set
    for a frame kept before any `slow`, which draws nothing yet. No page reads `arrived()` yet; a feed that must
    show every event would.
  - **Limits.** More than six events between two broadcasts are lost on `state` and fast alike, since the window
    starts from the projection. A client that keeps no frame for 32 ticks recovers with a whole frame, which
    still carries the newest six. A page that resumes builds a new reader, so its first frame's window may give
    again events the old reader gave; a feed spanning a resume compares ids. The room keeps a view's window only
    while the view is delivered fast, so a player resumed on a WebSocket drops it.
  - **Size.** An event costs about 34 bytes (an elimination with two names). A delta carries only the events new
    since its baseline, whatever the window holds. A whole fast frame on the room tests' arena grows from 494 B to
    about 1,580 B with 32 events in the window, and would exceed `MAX_FAST_DATAGRAM_BYTES` past about 115. That
    takes more than three events a tick for 1.6 s. Overflow then goes on the stream as before. The arena itself
    raises no events in 120 ticks, so its sizes below are unchanged (2026-11-18).
- **Overflow.** A `fast` message over the edge's four 1,100-byte fragments (`MAX_FAST_DATAGRAM_BYTES`, 4,400)
  goes on the stream instead, where it can be skipped like a `state`. `tests/edge-contract.test.js` holds the
  fragment size and count to the edge's. The `loop.fastWhole`, `loop.fastDelta` and `loop.fastStreamed`
  profiler counts say how often each happens.
- **The client's apply** (`public/room-connection.js`, through `createFastReader` in `shared/fast-state.ts`).
  - **Decoding.** A `fast` message, from a datagram or the stream, is decoded with the frames the reader holds
    as baselines. One naming a baseline it lacks (`MissingBaseline`) is discarded.
  - **Order.** A frame older than the newest held is ignored. A frame of the newest tick again (a paused room's
    re-send after a dev teleport) is drawn, so the teleport shows, and that tick is then no baseline, as on the
    server. Every other frame becomes the newest, kept as rebuilt as a baseline.
  - **Acknowledging.** The page acknowledges its newest frame after each `fast` (`socket.acknowledge`). The
    acknowledgement rides the next input datagram, or goes alone (`packInputDatagram([], max, ack)`) when no
    datagram has gone for 100 ms (`ACK_ALONE_MS`), as for a dead player or a page waiting for the match.
  - **Slow layers.** A `slow` message goes through the socket's layer decoder and the discovery decoder, as a
    `state`'s layers do. `fast` and `slow` are read only as bytes, and only on a binary session.
  - **Drawing.** The drawn frame is the fast part through `holdItemBodies`, with the newest six events (see
    Events), the items and gates held, and the message's `rosterRevision`.
  - **Waiting on the stream.** A datagram can overtake the stream, so the newest frame is always kept and
    acknowledged, and drawn once what it needs has arrived:
    - the first `slow`;
    - the match's map: a frame that overtook `ready` (or arrived before a welcome to a started room) waits for
      it, never drawn on the waiting yard's map. The reader lasts the socket, since a room plays one match;
    - its roster: a frame whose `seats` is still on the stream waits for it, rather than ending the connection
      as such a `state` does. Any other normalizing failure is unreadable, as for a `state`;
    - the slow layers it names: a frame drawn with older layers than its `slowVersion` is drawn again when that
      version or a later one arrives (a skipped `slow` is re-sent at the current version), since after a pause or
      the match's end no later frame may follow them.
    - the welcome itself: a `fast` can overtake it at join, before the session's encoding is known. It is kept
      and waits for the envelope; once the encoding is known, a `fast` or `slow` on a JSON session is unreadable.
  - **Reassembly.** The client keeps at most eight incomplete messages, none more than eight message numbers from
    the newest datagram's, so a fragment cannot linger until its number wraps round.
