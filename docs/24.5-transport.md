# 24.5. Transport: WebTransport with a WebSocket fallback (#1095)

Up: [24](24-networking-privacy.md). The split it carries: [24.2](24.2-lossy-transport-deltas.md). Evidence:
[42.56](42.56-transport-probe.md). **Proposed, awaiting Corey's decisions below; nothing here is implemented.** The
live protocol is still one WebSocket per connection (24). No simulation, input order, recording or fixture change
is proposed.

## Recommendation

Serve WebTransport (HTTP/3 over QUIC) from the room host's own Node process with
`@fails-components/webtransport`, and keep the WebSocket behind the same session seam as the fallback. Build it in
three stages (below), the first of which changes no behaviour.

Corey's lean (17.4 #14) was WebTransport over ENet or LiteNetLib. That stands: browsers cannot open raw UDP
sockets, ENet and LiteNetLib run over plain UDP, and LiteNetLib is C#. Neither can serve the browser client;
ENet would matter only for a future native client. WebRTC data channels are the other browser option, but they
need ICE/STUN signalling and an SCTP stack on the server for a client–server game, which WebTransport does not.

## What the evaluation found

Checked 2026-11-17. The prototype is `tools/perf/transport-1095-probe.mjs`; its results are 42.56.

- **Browsers.** WebTransport is Baseline: Chrome 97+, Firefox 114+ and, since March 2026, Safari 26.4+ (from
  MDN's Baseline status and secondary reports of Apple's release notes; the notes were not read directly). Older
  Safari, and networks that block UDP, still need the WebSocket fallback.
- **It works here.** The candidate's prebuilt Windows binary loads in Node 24.15, and headless Chrome opened
  sessions to it with a short-lived certificate's hash. Datagrams, a server-opened reliable stream and
  client-to-server datagrams all worked through a lossy UDP relay.
- **Under loss it behaves as 24.2 modelled.** Datagrams lose frames but their staleness tail stays short. The
  reliable stream delivers everything but stalls behind each loss. 42.56 has the numbers per profile.
- **The datagram cap.** Chrome reported `maxDatagramSize` 1,211 bytes on loopback, against 24.2's conservative
  1,200. It is path-dependent: read it per session, never assume it.
- **An oversized datagram vanishes silently.** Chrome resolved the write of a 1,300-byte datagram without an error,
  and it never arrived. The sender must enforce the cap itself (24.2's fragmentation and reliable-stream fallback).
- **API drift.** `datagrams.writable` is deprecated in favour of `datagrams.createWritable()`; the probe uses the
  new form where present.

| Go `quic-go/webtransport-go` | MIT | Upstream says it is unfunded and no longer tracks quic-go | Not recommended |
| Node's own `node:quic` | MIT (Node) | Experimental (`--experimental-quic`), QUIC and HTTP/3 only, no WebTransport | Revisit when Node ships WebTransport; it would replace the addon behind the same seam |

The addon's risk is a native binary with one main maintainer. Two things contain it. The seam keeps the
transport replaceable by the gateway or by `node:quic`, and the WebSocket path stays the fallback. The addon's own
dependency tree (`bindings`, `debug`, `prebuild-install` and theirs) is MIT, ISC, BSD, BlueOak-1.0.0 and
Apache-2.0. It runs on the server only, so it adds a notice obligation only to a deployment artefact that bundles
`node_modules` ([21.1](21.1-third-party-licenses.md)).

### Certificates and reachability

- **Development.** `serverCertificateHashes` accepts a self-signed ECDSA P-256 certificate valid for under 14
  days. The server generates one at start and rotates it before expiry, and the client learns its hash from
  `/api/client-config` before opening the session. That needs no CA or browser flag.
- **Production.** A certificate from a public CA for each room host's name. With direct connect (28.1), each room
  host terminates its own sessions, so each needs its own name and certificate.
- **UDP.** The room host needs a UDP port open through the NAS, VPS and any firewall (#907). Where UDP is blocked,
  the client falls back to the WebSocket.

## Channels

| Traffic | Channel |
| --- | --- |
| Session admission, `welcome`, lobby, pause, errors, replays, `ping`/`pong` | One client-opened reliable bidirectional stream, in today's message forms |
| Slow layers: items, gates, own discovery | That reliable stream (24.2) |
| Fast state: everything else in a player view | Datagrams, acknowledged-baseline deltas (24.2) |
| Shared views: dev, delayed spectators | The reliable stream only (24.2 decision 2) |
| Inputs | Datagrams, each carrying the last few inputs, because the sequence guard refuses an input overtaken by a newer one (24 "Tick-stamped input") |

## Stages

Each stage is one PR or a few, with its own checks and a `WIRE_VERSION` bump where the wire changes.

1. **Same messages on a reliable stream.** A WebTransport session becomes another peer behind the session seam
   (`deliver(payload, droppable, binary)`, `close`; `server/room-service.js`). Every message travels on one
   bidirectional stream, length-prefixed with a text/binary flag, so a room cannot tell which transport a
   session uses. The client tries WebTransport and falls back to the WebSocket on failure or timeout; a dev flag
   forces either. This stage gains nothing in staleness. It lands the dependency, certificates, fallback,
   reconnection and browser tests, so later stages change only what travels where.
2. **Inputs on datagrams,** with redundancy. Lost input packets stop costing the stalls a reliable stream adds,
   and the tick stamps of #1096 already order them.
3. **24.2's split.** Fast state on datagrams, with acknowledgements riding the input datagrams, a 32-tick history,
   whole-frame recovery, the item-body hold and the version stamps 24.2 lists. It needs the codec's changed-field
   masks. Roster revisions are compared for equality only: a revision identifies a roster's content, not its
   order (24 "Schema closure").

[41](41-roadmap.md) places WebTransport implementation in its "Later" tier, behind public-scale needs. Stage 1
is the cheapest place to start if Corey wants it sooner.

## Decisions for Corey

1. **Server stack:** the Node addon in process (recommended), or a Rust `wtransport` gateway.
2. **Timing:** start stage 1 now, or keep transport in 41's "Later" tier and leave this as the recorded design.
3. **The dependency:** adding `@fails-components/webtransport` and its quiche transport, pinned exactly, at stage
   1, with its licences recorded in 21.1.
