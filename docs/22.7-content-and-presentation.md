## Owners and dependency direction

| Data or decision | Owner and planned use |
| --- | --- |
| Retained and shipped content | `shared/simulation/content.ts`: complete retained literals, `contentById`, `defaultContent`. Roster, weapon/kit/trap tuning and existing content timers stay here. |
| Standalone compatibility defaults | `equipment.WEAPONS` and `rules.KITS` become detached mutable copies of the shipped content tables. The four exported timing defaults derive from the same shipped content. Existing paths, keys, ordering, signatures and facade exports remain. |
| Live match values | The match's pinned content, never those compatibility exports. Explicit weapon-table parameters in equipment helpers remain supported. |
| Display projection and resolution | New `shared/presentation.ts`: pure descriptor construction, parsing and recording fallback resolution. Types belong in `shared/types.ts`; this module imports content, never the simulation facade or server. |
| Shared interaction rules | Named constants in `shared/simulation/rules.ts`, and the pure gate query below. Naming existing rules does not move them into retained content. |
| Body geometry | `movement.bodyRadius`: gate closure can call it for the existing 12/23 radii. Respawn's 25-unit clearance remains a separately named rule. |
| Admission and room policy | `server/protocol.js` owns seed, room-name and authored-size validation; `room-service.js` owns countdown and idle expiry. The browser receives their public values through configuration. |
| Display context | `client.js` chooses the live, dev or replay descriptor. HUD and vocabulary helpers receive it explicitly. No module-global active content setter. |

The content module stays a data leaf (type imports only). Deriving compatibility
exports must not create a `content -> rules/equipment -> content` cycle. Keep the
literal `content-1` contract independent; neither retained nor current content
may be built from mutable compatibility exports. Copies must detach nested
arrays such as weapon spread. Mutation of an export must still leave both
content IDs and existing matches unchanged. The public simulation facade stays
exactly as pinned by `tests/boundaries.test.js`; new consumers import the narrow
module directly.

## Presentation descriptor

`describeContent(content: MatchContent): ContentPresentation` produces a detached,
deeply frozen plain-data value with these fields:

```ts
{
  contentId: string,
  weapons: Array<{ id: string, name: string, ammo: number }>,
  kits: Array<{ id: string, name: string, skill: string }>,
  capacity: { contestant: number, gladiator: number },
  durationTicks: number,
  cellChargeTicks: number
}
```

Weapon and kit entries retain `Object.entries` order from their source tables.
Role capacities count the two roster arrays; kits list the content's available
kit table, not merely the kits initially occupying its roster. This preserves
the current distinction: `content-1` has two gladiator seats and three available
kits. The descriptor contains no actor names, loadouts, locations, traps, damage
tables, secrets or commands. Glyphs, role words and utility item names remain
client presentation vocabulary. Kit colour has no current table-reading display
consumer and need not be transported.

`readPresentation(value: unknown, expectedContentId?: string)` returns a detached
frozen descriptor or `null`. Validate the complete required shape: nonempty IDs,
strings for labels, unique entry IDs, nonnegative safe-integer ammo/capacities,
and positive safe-integer durations. If an expected ID is supplied it must match.
Ignore extra fields; do not merge an invalid descriptor piecemeal with today's
content. Labels are always rendered with text/DOM APIs, never interpreted as
HTML. Lookup must not treat inherited object properties as entries.

The descriptor is display data, not sufficient to instantiate a simulation or
authorize a kit, pickup or input. It does not negotiate a new rules version,
tick rate, weapon mechanic or arbitrary plugin kit. Existing server validation
remains authoritative.

### Live transport and ownership

At room creation, derive and retain the descriptor from the same `lobby.content`
that is passed to `createMatch`. Expose it through the normal lobby/match adapter
surface; application code must not inspect `diagnosticState` or `room.game`.
All three welcome branches (player, spectator, dev) carry
`contentId` and `presentation`, including a welcome with `ready: false` and no map.
Every `ready` repeats both fields so a map/state replacement is self-contained.
Do not attach either table to `state`, snapshots, layered frames or inputs.
Lobby roster/capacity broadcasts retain their existing shape and authority.

The server serves the browser and shared modules from the same build. This
design therefore requires both fields on every live welcome/ready, rather than
supporting a mixed-generation live protocol. The descriptor must pass
`readPresentation` with the envelope's nonempty `contentId`; reject a malformed
envelope before installing its map/state/metadata. A valid descriptor may name
content unknown to the browser's retained registry. The retained/legacy/unknown
fallback chain below is for recordings, not live connection setup.

The waiting yard uses the room's labels and choices, but keeps its existing
movement-only simulation. This design does not inject match tuning into waiting
movement or reveal the match map before the start. Describing content consumes
no RNG, creates no player IDs and does not enumerate/reorder live players.

`client.js` keeps separate `liveContentPresentation`, dev-feed metadata and replay
metadata, distinct from its existing interpolated-frame variable `presentation`.
Install metadata before rendering a corresponding welcome/ready state. Reset
room metadata on a new connect. On socket close, retain it alongside any retained
last live map/state for offline display; clear all three when that room view is
discarded. Invalidate the old socket's ability to install later metadata.
An incoming live welcome/ready can update
the saved live context while a replay is shown, without replacing the replay's
labels. Closing playback restores the latest live descriptor with its map/state.
Dev step-out/back follows the same ownership rule. A late response from a prior
connection or replay request cannot install its descriptor after that lifecycle
has ended; coordinate with the guards in #387.

HUD `render` receives an explicit descriptor. Extend `slotPresentation`,
`kitName`, `kitSkill` and `fillFollowOptions` with explicit context parameters;
pass the relevant context at every production call site, including lobby and
dev/replay selects. Optional arguments for standalone consumers may resolve a
detached shipped default, but an explicit unknown context must never do so.
Rebuild labels/options on descriptor changes even if IDs/counts did not change.
Preserve a selected kit if it remains available; otherwise select `warden` when
offered, then the first offered kit. An empty kit list disables kit choice.
Do not automatically send a `choose` command while rebuilding controls.

## Recording compatibility

New recordings carry the same optional top-level `presentation` value once,
beside their existing `contentId`. The room service constructs it before the
first frame; the writer only serializes it. On implementation, advance recording
schema **5 to 6**, leaving `MIN_SCHEMA` and `minimumReaderForMap` unchanged.
If another additive schema has landed first, allocate the next unused schema
instead and update [26](26-recording-contract.md). Older readers can ignore this
field and still play the map/frames. This is not a change to `VERSION`, either
content ID, frame key order, commands, retained-frame hashing or the frozen
characterization fixture. Existing archives are not rewritten.

`resolveRecordingPresentation(header)` returns
`{ source: 'embedded' | 'retained' | 'legacy' | 'unknown', presentation }`.
`presentation` is a descriptor or `null` for unknown content. The legacy profile
uses the local-only ID `legacy-display`, never written as a match content ID or
passed to `contentById`. Resolution follows this order:

1. A valid embedded descriptor whose ID equals the header's nonempty string
   `contentId`, including an ID unknown to this build.
2. The retained descriptor from `contentById(contentId)`, when that exact ID is
   known. An invalid/mismatched embedded descriptor is ignored, not trusted.
3. With no `contentId` field, a named immutable legacy display profile. Preserve
   the existing pre-content fallbacks: weapon/kit vocabulary and default ammo
   from retained `content-1`, missing duration 2400 ticks and charge duration
   100 ticks. This is historical display compatibility, not an assertion that
   an unidentified archive ran `content-1` or today's rules.
4. An explicit unknown or malformed ID gets neutral display data: raw item/kit
   IDs as names, no guessed weapon ammo/skill or duration. Missing numeric
   display values appear as unavailable (`—`); the replay still plays.

An unusable descriptor must never turn an otherwise playable archive into a
format error. `recordingFit` remains the separate map/schema gate; neither
content lookup nor descriptor parsing resimulates a recording.

For every context, authoritative frame fields take precedence: present ammo,
duration and `cellChargeTicks` beat descriptor fallbacks. Preserve zero ammo;
use validity/absence checks rather than truthiness. Unknown content with valid
frame timing still shows its clock and charge progress. Legacy dedicated `cell`
display remains supported. Replay pacing continues to use recorded `hz`; any
clock formatting touched here takes that value explicitly (valid positive rate,
otherwise the historical `HZ` fallback). Live simulation/prediction stays at
`HZ`. Changing tick rates or archive-list metadata is outside this design.

## Deployment configuration and named rules

Add `GET /api/client-config` in `server/http-api.js`, `Cache-Control: no-store`:

```ts
{
  presentation: ContentPresentation, // default for newly created rooms
  seed: { min: 1, max: MAX_ARENA_SEED },
  roomNameMaxLength: MAX_ROOM_NAME,
  playerNameMaxLength: MAX_PLAYER_NAME,
  sizes: string[], defaultSize: string,
  matchmakingCountdownMs: MATCHMAKING_COUNTDOWN_MS
}
```

Compose values from existing owners: sizes from `ROOM_SIZE_NAMES` and the live
map default, names/seed from protocol/shared rules, countdown from room service,
and presentation from the server's default content source. This endpoint must
not expose any room, owner key or credential. It is a deploy default, not a
substitute for a particular room's welcome metadata or its admission checks.

Populate deploy kit/size options, seed bounds, name limits and countdown prose
after configuration arrives. Preserve URL seed/size overrides and user-entered
values across refresh; never silently replace an unsupported explicit size with
another size. Existing HTTP validation reports refusal. Before configuration is
available, use neutral loading placeholders and disable the deploy form's
creation/matchmaking controls. A failed load shows a retryable form error without
inventing policy values. Direct room links, archive viewing and automatic initial
room creation do not wait for deploy configuration. Existing room membership is
unaffected by its failure.
Lobby controls use the admitted room's descriptor; changing a deploy form must
not alter the current room's labels or choices.

Separate automatic first-load creation from submission of the deploy form:
without a room URL, POST immediately, omitting unspecified seed/size/name so the
server chooses its defaults. Forward explicit URL seed/size overrides to the
existing server validation without waiting for option population. Preserve
the existing default role, kit preference and `Runner` callsign at admission;
do not read unloaded form placeholders as those defaults. Configuration loads
independently for later form use, and a retry must not create another room or
reset an already-admitted session.

Player-name `maxlength` uses the advertised UTF-16-unit limit. Room names are
different: the server normalizes whitespace and counts Unicode code points.
Remove the HTML UTF-16 `maxlength` from that field; show the advertised limit as
help text and let the existing server validator enforce it. This is an
**intentional user-visible behavior change** in #386: the form will accept
astral-character names that its old UTF-16 limit blocked. Record it separately
from behavior-preserving extractions in the implementation PR and handoff.
Server acceptance and normalization remain unchanged; an as-you-type code-point
limiter is not required for this cleanup.

Name these existing values in their owners; preserve comparison operators,
evaluation order and units:

| Owner | Names/values and distinctions |
| --- | --- |
| `simulation/rules.ts` | `GATE_REACH = 85`, `EXTRACTION_REACH = 65`, `CHARGE_REACH = 70`, `PICKUP_REACH = 45`, `TRANSIT_REACH = 70`. Charge/transit are separate policies despite equal values. |
| `simulation/rules.ts` | `RESPAWN_HAZARD_MARGIN = 400`, `RESPAWN_CONTESTANT_DISTANCE = 1000`, `RESPAWN_CLEARANCE_RADIUS = 25`. Keep strict `>` margins and the 25-unit occupancy test; do not substitute the 23-unit body radius. |
| `simulation/rules.ts` | `MAX_PLAYER_NAME = 16` counts UTF-16 code units, matching existing `slice`/HTML behavior; `ROLES` keeps contestant before gladiator; `DEFAULT_KIT = 'warden'` is the existing preference/placeholder, not permission to use a kit missing from content. |
| `simulation/rules.ts` | `INITIAL_ESCAPE_SLOTS = 3`, reused by game initialization and current-rule UI. This is not a roster capacity or a new content field; retain a separate historical fallback for old replay outcome display. |
| `room-service.js` | `MATCHMAKING_COUNTDOWN_MS = 15000`, `UNSTARTED_ROOM_IDLE_MS = 180000`; retain existing expiry predicate (also covers finished empty rooms), countdown clock/start gate and the separate 30000 ms live grace. |
| Existing local owners | Keep transport fallback `Player`, client default `Runner`, direct simulation default `You`, and the renderer's self-label `YOU` distinct. Name repeated defaults locally; do not unify their semantics. |

Do not add these fields to `content-1` or repin them as balance data during this
cleanup. Moving a rule into future versioned content is a separate change.
Remove static claims such as `0/2` gladiators from initial HTML; capacities come
from the descriptor/lobby, never the number of kit choices. Decorative initial
seed/clock/slot values become neutral until the relevant state is available.

## Gate query contract

Add a pure `nearbyGate(map, point, { accepts, order })` in a narrow
`shared/gate-query.ts` module importing movement geometry, the shared reach and
types, with no simulation effects. `accepts(gate)` is a side-effect-free caller
predicate; `order` is explicitly `nearest` or `map`. Both policies require strict
distance `< GATE_REACH` and `lineClear(map, point, gate, gate.id)`: ignore only
the candidate gate for sight, not other gates/walls. `nearest` preserves the
current stable distance-sort/map-order tie; `map` returns the first qualifying
entry. It must not mutate the map or sort its gate array in place. Return the
original gate or `undefined`; callers retain mutation ownership.

| Caller | Policy to preserve |
| --- | --- |
| `interactions.interact` | `nearest`, accepts `!player.bot || !gate.open`; all gate kinds participate. Locked/key availability and blocked closure do **not** filter selection: the nearest unusable gate still consumes this interaction. |
| HUD door hint | `map`, accepts only `kind === 'door'`. Keep current hints, including locked/keyless and occupied-door hints. This is a proximity hint, not proof E will perform that action. |
| Bot intent | Retain the existing closed-gate proximity predicate, without adding sight/key filtering. Share only `GATE_REACH`; the later authoritative interaction still decides the result. |
| Micro lab / generation demo | Retain nearest/no-LOS selection and walker-only `canOccupy` closure. Share only the reach constant in #386; no production gate query substitution. |

Keep authoritative action precedence: extraction, charging, full-inventory
pickup, gate, transit. Keep lock fallback `gate.locked ?? gate.kind !== 'door'`,
key spending, bot/open-gate behavior and path clearing. Closure remains limited
to a human closing an open door, blocked by any active player's existing
rectangle-to-circle strict-overlap test; use `bodyRadius(other)` without changing
that geometry. A locked gate with no key must not fall through to another gate
or transit. Changing HUD hints to predict the complete action, or making labs
follow gameplay sight/keys, would be a separate behavior decision.

## Acceptance for implementation

| Case | Required witness |

| Mutable compatibility exports | Mutate nested standalone tables; retained/current content and already-created matches remain unchanged; public facade and default equipment behavior remain compatible. |
| Different live content | An internal injected content supplier with different weapon name/ammo, kit name/skill, roster sizes and timers feeds room creation. Derive the descriptor from that same pinned content and assert match/descriptor agreement in player, spectator and dev welcomes, including map-pending and waiting-to-match `ready`.
