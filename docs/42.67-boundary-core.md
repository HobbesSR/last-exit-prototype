# 42.67. The tick boundary's body work in the Rust core (#1234)

Up: [42](42-performance-history.md). Design: [27](27-rust-path.md#the-state-flip), step 5b.3. The work is
`rust/core/src/boundary.rs` and `placement.rs`, driven by `shared/simulation/boundary.ts`, with phase 1's queries in
`phase_one.rs`. `characterization-physics`, its `-bots` variant and `tests/tick-phases.test.js` passed unchanged.

## Finding

**The tick costs what it did. The body sync is level with the TypeScript within the runs' noise, and phase 1 with its
queries is unchanged. So 42.58's budget is met without the state-flip exception.** The first version was not: it
cost about 25 µs a tick more, which the profile below found and the fix removed.

| 24x12, seed 4217, ticks 301–900, median of 5 rounds per run | `main` (713ac3da) | This branch |
| --- | ---: | ---: |
| Body sync (`sim.sync`, three calls a tick, with the item sync) | 65.2–74.0 µs | 66.3–75.1 µs |
| The rest of the step no `sim.*` label times (phase 1, the hooks, the admission, discovery, the finish) | 556.7–573.3 µs | 567.5–571.0 µs |
| Whole tick (`match.advance`, with the snapshot), mean | 4.2–4.4 ms | 4.3–4.5 ms |
| `createMatch`, median of 5 | 180–240 ms | 214–234 ms |

The two "after" rows are the second pair of interleaved runs, taken after the fix. Load on the machine differed
between the pairs: every phase, `sim.bots` included, read about 4% higher in the second.

- **The relative budget.** The sync's crossing overhead cannot be timed apart from the work that moved with it, so
  the module was timed whole. Its cost is unchanged within about ±5 µs, about 7% of its TypeScript cost. That is
  inside 42.58's 10%. As an absolute figure, the difference is under 0.2% of the tick.
- **What the first version cost.** Timed by part, the extra 25 µs a tick were the open-mask writes (three a tick,
  421 gates) and the packing. They hid behind a lookup of every held item body's ground item on every call, which the
  TypeScript also made, about 34 µs a tick. The fix packs only the bodies whose items left the ground. It also parses
  each body's label once (`heldItem`), which more than paid for the masks.
- **Placement per call is level.** On real candidates, a gladiator's placement costs 4.5–4.7 µs in the TypeScript and
  4.5–4.6 µs in the core. The candidates are the 24x12 map's stations and the actors' positions every 20 ticks of a
  600-tick bot match: 336 in all, 38 of which reach the ring search. 42.66's fourfold gain per query does not show,
  for two reasons:
  - the prop test (`overlapsProp`, Rapier's query over the dynamic bodies) is the same in both;
  - one call per search pays the mask write (0.55 µs).
  The two answered all 336 identically.
- **The item admission is chunked.** Packing every item awaiting a body each time a slot freed would have grown with
  the map. Chunks of 32, then 64, keep a sync that admits one item to a few dozen packed (27, step 5b.3).
- **`createMatch` builds the collision upload.** `prepareCollision` builds it in `createGame`, 23–29 ms on this map
  (42.66), so no tick does. It is within the runs' spread here, which the yields and the bot-route preparation
  dominate.

## Method

- **Environment.** The development machine (Windows 11), Node 24, the core built with `npm run core:build` in each
  checkout. 2026-11-20, under the exclusive bench lock, with no orphaned test processes.
- **The scripts** were ad hoc, not committed. Each ran against a checkout: this branch, or a worktree of `main` at
  713ac3da with that commit's core, its `node_modules` a junction.
  - **The tick script** (`bench-boundary.mjs`): the 24x12 live map for seed 4217, built once and cached with
    `v8.serialize`. Each round clones it and calls `createMatch`, steps 300 ticks, then times 600 with the profiler on,
    taking `sim.*` from the profiler's per-tick totals. Five rounds a run; the run reports the median of its rounds.
  - **The placement script** (`bench-placement.mjs`): one match on the same map. After 600 bot ticks it times the
    TypeScript search (the reference in `tests/boundary-core.test.js`) against `placeInCore` over the candidates. That
    is five warm-up passes, then seven rounds of 20 passes in alternating order; three runs.
- **The runs.** Three interleaved pairs before the fix, then two after it. The profile in between added timers to
  `boundary.ts` by part; they are gone.

## Limits

- **Node only.** The browser runs no sync: its prediction makes no game.
- **One map and content.** On a map with more gates the mask writes grow, about 1.3 ns per gate per call.
- **Rare paths are not in the tick figures.** A respawn, an arrival, an attachment or a slot freed for an item shows
  up only a few times in 600 ticks. The placement script times the search itself.
