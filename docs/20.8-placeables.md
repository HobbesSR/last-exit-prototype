A placeable is one kind of thing a builder can put down: a warehouse, a house, a
piece of cover. Each is a code module in `map/micro/placeables/`, because a
placeable may have mechanics of its own that data couldn't describe. The aim is
that builders, and agents writing them, reuse a placeable rather than copying it,
and add new ones the same way.

This is not the macro library (52). That one is data, resolved by `name@version`
across the map. Placeables are code inside a region's strategy. Neither should
be merged into the other.

## What a placeable owns

Corey's answer (17.2.8 M35): a placeable owns what it is and "a demand for
control over an area, but not where that area is".

- **What it is:** `build(params, cellSize)` returns its elements in world units
  local to its body's corner, its demand, and `details` for tools, such as a
  building's design and the designs passed over. Or it returns a `Refusal`
  with a reason, when these parameters can't make one. A defect throws.
- **Its demand:** `body`, the `w` × `h` cells its elements stand in from (0, 0),
  and `clear`, cell boxes outside the body that it relies on staying clear,
  such as a house's doorstep. They are disjoint, so `demandShapes` gives
  shapes an addressed area (20.2) can mark one by one.
- **Not where:** siting stays the builder's. A builder chooses the cell, checks
  its own rules there (ownership, margins, protected routes, aisles, hints),
  and grants the demand. `placedElements` turns the result into the region's
  elements, under the builder's label.

`build` is pure. It draws no random numbers except from a seed in its
parameters, and assigns no ids. Ids come when the region is stamped, in element
and part order (`element.ts`), so a placeable's part order is frozen for its
version. A placeable never calls `nextId` (#343's pitfall). The ids after it
depend only on the parts it emits, so changing them changes its output and
bumps its version.

## The descriptor

```ts
interface Placeable<P, D> {
  id: string;                    // unique in the registry
  version: string;               // 'house-1'
  summary: string;               // one line, for lists
  params: readonly ParamSpec[];  // int | number (bounded), boolean, enum
  check?(params: P): string[];   // rules across parameters
  examples: readonly P[];        // previews and the version test
  build(params: P, cellSize: number): Placed<D> | Refusal;
}
```

Strategies call a descriptor directly, with typed parameters, and
`expectPlaced` for a call they know can't be refused. Tools and agents with
unchecked input call `buildPlaceable(id, params, cellSize)`, which checks
the parameters against their specs and the placeable's `check`, then builds.
The specs and examples are what a tool lists and previews: the Map Lab's
Placeables tab (53) does, editing parameters within their specs.

## Registry and versions

`placeables/index.ts` lists every placeable explicitly, by id. Modules don't
register themselves on import, so the list never depends on import order.

A change to what `build` returns bumps the placeable's `version` and
`REGION_TYPES_VERSION` (53). `tests/micro-placeables.test.js` pins each version
to a digest of what its examples build, so changing output without bumping
fails. The same test requires every module in the folder to be registered and
to open with a header comment naming its id.

Warehouse builders retain their aisle siting rules. Hut and compound mark their
placeable's body and clear demands into their addressed area, then mark the
remaining cells of their existing yard band without overlap (20.2).

Ruins keeps room slots, doorway selection, decay rolls and per-span route
refusal in its strategy. Hall, ruins and rubble retain their legacy aggregated
or world-absolute element records with adapters from local placeable geometry;
the adapters preserve arithmetic order as well as element and part order.
Compound roof groups are local suffixes until the builder scopes them to its
region identity. No placeable receives the site's coordinates or assigns IDs.

The park pocket is a reusable fixed placeable; its descriptor owns the hedge
geometry and body demand, while the park builder owns its optional siting and
route proof. It adds no general growth or macro-library behavior.

## Adding one

1. Add a module to `map/micro/placeables/`. Open it with a block comment that
   starts with `` `id`: ``, followed by what the placeable is and which
   builders use it. Export one descriptor.
2. Add it to `PLACEABLES` in `index.ts`.
3. Pin its version and digest in `tests/micro-placeables.test.js`, and test
   any mechanics of its own there or in its own test file.
4. Add a row to the table above.

When moving an existing piece out of a strategy, prove the move
byte-identical first. Hash every region type's results over a sweep of seeds
and shapes, and a set of live maps, before and after (#405 used 2,080). Don't
regenerate the fixture (31).
