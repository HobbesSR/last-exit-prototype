# 42.59. The split delivery under real loss, Chrome to the edge (#1095)

Up: [42](42-performance-history.md). Design: [24.5](24.5-transport.md) "Stage 3's contracts" and
[24.2](24.2-lossy-transport-deltas.md). It uses the same relay and profiles as [42.56](42.56-transport-probe.md),
which measured the transport with synthetic frames. This record measures our own delivery:
- the edge's fragments;
- the page's reassembly and acknowledgements;
- deltas against acknowledged baselines;
- whole-frame recovery.

## Finding

**Stage 3's delivery holds under real loss.** Chrome played the default room through the Rust edge on each profile,
with a lossy UDP relay between them.
- **Staleness.** The newest drawn frame aged as 42.56's bare datagrams did: p95 112 ms on typical against 110,
  171 against 174 on wifi, 281 against 345 on poor, and 124 against 144 on bursty.
- **Deltas.** In steady play every frame went as a delta.
- **Whole frames** went only while acknowledgements lagged past the 32-tick history, and deltas resumed as soon as
  one landed.
- **Size.** No message fragmented or overflowed to the stream: deltas were at most 245 B.
- **No refusals.** A diagnostic run with counters patched into the page saw no `MissingBaseline`.

**One defect, fixed separately (PR #1202).** On poor every session closed about 2 s into the match with 1008
"Input rate exceeded".
- **The cause.** The server pinged each second whether or not the last ping had come back. A join that took over a
  minute queued about sixty pings on the stream, the page echoed them all at once, and the message-rate limit (70 a
  second) closed the session.
- **The fix.** Pings now wait for their echo. The results below include it.

**The relay sent same-pass packets last-first.** It is shared with 42.56 and now lives in
`tests/helpers/lossy-relay.js`.
- **The bug.** Packets due in the same pass of its loop went out in reverse. Under independent jitter that is rare,
  since packets are due within the same millisecond, so 42.56's numbers were not rerun.
- **Ordered mode.** It reversed most of them, until fixed.

**Reordering explains drawn against received.** On the default relay, each packet draws its own delay, so frames
overtake each other. The reader rightly ignores a frame older than the newest it holds.
- **Wifi:** 97% of messages arrived whole, but 86% were drawn.
- **With `--ordered`,** where each direction keeps its order and jitter queues as on a real path, every frame that
  arrived was drawn: 96.8% on wifi and 96.5% on poor.
- **The cost:** ordered staleness is higher, because a late packet now delays those behind it.

**Joins are slow under latency, mostly through the relay's reordering (#1201).** From page load to the live match
took 10 s on lan, 24 s on typical and 96 s on poor. Ordered, that was 31 s on wifi and 35 s on poor, against 45 s
and 96 s. Chrome's net log showed QUIC declaring losses that the relay never made. #1201 holds the rest.

**Poor's player is a spectator, and its first seconds go whole.**
- **Eliminated during the join.** On the default relay the player was eliminated during the minute-and-a-half join,
  so its deltas are an eliminated view's (15 B).
- **Late acknowledgements.** For the first 3.6 s of the run, acknowledgements arrived 82–89 ticks late, past the
  32-tick history, so frames went whole: 73 of 400, 176 B each.
- **Then deltas.** From the fifth second the newest acknowledgement was 8 ticks old at p50 (26 at most), and every
  frame was a delta.
- **The cause is not shown.** It is probably what the long join left queued in Chrome's uplink. Ordered poor joined
  in 35 s, kept its player alive, and sent no whole frame.

## Results

One 20 s run per profile, about 400 fast messages each. The relay is 42.56's: half the rtt plus exponential jitter
per packet, independent loss or bursty outages, in both directions.

Columns:
- **Received:** of the messages sent in the run, those whose every fragment reached the page.
- **Drawn:** of the same messages, those the page drew.
- **Staleness:** p50 / p95 / p99 in ms.
- **Stall:** the longest time without a new drawn frame.
- **Ack age:** ticks between a send and the newest acknowledgement it was sent against, p50 / max.
- **Delta bytes:** p50 / p95.

## Method

`node tools/perf/fast-loss-1095.mjs --seconds=20 --out=docs/reports/issue-1095/fast-loss.json`, then
`--profiles=wifi,poor --ordered` into `fast-loss-ordered.json`.
- **Environment.** The development machine (Windows 11), Node 24.15.0, Chrome 157.0.8103.51 headless, the edge
  built in release, under the bench lock. 2026-11-19, on PR #1202's ping fix.
- **The match.** The default room on seed 4217, rooms on the host thread, `?transport=wt`. The page reaches the
  edge through the relay because the probe rewrites `/api/client-config`'s port. It starts the match and waits for
  it live, then walks back and forth (D and A, 0.7 s each) for 20 s.
- **Server side.** The player's session `datagram` is wrapped to record each send's tick, size, edge message number,
  the age of the session's newest acknowledgement, and whether it went as a delta: the acknowledged frame was in
  the session's history, as `deliverSplit` decides. The profiler's `loop.fastStreamed` counts overflow.
- **Message numbers.** The edge numbers a session's messages in the order Node sends them. The probe waits until no
  other session is being sent any before it joins, and refuses delivery counts if another send interleaves.
- **Page side.** An init script notes each message Chrome hands the page whole, by number. It counts a message as
  drawn when the page draws (a `net.stateBytes` sample) before reading again. It also notes how each WebTransport
  session ended. The page samples `arenaDebug().buffer.newest` every 10 ms.
- **The window.** All counts are of the messages sent within the page's sampling window. Arrivals are read 1.5 s
  after it, so in-flight messages count.
- **Staleness.** A sample's time, less the time the server sent that tick. Both are the machine's clock, as in
  42.56, so staleness includes the up-to-50 ms gap between ticks.
- **The diagnosis.** One-off additions not kept in the tool:
  - Chrome's net log (`--log-net-log`) gave the 1008 close and the stream's spurious losses;
  - a patched `room-connection.js` counted refused deltas and ignored frames;
  - logging the page's stream writes found the pongs.
- **When to rerun.** This is a dated record, not a check: no gate or PR needs it refreshed. Rerun it only for a
  change that could move what it claims (the edge's fragmenting, the client's apply, acknowledgements or the
  history), with one run of the profiles in question. A run costs its join plus 20 s, about 2 minutes on poor.

## Limits

- **One machine, loopback,** and one map at one size. One run per profile.
- **No live whole frame was measured.** Whole frames were sent only to poor's eliminated view (176 B). A live
  player's whole frame on this map, which recovery sends, was not.
  - Its size against the 1,100-byte fragment is still 24.2's estimate (0.66–2.4 KB).
  - `tests/edge.browser.mjs` exercises that recovery but does not record sizes.
  - [42.60](42.60-whole-fast-frames.md) has since measured it on every live size: at most 920 B, one fragment.
- **One player, no fragmentation.** Larger rosters or maps, which would fragment whole frames, are not covered.
- **The relay's model.** Jitter is still independent per packet, or a queue when ordered. Real paths sit between
  the two, so the tables bracket a real path's drawn share and staleness rather than predict it.
