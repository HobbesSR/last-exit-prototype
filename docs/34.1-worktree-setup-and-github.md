# 34.1. Worktree setup, GitHub publishing and the Forgejo tool server

Up: [34](34-forgejo-workflow.md). Reference for the human or a lead setting things
up, and for the human publishing to GitHub. An agent on a normal task needs only 34.

## Setting up a worktree

Done once per agent by the human or the lead, from the primary checkout.
`extensions.worktreeConfig` must be on (it is set once for the repository). The
accounts, paths and ports are in [34's table](34-forgejo-workflow.md#who-works-where).

```sh
git worktree add --detach ../astra_test.agents/<agent> forgejo/main
git -C ../astra_test.agents/<agent> config --worktree user.name  <account>
git -C ../astra_test.agents/<agent> config --worktree user.email <commit email>
git -C ../astra_test.agents/<agent> config --worktree credential.<forgejo-url>.username <account>
printf 'PORT=<game port>\n' > ../astra_test.agents/<agent>/.env.local
(cd ../astra_test.agents/<agent> && npm ci && npm --prefix map/macro ci)
```

Store the agent's Forgejo token in the OS Git credential helper (`git credential approve`
with `protocol`, `host`, `username`, and `password`) and verify with
`npm run check:git-credentials`.

Once per clone, enable the tracked hooks with `git config core.hooksPath tools/git-hooks`.
The relative path resolves in each worktree, so a worktree on a branch older than
the hooks has none. The primary checkout pins the human's identity the same way,
with `user.name`, `user.email` and the credential username in its
`config.worktree`, and the repository's shared `.git/config` holds no `user.*`,
because every worktree without its own pin would inherit it.

### Agent identity by branch

Every agent works on `<agent>/` branches, so the branch namespace names the
agent, whichever worktree or harness runs the command. Once per machine, the
human writes one identity file per agent outside the repository, and the
repository's shared `.git/config` includes it while a branch in that namespace
is checked out:

```sh
# for each <agent> in 34's table
mkdir -p ~/.config/git/agents
printf '[user]\n\tname = <account>\n\temail = <commit email>\n[credential "<forgejo-url>"]\n\tusername = <account>\n' \
  > ~/.config/git/agents/<agent>.inc
git config --local 'includeIf.onbranch:<agent>/**.path' '~/.config/git/agents/<agent>.inc'
```

The include reads at local scope, so `config.worktree` pins (the primary
checkout's human identity, the worktrees in 34's table) and harness environment
(`GIT_CONFIG_*`) override it. During a rebase it follows the branch being
rebased. A detached HEAD or a branch outside every namespace gets no credential
username, and the `pre-push` hook refuses its push. The hook accepts a key read
from one of these include files as pinned, and refuses any other key from the
shared config, which applies to every worktree. `studio-ops` carries the same
includes for its own branch prefixes; where each identity lives is recorded with
the credentials there.

## GitHub

The `gh` remote is `github.com/HobbesSR/last-exit-prototype`, which is public
(the primary checkout has no `origin`). It makes the project reachable away from
this machine and lets work start elsewhere. The local side is managed with git
and the Forgejo tools; the GitHub side with the `gh` CLI.

- **Only the human pushes to `gh`.** An agent's worktree carries a Forgejo push
  identity only, so a push to `gh` would go out under the human's GitHub
  credentials.
- **`main` moves on Forgejo first.** In the primary checkout, `main` tracks
  `forgejo` (`branch.main.remote`), so after a merge `git pull` then
  `git push gh main` publishes it; a bare `git push` goes to Forgejo.
  Nothing is merged on GitHub, which keeps the two `main`s from diverging.
- **Branches made on GitHub are reviewed on Forgejo.** For work pushed to
  GitHub from elsewhere, list it with `gh pr list` or `git fetch gh`, bring
  it across with `git push forgejo gh/<branch>:refs/heads/<branch>`, and
  open the PR on Forgejo. Delete the GitHub branch with `gh` once it has merged.
- **No Forgejo push mirror.** A push mirror runs `git push --mirror`, which
  deletes every GitHub branch that Forgejo lacks, including branches started
  on GitHub.

## The Forgejo tool server

The Forgejo MCP server (`forgejo-mcp`) is its own git repository outside this one.
Its shaping functions and tests are in `shape.js` and `shape.test.js`, run with
`node --test`. It returns compact text, not raw API JSON:

- Writes return a compact identifier and URL (`{number, html_url}`, or `{id, ...}`
  for reviews); idempotent ones add a `_note`.
- Lists are one line per item (`limit`/`page`); lists and comments follow every API
  page before paging locally. A partial result states its total and next offset;
  nothing is silently truncated.
- Read-only text over about 6K characters is written to `.forgejo-cache/`
  (gitignored, in the server's working directory, or `FORGEJO_CACHE_DIR`), and the
  call returns a digest and the path.

To measure what Forgejo reads cost, run `npm run forgejo:usage`
(`tools/forgejo-usage.mjs`): per-tool call counts and result sizes from Claude Code
transcripts only. `-- --split <ISO date>` compares before and after a date.
