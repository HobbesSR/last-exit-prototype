# 42.46. Room threads: startup isolation (#1089)

Up: [42](42-performance-history.md). The acceptance measurement for running each room on its own thread
([22.3](22.3-server.md#room-threads)). The tool and its method are in
[31.2](31.2-benchmarks-and-timing-tools.md) (`tools/perf/room-isolation.mjs`).

## Method

Measured 2026-11-15 on the development machine, Node v24.15.0, under the benchmark lock (no run was
contended; other processes' busy share 2–3.5 %). Each size and host ran three sequential pairs. In each
pair, room A starts with one recording dev viewer over a real loopback WebSocket, and its archive goes to a
real file store. A settles for 2 s, then its state receipts are measured over a 3 s steady window. Then
room B is created with the second map (packed, as the map worker leaves it), joined and started, and A is
measured from B's creation to 1.5 s after B's first state frame. Maps were generated once before timing (seeds
4217 and 4218). CPU is process-wide, so it includes every thread and the socket client worker.
`threads` is the production host. `inline` runs every room on the host thread, which is the shape before
#1089.

## Reading

- At 36x18 the inline host reproduces the stall #1085 left: 136–189 ms gaps while B prepares and starts,
  against 65–66 ms steady (42.22 recorded 145–196 ms). On threads, two pairs stayed inside the steady range
  (64–65 ms). The third had one 90 ms gap, above that pair's 65 ms steady maximum but below the steady maxima
  seen at 12x6 (69–91 ms); one gap of that size is within the cadence jitter that a 3 s steady sample shows.
- At 12x6 neither host is disturbed: the startup windows are no worse than the steady ones.
- A thread costs startup time. A threaded room is ready about 0.4 s later at 12x6 (about 0.5 s against
  0.1 s), and about 0.2 s later at 36x18, the time to start a thread and load the modules. Process CPU in
  the startup window is higher on threads at 12x6 for the same reason. At 36x18, CPU above wall time shows
  B's preparation running beside A instead of in its turns.
- This covers what #1085 left unmeasured: live worker-map handoff and adoption (B's packed map decoded only
  in B's thread), and real-socket delivery during startup.
- Not measured: more than two rooms, sizes above 36x18, other hardware, or a map generated during the window
  rather than before it (generation already has its own worker, #253).

## Re-run after #1087 and #1088 (#1119)

2026-11-15, main `ced6be0`, 36x18 threads, same method, three pairs, no contention. Room A's steady maxima were
65–67 ms with no gap over 75 ms. Its startup maxima were 69.5, 71.5 and 78.0 ms, with one gap over 75 ms, in
the third pair. That is the same picture as above. B was ready in 1446–1466 ms, about 0.2–0.25 s later than
above; #1088's earlier recording header accounts for about 140 ms of that. Neither recorder dropped a frame.
Figures are in [the #1119 report](reports/issue-1119/README.md#isolation-re-run-36x18-unprofiled).
