# 33.1.1 Running a Foundation Pass

Up: [33.1](33.1-foundation-pass.md)

Operational playbook for running a Foundation Pass in this repository against
Forgejo ([34](34-forgejo-workflow.md)) and the delegation rules
([32](32-delegation.md)), distilled from the first pass (`#914`). The
project-agnostic charter remains [33.1](33.1-foundation-pass.md).

## Single ledger and queue state

A pass runs from one Forgejo tracking issue (the ledger), opened with a baseline
checkpoint (`main` SHA, doc/code/test/runtime baseline metrics) and holding the
**Swept so far**, **Recorded defects**, and **Declined findings** tables.

- **Body edits belong to the steward alone.** Work sessions post a short ledger
  comment at the end of their turn; only the steward folds those into the ledger
  body so parallel sessions cannot overwrite each other.
- **Forgejo state is the queue:**

  | Issue / PR state | Meaning |
  | --- | --- |
  | Open pass issue, unassigned, no `Waits on` | Ready for a fresh work session |
  | Open pass issue with `Waits on` | Blocked on listed prerequisite(s) or phase gate |
  | Assigned to an agent | In progress or paused at a handoff comment |
  | Assigned to `corey` | Waiting on human decisions in its latest findings comment (if MCP cannot unassign `corey`, the steward records a claim-override note when decisions are answered) |
  | Open pull request | Waiting on cross-model diff review ([34](34-forgejo-workflow.md)), then human merge |

- **Issue naming:** In-pass work issues use the prefix `"Foundation Pass: ..."`.
  Defects recorded for outside-pass triage, deferred items, and post-pass work
  omit the prefix.

## Phase sequence

1. **Phase 0 — Backstops, inventory, and stocktake (before parallel sweeps):**
   - Verify or land required verification backstops first: link checker
     (`tools/check-doc-links.mjs`), machine lock and CPU timing
     ([31.2](31.2-benchmarks-and-timing-tools.md)), and an initial exclusive-lock
     `npm run test:times` baseline on Day 1 so later phases compare apples to
     apples.
   - Run a read-only mechanical inventory across the repository (file/line counts,
     unreferenced exports, commented/disabled code, test runtimes).
   - Run the **experimental and legacy path stocktake** next and land its
     retirements before Phase 1 opens, so surface sweeps do not spend time
     polishing dead paths.
2. **Phase 1 — Pilot sweep, then parallel surface sweeps:**
   - **Slice by surface, not by track:** each sweep owns a disjoint directory or
     doc range plus its owned [test sets](31-verification.md#test-sets).
   - Run **one pilot sweep** first (such as server/client and their fast tests)
     and fold any ambiguity into the ledger rules before fanning out the rest.
   - Guard against **queue starvation and stale briefs**: if early subsystem
     reworks fill agent slots while other surfaces have not started, prioritize
     opening/running unstarted sweeps or post steward staleness notes whenever
     multiple reworks land across shared files. Batch documentation sweeps
     alongside early code reworks cleanly, and run doc archive/owner cleanups in
     step.
3. **Phase 2 — Cross-surface assessments:**
   - Test suite structure and cost against [31](31-verification.md) and
     [31.1](31.1-test-catalogue.md).
   - Whole-system architecture against foreseeable work in
     [13](13-accepted-features.md), [16](16-deferred.md),
     [17](17-open-questions.md), and [41](41-roadmap.md).
   - Optimization register (`#900`-style investigations weighed by benefit, cost,
     optionality, and reversible evidence).
4. **Phase 3 — Entry points and closing fixture/doc batch:**
   - Refresh `README.md` and audience guides ([33.2](33.2-readme-design.md))
     last, once code and doc paths stop moving.
   - Bundle any approved behavior-changing or recorded-schema retirement candidates
     into **one combined recapture PR** rather than recapturing frozen fixtures
     ([31](31-verification.md)) multiple times. Decide at kickoff whether that
     recapture batch lands inside the pass window before closure or is deferred.

## Human throughput, concurrency, and model routing

Human decisions are the pass's throughput limit:

- Keep concurrency to **two or three active work sessions** at once. Run
  timing and benchmark workloads **alone** under the exclusive `bench` lock
  ([31.2](31.2-benchmarks-and-timing-tools.md)).
- Clear what waits on the human first (decision-blocked issues, then approved
  PRs), every few merges run a **steward** pass to reconcile the ledger and name
  ready work.
- Match model tiers to risk under [32](32-delegation.md):

| Work | Model tier |
| --- | --- |
| Steward, stocktake, code sweeps, architecture, optimization register, product/capture docs, approved reworks | Flagship lead |
| Inventory, link checks, engineering docs checked against code, README writing from fixed design | Mid tier |
| Bounded explicit removals, archive moves, link retargeting from a complete edit list | Cheap |
| Live Lab verification and README visual captures | Browser/vision-capable model |

### Standard kickoff prompts

- **Work issue:** `Foundation Pass: read AGENTS.md, then ledger #<ledger> and issue #N on Forgejo. Claim #N and deliver exactly what it asks, under the ledger's rules. Stop at its stopping rule.`
- **Cross-model review** (use a different model family from the PR author, diff-only per [34](34-forgejo-workflow.md)): `Review PR #N on Forgejo against its issue and ledger #<ledger> / docs/33.1.1-running-a-pass.md. Post the review there.`
- **Steward (flagship):** `Foundation Pass steward: read ledger #<ledger> and every open issue and pull request titled "Foundation Pass". Bring the ledger's tables up to date, file the next planned issues whose prerequisites are met, and tell me what is ready to start with a model for each, what is waiting on me, and anything stalled.`

## Sweep scope, hygiene, and stopping rules

A sweep is **one reading of its surface, one findings comment, and one pull
request**.

- **Upfront reader split:** For surfaces larger than ~5,000 lines, name the
  lead vs. mid-tier reader split in the issue upfront. Leads inspect core
  contracts and spot-check reader claims; explicitly list `Read` vs `Not read` in
  the ledger row rather than re-reading the surface.
- **No regex-only deletions:** Never delete an export, import, CSS selector, or
  branch flagged as "unused" by grep alone. Verify dynamically referenced names
  (string-keyed registries, spread props, CLI/tool names) with `tsc` / execution
  before removing.
- **Mechanical vs. judgment boundary:**
  - *Allowed in a sweep PR:* truly unreferenced dead code, comment distillation
    (`33.1`), broken local links, tests whose assertions mismatch their claim, and
    obvious redundant waste.
  - *Requires a decision + separate lead PR:* merging abstractions, **extracting
    new shared helpers or exports (including file-local deduplication across
    distinct concepts)**, splitting or renaming modules, changing failure modes,
    or removing tests on cost grounds.
- **Decision cap (`≤5`):** Surface at most five ranked decisions per sweep (each:
  evidence, alternatives, recommendation). Record lower-priority items in one
  line as `not pursued` with their reason.
- **Issue and PR hygiene (no orphan notes):**
  - Sweep PRs use **`Refs #N`**, never `Fixes #N`, while decisions remain open on
    `#N`.
  - Every handed-on item, recorded defect, or deferred choice is posted directly on
    an open target issue before the session ends (never leave action items only in
    ledger comments that disappear at closure).
  - Pre-existing unrelated failures (outside visual/rendering reworks) go into an
    outside-pass defect issue; a behavior-preserving sweep touching those checks
    may document that the check fails identically on base.

## Closing a pass

1. Confirm all tracks and surfaces are swept and every finding is fixed,
   declined with reason, or filed on an open issue.
2. Run a clean exclusive-lock `npm run test:times` pass and update
   [31.1](31.1-test-catalogue.md) set totals and row timings if stale.
3. Land any scheduled Phase 3 entry-point or closing recapture PRs.
4. Measure closing code, doc, instruction, and runtime metrics against the
   ledger baseline; archive a retrospective under `docs/archive/<YYYY-MM-DD>-<topic>/`
   ([33](33-maintenance.md)) if warranted, update [41](41-roadmap.md), and post
   the closing summary on the ledger for the human to declare the pass closed.
