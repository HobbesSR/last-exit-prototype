# 22.8. Development tools: one core, three faces

Up: [22](22-ownership.md). Plan and issue order: [41.3](41.3-tools-plan.md).
Tracker: #772.

Status, 2026-11-01: design. The contract below is direction for new and changed
tools; the inventory records what exists today. Map generation already follows
most of it ([53.1](53.1-map-lab-and-tools.md)); the other domains do not yet.

## Why

Agents and people work on the same things by different means. Some work is exact
and wants text: values, validation, batches, sweeps, diffs. Some is judgement and
wants a picture or a GUI: does it look right, does it walk right. Most real work
mixes the two: an agent sets up a case by text, hands Corey a link, Corey tunes it
in a lab and hands back JSON, the agent commits it. A tool serves all three only if
its logic lives in one place and its state can move between faces.

## The contract

Each tool domain (map chain, chain library, placeables, micro regions,
decomposition, physics, appearance) meets these rules.

1. **One core, thin faces.** Pure modules that run in Node and the browser own the
   operations. The lab (GUI), the CLI and the MCP tools call the core and agree on
   inputs, validation and output; no face implements logic another lacks. This
   generalizes 53.1's GUI/CLI/MCP parity rule beyond the map.
2. **State is a document.** A lab's state is a versioned JSON object,
   `{ tool, version, ... }`, holding the inputs that reproduce what it shows, not
   derived output. It round-trips through export/import in the lab, a CLI
   `--state=FILE` and an MCP argument. Unknown fields are kept and ignored; an
   unsupported version is refused with a reason. A state document is a tool
   artifact, never a saved map or replay; it changes no compatibility domain
   ([53](53-map-artifacts-and-tools.md), [26](26-recording-contract.md)).
3. **Links carry state.** `#state=` holds the document deflated and
   base64url-encoded, generalizing `map/micro/brief-link.ts`; `#brief=` stays an
   alias. A fragment never reaches a server and survives any origin or worktree
   port. Every lab offers Copy link and Copy state; CLI and MCP results include the
   link that opens the same view.
4. **An in-page handle.** Each lab exposes `globalThis.devLab`:
   `{ tool, version, ready, getState(), setState(state), describe(), capture?() }`.
   `ready` resolves when the current state has rendered; `describe()` returns a
   structured summary of what is shown; `capture()` returns the preview as a PNG.
   Browser and computer-use agents and the lab browser tests use it instead of
   scraping the DOM. It mirrors the core and the UI, never adding an operation the
   GUI lacks. DOM ids remain for people and visual agents.
5. **Pictures for text agents.** Where a domain's output is visual, CLI and MCP can
   return an image of a state, drawn as the lab draws it: SVG from the shared part
   drawing for maps, regions and tiles; PNG from the real renderer in headless
   Chrome for appearance. MCP returns image content inline, so an image-capable
   agent can look without driving a GUI.
6. **Writes go through files.** No tool writes repository source from the browser.
   A lab exports state or a patch summary; an agent or person commits it. CLIs write
   only to an explicit `--out` or `test-results/`. Dev tools add no HTTP endpoints:
   the server's part is serving the pages and modules (53.1 "Serving"), and its
   `/api` stays for rooms, replays and profiling.
7. **One MCP server.** `tools/mcp.mts` registers each domain's tool set from that
   domain's own module. Names are domain-prefixed (`map_*`, `library_*`,
   `region_*`, `placeable_*`, `art_*`); existing names keep working. Outputs are
   bounded, with large results written to an explicit path. It is registered in
   `.agents/mcp_config.json`.

Verification for tools: core unit tests in the fast tier; a parity test per domain
showing CLI, MCP and core agree for the same state; lab browser tests through the
handle, run when a lab changes ([31](31-verification.md)).

### Choosing a face

- **Text** for anything with an exact answer: generating, validating, measuring,
  sweeping, comparing a candidate value, and editing authored data files.
- **A picture** (CLI/MCP image) when the question is how something looks and no
  interaction is needed.
- **The GUI** (a person, or browser/computer use) when judgement needs
  interaction: walking, dragging a light, comparing views side by side.
- **Mixed**: set up by text, open the link, adjust in the lab, copy the state back,
  verify by text, commit.

### Editing

Authored data is edited as text in its files: library modules, region examples,
kit constants. Adding MCP verbs that paint cells or add slots would duplicate file
editing. What text editors lack is feedback and a way to hand an entry to a person:
a preview of what the tab derives (portals, prescription checks, issues, a cell
grid and a picture), and a link that opens the entry in its tab (#777). The Chain
Library tab's derivations move into a core module so the tab and the tools share
them.

## Appearance tools

### What exists

- `public/palette.js` owns swatches, themes and colour arithmetic (`mix`,
  `luminance`, `contrast`); `public/appearance.js` owns the static material,
  wear and spatial lighting resolver ([29.4](29.4-drawing.md)). Both are pure and
  already import in Node: `tests/appearance.test.js` runs the 72-combination theme ×
  field × substrate matrix there. Contrast arithmetic does not need a browser; it
  lacks a face.
- 29.4's readability tiers have no code owner: their thresholds are literals in
  the tests and the witness.
- The game exposes the palette (`?palette=`, the dev view menu). The resolver also
  takes `lighting` and `wear`, but nothing outside the witness sets them.
- `tests/art-witness.browser.mjs` builds its own scene and captures through the
  real renderer. Rendered checks stay necessary: alpha, line width, tile
  resolution, LOD and motion are not visible to colour arithmetic (29.4,
  [41.2](41.2-art-direction-plan.md)).

### Design

- **A1. Readability owner** (#778). `public/readability.js` holds the tier table
  (role → tier, thresholds) and `assessContrast`, and `appearanceMatrix` runs the
  sweep. 29.4 states the rule; this module is its only code statement, and tests,
  witness, lab and tools import it. Its numbers are sampled-colour screening, not
  rendered or perceptual certification.
- **A2. Art state and overrides** (#779). The art state document is
  `{ tool: 'art', version, scene, theme, lighting, wear, fog, view, roofs, overrides }`.
  `overrides` layers swatches, per-theme role colours (hex or `mix()` over swatch
  names) and lighting fields over the frozen themes, through the resolver and the
  existing restyle path, without editing `palette.js`. It stays presentation-only:
  never on the wire, in recordings or in saved maps. `exportOverrides` names the
  source constants to change.
- **A3. CLI and MCP** (#780). `tools/art.mjs` and `art_themes`, `art_contrast`,
  `art_matrix` (with an override to test a candidate before editing source) and
  `art_resolve` (descriptor or kit + tier + seed → resolved fills, edges, marks).
- **A4. Scenes and capture** (#781). The witness's scenes become presets of one
  scene builder (the #697 test-arena direction), servable to a lab. `art_capture`
  renders an art state through `arena-scene.js` in headless Chrome at the requested
  zoom tiers and returns PNGs, probe values and 41.2's provenance fields.
- **A5. Appearance Lab, view and compare** (#782). `/dev/art` renders a preset with
  the real renderer (no second renderer): theme, lighting, wear, fog, roofs and
  zoom presets; pinned probes with rendered value, predicted value and tier
  verdict; a kit × decay-tier strip; grayscale; state link and handle.
- **A6. Appearance Lab, tuning** (#783). Role and swatch editing with live restyle
  and a live failures-first matrix; lighting field staging by dragging; export of
  state and patch summary.
- **A7. Game dev view toggles** (#784). `?lighting=0`, `?wear=0` and dev-view
  toggles, restyling in place.

### Not adopted from the 2026-11-01 proposal

- **An HTTP dev API** (`/api/dev/appearance/...`): it would be a fourth face with
  the server involved, for operations the core, the handle and MCP already cover
  (rule 6).
- **An automated landmark silhouette validator**: silhouette survival is part of
  41.2's promotion gate, which requires visual sign-off. Appearance-only geometry
  invariance is already tested. Captures and the lab support the review rather
  than replace it.

### Assumptions to confirm

Recorded so implementation can start; each is cheap to reverse.

- One MCP server rather than one per domain (rule 7).
- Labs export state and patches; nothing writes source from the browser (rule 6).
- The Appearance Lab judges the real renderer; Node arithmetic only screens.
