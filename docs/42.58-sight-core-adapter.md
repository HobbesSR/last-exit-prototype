# 42.58. The core's first per-tick module: sight through the flat-buffer adapter (#1175)

Up: [42](42-performance-history.md). Design: [27](27-rust-path.md#the-core-and-its-adapter), rule 3. The port is
`rust/core/src/sight.rs` with its adapter `shared/sight-core.ts`. It was measured while `tests/sight-core.test.js`
held it equal to `shared/sight.ts` bit for bit. The TypeScript cast has since retired, and the test pins the core's
polygons by digest (#1175, 27); `tests/bench-sight.mjs` no longer has the `ts` variant.

## Finding

**Crossing is cheap; building JavaScript objects is the cost to watch.** On the room arena's map, one
`visibilityPolygon` at the default radius (620) returns 988 points on average:

| Variant | Wall per call | Share of the TypeScript |
| --- | ---: | ---: |
| `ts`: `shared/sight.ts` | 419–431 µs | 1 |
| `core`: the core, returning the same point objects | 157–160 µs | 0.36–0.40 |
| `flat`: the core, points left in WASM memory | 135–136 µs | about 0.32 |
| `empty`: one call to `adapter_version` | 0.03 µs | — |

- **The crossing itself** costs about 0.03 µs, nothing beside the work.
  - That includes writing the 90-gate open mask and making the output view: `flat` minus Rust's own compute
    is too small to separate here.
- **Materializing the result** costs about 22 µs per polygon (`core` minus `flat`). That is about 22 ns per
  four-field point object, about 14% of the core call and 5% of the TypeScript's time.
- **Uploading the index** is a one-off per map, of 15–20 ms on this map: deriving the flat tables in
  JavaScript, copying them in and building the first polygon. Every later call reuses it.
- **The ratio held in every round** of three runs (0.36 to 0.40). None was contended: other load on the machine
  was 11–13% against the lock's 25% threshold.

**In a tick (24x12, seed 4217, 1,500 ticks, uncontended):**
- The mean tick was 2.81 ms. `sim.step` was 1.69 ms of it, and `sim.discovery` 0.85 ms.
- Discovery built 0.58 polygons per tick on average (p50 1, max 1).
- This is an estimate, not a measurement: sight was not swapped into the tick. At this map's per-call ratio,
  sight would cost about a third of what it does in discovery now. Its crossing overhead would be under 25 µs
  per tick, about 0.05% of the 50 ms tick at 20 Hz.

## The budget

For a per-tick module ported through this adapter (27, rule 3):
- **Crossing overhead must stay at or below 10% of the module's TypeScript cost per tick.** Crossing overhead
  is the calls, the per-tick input writes, and materializing results into JavaScript objects. Sight is at
  about 5%.
- **A result read many times stays in JavaScript.** `litPoint` is queried tens of times per polygon, so it stays
  in TypeScript over the materialized points, rather than crossing once per query.
- **Over budget, return a flat view, not objects,** and let the caller read it. If callers cannot, that is the
  evidence 27 names for flipping state ownership earlier (#1066).

## Method

- **Environment.** The development machine (Windows 11), Node 24, and the core built with `cargo build --release`
  for `wasm32-unknown-unknown` (`tools/build-core.mjs`). 2026-11-18.
- **The script.** `node tests/bench-sight.mjs`: 2,000 eye positions on the room arena's playable ground, from a
  fixed sequence, and 7 rounds.
  - Each round times every variant over the same positions, rotating which goes first.
  - Every path is warmed before timing.
  - The script holds the exclusive bench lock and reports process CPU beside wall time. CPU is too coarse at
    this granularity to add anything, at Windows' 15.6 ms tick over 2,000 calls.
- **Three runs**, sequential. Each reported the per-variant median of its rounds.
- **The tick numbers** come from `node tests/bench.mjs --size=24x12 --ticks=1500 --json` under the same lock,
  from the profiler's `sim.discovery` and `calls.visibilityPolygon`.

## Limits

- **One map for the per-call numbers.** The room arena is 12x6. Larger maps have more edges per polygon, which
  shifts work toward the compute and makes the ratio, if anything, better.
- **Node only.** Chrome's WASM tier and its object costs are measured when the client loads the core.
- **No in-tick swap.** The tick estimate scales discovery's time by the per-call ratio. It assumes the polygon is
  most of discovery's time, as #1175 comment 16306's profile found.
