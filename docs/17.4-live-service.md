## Live-service policy

No answer is required for the current implementation. Existing prototype behavior
remains the default until these policies are decided. These supplement, rather than
replace, the map hierarchy, multi-floor, balance and presentation questions in [17.3](17.3-product-gameplay.md).

1. First release: private invited playtests, public anonymous play, or accounts?
   What concurrent players/matches and geographic footprint should we plan for?
   Let's say worldwide for now. Imagine we deploy this on a VPS and other turn key services for deploying something like this as a live service.
2. Deployment behavior: finish matches on the old server version, reconnect to a
   replacement, or tolerate interrupted matches? Is crash recovery required?
   So I guess you know there is the lobby server and then there are the spawned game server. So I guess when you come back to join a new game yoru client will have to update.
3. Replay policy: who may download full-state recordings, how long are they kept,
   and how long must old recordings remain playable?
      - Replays can only be downloaded by the room owner. They last as long as the owner has not exited the game. Ideally replays will be stored in BSON and recorded in JSON only for debugging.
4. Content rollout: should a match always retain its starting balance/content,
   and are simultaneous balance variants/experiments needed?
5. Persistent progression/rewards: which outcomes survive a match, and what must
   happen when storage fails or the same result is delivered twice?
6. Observer fairness: public spectators/presenters, delay policy, and whether the
   same person may participate and observe through separate sessions?
      - We should plan to be able to restrict who is allowed to spectate, but not implement it. We should plan to be able to delay spectation,
      but not automatically do it. During the initial bring up of the game, we will not worry about whether there are bad actors, we simply tolerate
      them during rapid development. But we try not to box ourselves in.
7. Failure policy: if recording cannot keep up or fails, pause the match, continue
   without a replay, or end it? Current disk backpressure pauses advancement.
   *(Status when asked. Since the answer below, backpressure never pauses
   advancement; frames that do not fit are omitted ([14](14-match-rules.md), [26](26-recording-contract.md)).)*
      - Recording replay should not impact gameplay. If replay fails for some reason it should
      fail gracefully for all clients and systems. If replay can be recovered, playback should
      handle missing data gracefully.
8. Dev tools (#231): who may open the dev view, which shows a live match unfogged and undelayed?
      - I guess I just want anyone to be able to use it when we're doing npm run dev. We would eventually have like an npm run prod right? Otherwise I guess I'd have a flag that picks none, owner, or all or something like that.
   - Following a player shows their fog, with a toggle; pause stops only that room (answered 2026-10-05).
9. Named lobbies and the lobby browser (#237, design in [22.5](22.5-lobbies-and-matchmaking.md)). Corey: "Perhaps we should have a way of making named lobbys and a viewer to interact with them and select them, along with auto. Maybe they're dev lobbies."
   - Who sees a named room in the list: everyone on the server, or only people with dev tools? (Proposed: everyone; an unnamed private room stays link-only.)
   - Are names free text (length-limited), and must they be unique among open rooms? (Proposed: up to 24 characters, unique while the room is open.)
   - Should live matches stay listed so they can be watched, and by whom: anyone through the delayed spectator stream, or only through the dev view? (Proposed: dev view only for now, matching 6.)
   - Is eight rooms per process still the cap once rooms can be browsed? (Proposed: yes, until hosting is planned.)
   - Accept all proposed answers.
   - *(Since #1089 each room has its own thread, so the cap limits rooms per host process, not rooms sharing one event loop. The number itself is #907's.)*
10. Map pool (#266, from Corey's answer to 17.3 #15: "the server should have a pool of generated maps it maintains so it can serve them immediately"). Recorded assumptions, implemented; only the pool size is a product choice, and it is a setting:
   - Two maps per size, for every size a room can use (`MAP_POOL`, default 2; 0 turns it off). Held in memory: about 6 MB of map JSON in all (42).
   - A room that names no seed, private or matchmade, takes a pooled map of its size; one that names a seed generates that map on demand, as does any room when the pool has none of its size ready. The deploy dialog's seed is blank ("Random") unless typed or given by `?seed=`, and its shuffle button clears it.
   - The pool is not saved: a restart starts it empty, and since new generator or content code arrives only by a restart, a pooled map is never from another version. Saving it would need a version check (`REGION_TYPES_VERSION` and the like) before use.
   - Refilling runs on its own worker, one map at a time, so it never delays a seeded room's generation and takes at most one core beside the ticks. On a single-core host it still competes with them; lower `MAP_POOL` there.
   - Recording is unchanged: its frames start at the match start, from the map the room used (the header is written once the match is prepared, #1088).

14. Netcode direction (2026-11-14, in the #901 session). Asked what comparable games do with wire formats and netcode.
   - "We want to move in the direction of industry best practices, including considerations that will aid us with anti-cheat and other security considerations."
   - "So yes encoding and quatization seem like important changes we'll want even in alpha. Deltas as well. And Transport to UDP (or even some newer UDP like technolgoy that has some reliability features, I forget the name)."
   - "I'm imagining a server with some sophistication that doesn't fully seal game state until some latency has passed that covers the maximum amount of time we're willing tow ait for a client's purported input to still be valid at the time it's received, which then requires walk back and resimulation as events are potentially re-ordered."
   - "WebTransport or ENet LiteNetLib look like the right technology for our game, however I'm not sure which to choose. I'm leaning towards WebTransport because it seems like it is more widely supported and probably easier to integrate."
   - The accepted direction is application-owned projection and replication, with the bounded comparison and rollout recorded under question 17 below. This does not choose a concrete backend or change the current JSON runtime.

16. Spectator tiers and viewer publication (2026-11-15, follow-up to #1092 and #1121; #1123). Asked to adopt three recommendations separating authoritative simulation, live-wire netcode, and downstream viewer publication:
   - **Input timing (#1096):** keep tick-stamped inputs with hit rewind kept (`#1096` Option 3, or Option 1 with existing hit rewind) as the candidate recommendation, and complete #1096's bounded comparison before deciding.
   - **Input timing decided (2026-11-16, #1096, on [42.48](42.48-input-timing.md)).** Corey, in #1096 comment 15346, verbatim: "I'm leaning towards 1 or 3. Should probably try both and see." Then, in a session the same day, verbatim: "I answered on the tick option 1 or 3. Kind of a do 1 with 3 in mind and push through if it's easy. Is that sufficient an answer. Everything else I guess I just accept recommendations." Confirmed with him in that session (#1096 comment 15527):
     - Build option 1 with option 3 in mind: tick-stamped inputs, a server jitter buffer, client send-rate dilation toward a target margin, late inputs discarded and never rewound, one input per tick and sequence order kept. Hit rewind stays as it is. A stamp's lead is bounded by the server's measured round trip, not a constant (42.48 recommendation 4).
     - No delayed sealing (option 2) for now; revisit only if discarded inputs prove noticeable in play.
     - Target margin 1 tick by default, as a configurable tuning value that tests do not fix.
     - No interim queue-trim fix, since option 3 went ahead.
     - Implemented by #1096 ([24](24-networking-privacy.md#tick-stamped-input), [26](26-recording-contract.md#schema-19-tick-stamped-input-1096)). The lead bound of three round trips is an agent choice measured in 42.48, not Corey's.
   - **Spectator tiers:** adopt the two-tier split as proposed architecture ([28.1](28.1-deployment-topology.md), [24](24-networking-privacy.md#two-tier-spectators)), with explicit authorization for high-trust live viewers (casters/admins, separate from `DEV_TOOLS`) and configurable server-enforced delay plus explicit access policy (consistent with Q6) for low-trust delayed spectators.
   - **Codec:** prefer shared projection rules (`shared/simulation/projection-contract.ts`) and reusable delta primitives (`shared/keyed-list.ts`), with separate live-wire (#1093/#1094) and `delta-1` recording (#901) contracts; retain `delta-1` provisionally and benchmark before replacing it.

17. Wire encoding and replication (#1093; accepted 2026-11-15). Following the cross-agent synthesis in #1093 comment 15211, Corey replied in comment 15214 at 2026-11-15T23:09:52-06:00, verbatim: "I accept the direction and recommendations." [24.1](24.1-wire-encoding-design.md) owns the accepted direction.
   - Adopt application-owned projection and replication. Compare bounded descriptor/static `DataView` encoding with a maintained stateless library, using both Node and Chrome, and include JSON and limited-deflate controls.
   - The first rollout is outbound-only; inputs remain JSON. Every prediction-consumed field is exact, including own/proxy/gate/motor/shapes state.
   - Decide final quantization precision and activation jointly with #1094's pre-delta representation, and qualify the precision against [29.2](29.2-physics-state-networking.md).
   - This accepts direction only. It does not select a concrete backend, accept a TypeScript-AST compiler or full-metadata approach, decide final precision, or authorize a live switch. The current runtime remains JSON; implementation has not begun.
   - Backend (2026-11-16, #1130). On the D-versus-msgpackr recommendation, Corey replied in comment 15345, verbatim: "My current thinking is D combined with protobuf is a potentially strong solution, and I'd pursue those until they are clearly shown to not be viable, either piece or together, leaving them separable, or whether there net performance drops below what we expect the end result would be with one of the other alternatives." Asked in a session the same day what protobuf contributes, Corey chose to measure stock protobuf head-to-head against D first and to decide on combining them afterwards (recorded on #1130, comment 15382). The result is [42.51](42.51-protobuf-head-to-head.md). Reviewing it the same day, Corey said, verbatim: "Well I think the point was we were moving away from JSON shaped data. Yea if you run JSON through protobuf, what's the point. Right?" and "Now the idea is protobuf would be tightly integrated." So protobuf is judged on natively shaped data, with projections building protobuf messages directly, not through an adapter. He then added, verbatim: "It sounds like for us to truly assess the wire model, we have to visit the engine's data model." Per-field wire types are to come from the engine's data model rather than from the generic `num` of the measured slice. No backend is selected yet.

Reviewing 24.3's recommendations and borderline calls, Corey said, verbatim: "Alright, none of that looks like stuff I just won't go with what is recommended I'd think", then on the borderline items: "efficient relations both in lookup, storage, and transfer is probably something we want regardless of down chain things that care about them, but also, especially because down chain things care about them, we should resolve sooner than later our general relational strategy for out data (including when we use implicit indices)", "Also seems like we should do the harder thing up front" (Proposal 9 static geometry), "no events should have identifiers and lookup utilities with localization features (with only english supported initially, and defaulted / assumed)", and on quantization: "if we can add quantization in later without causing chaos, then I'm fine to defer that."
