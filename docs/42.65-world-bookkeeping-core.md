# 42.65. The physics world's bookkeeping in the Rust core (#1232)

Up: [42](42-performance-history.md). Design: [27](27-rust-path.md#the-state-flip), step 5b.1. The bookkeeping is
`rust/core/src/world.rs`, driven by `shared/physics/world.ts`. `characterization-physics`, its `-bots` variant and
`tests/tick-phases.test.js` passed unchanged.

## Finding

**The tick got slightly cheaper, and building a match got about 20% cheaper, so 42.58's budget is met with no added
crossing cost.** The state-flip exception is not needed.

| 24x12, seed 4217, ticks 301–900, median of 5 rounds per run | Before | After |
| --- | ---: | ---: |
| Phase 4's solve (`sim.solve`: floor drag and the step) | 184.6–194.5 µs | 178.4–182.6 µs |
| Body sync (`sim.sync`, three calls a tick) | 63.8–75.9 µs | 62.8–73.4 µs |
| Item sync (`sim.itemSync`, inside `sim.sync`) | 34.8–43.1 µs | 33.4–36.6 µs |
| Whole tick (`match.advance`, with the snapshot), mean | 4.49–4.68 ms | 4.51–4.57 ms |
| `createMatch`, median of 7 | 212–216 ms | 169–173 ms |

The before and after runs were interleaved. Each phase was 3–8 µs lower in every pair.

- **The step packs nothing.** It used to write 7 values per dynamic body, plus the pushes and constraints, into the
  input on every tick. The core already holds all of that, so the call takes only the contact flag.
- **Commits got cheaper.** Building a match commits about 14,400 map colliders in batches of 512. Each batch was
  sorted and admitted in JavaScript, and its native calls crossed one body at a time. Now each batch is one call,
  sorted in the core. Interning each ID once costs less than the per-body calls it replaced.
- **What now crosses per query.** `getGeneration`, `getTransform` and `hasConstraint` are each one call, as
  `getTransform` already was. `hasBody` and `bodyLifetime` read JavaScript's records and cross nothing. The body sync
  shows no added cost.
- **Snapshots read one call.** `snapshot({ includeStatic: false })` returns every dynamic body's generation and
  pose in one call, where it used to make one `getTransform` call per body.

## Method

- **Environment.** The development machine (Windows 11), Node 24.15, the core built with `npm run core:build`.
  2026-11-20, under the exclusive bench lock.
- **The scripts** were ad hoc, not committed. Each ran against a checkout: this branch, or a worktree of `main` at
  c7c7455e with that commit's core.
  - **The tick script:** one match (`createMatch`) on a 24x12 live map, seed 4217, the shipped content. It steps 300
    ticks, then times 600 more with the profiler on, taking `sim.*` from the profiler's per-tick means. Five rounds a
    run, each on a fresh match; the run reports the median of its rounds.
  - **The construction script:** `createMatch` timed 7 times on clones of the same map; it reports the median.
- **The runs:** three of each version in sequence, then two interleaved pairs. The ranges in the table span all of
  them.

## Limits

- **Node only.** The browser's prediction makes a fresh world per correction, so it gains construction cost the same
  way, but that was not timed.
- **The world held 80 dynamic bodies,** as in 42.64. Per-tick costs follow the dynamic bodies, never the map's
  colliders, as the per-tick rule requires.
- **The phases are timed whole.** They include gameplay work that did not change, such as the ground-list walks in
  the item sync, so the bookkeeping's own share is smaller than these totals.
