# 42.38. Generation cost after the matched adoption

Back to [42](42-performance-history.md). Issue #868, following [42.37](42.37-matched-adoption.md)'s
cost finding: on the matched libraries a 36 × 18 map took 112 s to generate, against 50.4 s before,
and building took nearly all of the increase. This attributes the time per builder and records four
exact savings. Content is unchanged: no version bump.

## Method

One `node --cpu-prof` run (500 µs sampling) of whole-map `generate` on `size-36-1` with #688's
parameters at `9464a67` (`types-64`), under the `bench` lock: `generate` took 117.5 s, and the
profile's samples total 119.2 s, as they include loading the modules. Each sample is
charged to the nearest `build*` frame on its stack, to a phase within it (park's hedge fronts,
edge walls through `perimeterWallsIfAsked` or `withPerimeterWalls`) and to the innermost cord-work
function it ran in, each sample once. The summarising scripts are throwaway; the categories are 42.32's.

The machine was shared with another agent's changing test load, so timings compare the two versions
in alternated pairs, each pair's ratio being the measure (31). **Every figure here was taken under
that load.** The pair ratios and the profile's shares are the measure; absolute seconds are only
indicative. No quiet recapture was made: no decision depends on more precision, and each content
option is measured against `main` when it is built.

## Where the time goes

By builder, profiled seconds of the 119.2 sampled:

| Builder | Total | Largest part |
| --- | ---: | --- |
| Park | 41.5 | hedge fronts 30.4, edge walls 7.1, the rest 4.0 |
| Rubble | 28.7 | `stage().flush()`'s `commitEach` 20.6; meshes 14.8 of the whole |
| Compound | 11.8 | as in 42.32: handoff partition, `structuredClone`, region checks |
| Cover | 7.6 | edge walls 4.6 (a second live cord, the pieces recommitted, then the walls) |
| Placement and briefs (macro) | 8.0 | |
| Checkpoint, depot, ruins, market, block, plant, hall, others | 11.9 | |
| Not under a builder (GC, module loading, the rest of `generate`) | 9.6 | |

**Park's hedge fronts** are the largest single cost. Each front bisects its depth against one revision,
up to 32 probes (`growFront`, 20.10). A probe the live witness doesn't clear is rediscovered from it:
paths the front leaves clear are kept, and a mesh is built only when a stand's old path and a straight
sweep both fail. Under `probeClaim`, discovery takes 21.6 s, of which 7.1 s is mesh builds.

**Rubble** sites its debris on a draft and proves the cord once for as much as stands together
(#787). When the whole batch is refused, `commitEach` bisects, and each half is another discovery
from the live witness, with a mesh wherever the half breaks a path: 14.8 s of meshes in rubble alone.

**Edge walls** (`perimeterWalls: true`, #838) cost about 12 s across park, cover and ruins. Almost all of
it is `commitEach` after the whole set of a region's walls is refused. Cover's walls also build a second
coordinator and recommit every piece before offering them (`withPerimeterWalls`, review 669).

Across builders, free-space meshes take 31.4 s, all from `discoverCordWitness`.

## Exact savings

- **Edge normalisation.** A witness repeats each shared path prefix once per portal stand, so most of
  its segments recur, some reversed. `geometricEdges` now reads each distinct segment once. A segment's
  edges depend only on its ends and on the set of endpoints, both unchanged, so the edges are the same.
  It took 9.7 s.
- **Region mask lookups.** `createRegionMask`'s `has` built a string per lookup, and every sweep reads it
  for each cell its capsule's box touches (4.8 s). Whole-number cells are now keyed by their index in
  the mask's bounds. Cells that aren't whole numbers keep string keys, so every answer is the same.
- **Checked cells and access mask per discovery.** `discoverCordWitness` checked the region's cells and
  built its access mask on every call (about 3 s; 42.32 left it, as callers could change a brief). It
  now takes an optional `CordRegionCache` for a brief its caller never changes. The coordinator keeps
  one for its private routing brief and replaces it when a handoff replaces the brief. The check still
  runs on the first call, at the same point in the validation order.
- **Proposal witnesses.** Each `probeClaim` proposal carried a deep copy of the found witness (2.3 s),
  and nearly all are probes whose witness nobody reads. The copy is now made on first read and kept, so
  reads see one object, as before. The coordinator never changes a witness in place, so a later copy
  equals an immediate one.

Proof: at `types-64` (`9464a67`), `size-36-1`'s digest was `e7bb78efa0345ac1`, before and after the
savings, in every run below. On `types-65` (#769, merged in) it reads `471fd6a139aaad0b` before and after
(review 685 also compared eight more seeds at 12, 24 and 36 wide). The full chain sweep against
`chain-baseline.json`, at `types-65`, shows no drift over 228 maps.

| Pair | Before: CPU / wall | After: CPU / wall | Ratio, CPU / wall |
| --- | ---: | ---: | ---: |
| 1 | 217.3 / 176.9 s | 153.4 / 121.0 s | 0.71 / 0.68 |
| 2 | 170.1 / 138.1 s | 135.4 / 107.4 s | 0.80 / 0.78 |
| 3 | 152.3 / 122.3 s | 105.5 / 85.1 s | 0.69 / 0.70 |

The change saves about a quarter of the 36-wide map's time, judged by pair. That is more than the
named costs add up to (9.7 + 4.8 + 3 + 2.3 = 19.8 s, about 17% of the profile), and not all of each
would go. The profile's shares are main-thread samples. CPU time also counts V8's helper threads,
and the savings allocate far less (no per-lookup strings, no per-probe copies), so collection
shrinks too: 7.9 s of the profile's samples were in the collector. The profile was also one run at
another moment of the load, not the pairs' baseline. The exact split was not pursued. The machine's load moved
the same version's runs by more than that, CPU time as much as wall time, which is why 31 now asks for
alternated pairs.

## Options that change content

For Corey, under 31's batching rule: each would land switched off and join a content batch.

- **Fewer front probes.** Cap `growFront`'s bisection at a few probes (full depth, then halves), or
  take the full depth or nothing. Fronts would come out shallower or absent where the cord is tight.
  This targets park's 30 s directly.
- **Fronts on a draft.** Grow park's fronts on a staged draft, as rubble's debris is, and prove them
  together, bisecting only on refusal. One discovery per park instead of one per probe in the common case.
- **Smaller rubble batches.** Flush rubble's debris in bands rather than all at once, so a refusal
  re-proves a band. `commitEach`'s greedy choice over a different grouping can keep a different set.
- **Edge walls per run.** Offer each perimeter run's walls as its own batch, so one refused wall costs
  one run's bisection. Cover could also offer its walls on the cord it sited with, rather than a second
  one, where its fallback doesn't need to be kept apart from them.
- **Fewer or incremental meshes**, as 42.32 listed: 31 s of the 117 are mesh builds.
