# 42.69. Tick phase 3 in the Rust core (#1238)

Up: [42](42-performance-history.md). Design: [27](27-rust-path.md#the-state-flip), step 5c.2. The Rust implementation
is `rust/core/src/phase_three.rs`, driven by `shared/simulation/phase-three.ts` from the phase-3 loop in
`shared/simulation/tick.ts`. It handles per-player action state, combat facts, item identity changes, and the
drop boundary where the adapter returns to JavaScript to admit physical items before resuming the next operation.

## Finding

**After reducing the input and output work, the crossing stays below 1% of the whole tick.** The crossing remains
well above the generic 10%-of-TypeScript-module budget in [42.58](42.58-sight-core-adapter.md#the-budget): it is
about 243–269% of the baseline `sim.actions` cost. This is the state-flip case, where the records being packed are
the game's own records and the caller cannot use a flat view. The two final measurements put the conservative
crossing estimate at 0.771–0.844% of the whole tick, inside the exception's strict 1% ceiling.

A final five-round confirmation after the last guard and dependency-wiring fixes measured **41.461 µs crossing,
0.874% of its 4.743 ms whole tick**, with `sim.actions` at 50.646 µs and the core call at 8.244 µs. That is about
278% of the earlier TypeScript module cost and still meets the state-flip exception. This single confirmation
is separate from the interleaved comparison below; its other busy share was 4.58%.
[Final raw rounds](reports/issue-1238/final-current.json).

The adapter-13 review revision (shared speed/utility parameters and per-game allocator binding) measured
**40.412 µs crossing, 0.861% of a 4.695 ms tick**, with the core at 8.231 µs and the action module at 49.511 µs.
This is about 271% of the earlier TypeScript module cost and remains under the exception. It was a separate
five-round current-only confirmation using the same cached map; other busy share was 4.90%.
[Review revision rounds](reports/issue-1238/review-current.json). Series are aggregated independently: crossing
is subtracted per round before taking its median, so medians need not subtract exactly.

The total `sim.actions` delta over baseline is 29.603–34.385 µs per tick. The conservative crossing is 2.43–2.69
times the baseline module cost, above 42.58's generic relative budget; as a whole-tick share it has about 0.16
percentage points of headroom under the state-flip ceiling. Whole-tick medians ranged from 0.74% below to 0.54%
above baseline.

The first final comparison, before the input/output packing optimization, did not meet the exception: its measured
crossings were 53.296 µs (1.146% of the tick) and 47.533 µs (1.019%). Static scalar field writes, direct item-row
appends, avoiding an output copy unless a drop or damage may grow memory, and reusing identical frozen motor
records brought both optimized measurements below the threshold. Those earlier results are retained alongside
the final results: [pre-optimization current 1](reports/issue-1238/pre-optimization-current1.json),
[baseline](reports/issue-1238/pre-optimization-baseline.json), [pre-optimization current 2](reports/issue-1238/pre-optimization-current2.json).

## Method

- **Environment.** Windows development machine, Node 24.15.0 and Cargo 1.100.0; the Rust core was built with
  `npm run core:build` in both checkouts. The baseline was commit `285404a23ad5d0e8ae416115a2125cca2aca3be1`,
  extracted by `git archive` into `.tmp-phase3-baseline`; its `node_modules` was a junction to the current checkout's
  dependencies.
- **The script.** [`tests/bench-phase-three.mjs`](../tests/bench-phase-three.mjs) generates and serializes the 24x12
  seed-4217 live map once, with prebuilt bot tiles. Each round deserializes that same map, creates a game with the
  shipped content, warms 300 ticks, then times 600 `step` plus `snapshot` ticks. It records the profiler's
  `sim.actions` and `sim.actions.core` means and reports the median of five rounds. It holds the exclusive bench
  lock and reports machine contention. Each run uses the same serialized map cache path so current and baseline
  deserialize identical map bytes. Prebuilt tile adoption is a WeakMap association and does not survive
  serialization; the 300 warm-up ticks amortize route preparation in every round. The run does not claim that each
  deserialized map retains prebuilt tiles.
  The measured serialized input's SHA-256 was
  `b13d673b8b5fc101dca36b2b2d27cbc9d15c525a281a902d0b9f5b7a95c37ebe`.
- **Reproduction setup.** From the current checkout root, create a baseline archive in a dedicated temporary
  directory, link dependencies, and build both cores:

  ```powershell
  git archive --format=zip --output=.tmp-phase3-baseline.zip 285404a2
  New-Item -ItemType Directory .tmp-phase3-baseline
  Expand-Archive -LiteralPath .tmp-phase3-baseline.zip -DestinationPath .tmp-phase3-baseline
  New-Item -ItemType Junction -Path .tmp-phase3-baseline\node_modules -Target (Resolve-Path node_modules).Path
  Push-Location .tmp-phase3-baseline
  npm run core:build
  Pop-Location
  npm run core:build
  ```

  Then, from the current checkout root, run the same cache and rounds in this order:

  ```powershell
  node --experimental-strip-types tests/bench-phase-three.mjs --root=. --cache=test-results/phase-three-map.v8 --rounds=5
  node --experimental-strip-types tests/bench-phase-three.mjs --root=.tmp-phase3-baseline --cache=test-results/phase-three-map.v8 --rounds=5
  node --experimental-strip-types tests/bench-phase-three.mjs --root=. --cache=test-results/phase-three-map.v8 --rounds=5
  ```

- **Run order and contention.** Current, baseline, current, with no intervening build or other test. All three
  optimized runs were below the lock's 25% contention threshold: other busy share was 4.54%, 5.19%, and 4.45%.
- **The crossing estimate.** `sim.actions.core` times only the mode-0 core call. Subtracting it from the outer
  `sim.actions` series conservatively counts input preparation, result application, and any phase-3 work outside
  that call as crossing overhead. It does not charge the phase-5 attack call to the core timing label.
- **Test cost.** `npm run brief -- test:times -- tests/phase-three-core.test.js` passed in 0.5 seconds for the file
  (1 second serial total).
  The review revision keeps its 14 cases at 0.5 s; the three new `action-parity` cases cost 0.5 s,
  `item-id-allocation` costs 0.7 s, and the updated prediction contract costs 0.5 s. Timing those and the three
  migrated equipment/utility files individually took 4 s total across seven files (each 0.5–0.7 s).

The archived optimized run results are [current 1](reports/issue-1238/optimized-current1.json),
[baseline](reports/issue-1238/optimized-baseline.json), and [current 2](reports/issue-1238/optimized-current2.json).
The complete raw rounds and contention readings are in those files. The earlier pre-optimization set is separate;
the initial exploratory measurements are not needed to interpret the final comparison.
The six older PowerShell captures also remain byte-for-byte in [raw/](reports/issue-1238/raw/README.md);
the linked copies are normalized to UTF-8 with their parsed values checked unchanged.

## Limits

- **Node only.** This does not measure browser WASM or JavaScript costs.
- **One map and content.** The run uses shipped content and a 24x12 seed-4217 map; other player counts and contents
  can change action and packing costs.
- **No rare-action workload.** A normal bot match does not exercise every item drop, damage, hook cancellation,
  or output-buffer growth path. The test suite carries the focused parity witnesses.
- **Source checkpoints differ.** The interleaved optimized runs preceded the optional missing-ammo fix, equivalent
  Clippy guards, removal of unreachable modes, and the acyclic adapter dependency wiring. The final confirmation
  includes those changes and packing of optional kit entries. It uses the same cached map and workload, after
  `npm ci`, but does not have another interleaved baseline. None of these measurements times every rare action.
