# 42.54. Field-typed descriptor codec against protobuf (#1130)

Up: [42](42-performance-history.md). Earlier comparisons: [42.49](42.49-wire-codec-selection.md),
[42.51](42.51-protobuf-head-to-head.md). Type model: [24.3](24.3-wire-data-model.md), on the relational
wire of [24.4](24.4-relational-data-model.md). This is the comparison that 24.3 and 42.51 called for: D and
stock protobuf (P) built from **one per-field type model** taken from the engine's data, after the relational
migration (#1147). Scope, budgets, the decision rule and a napkin estimate were posted on #1130 (comment 15982)
before any measurement. Nothing live changed: no protocol, `WIRE_VERSION`, simulation, recording or fixture.

## Finding

**On the declared rule, D: protobuf's steady messages are 1.59–1.83× D's.** The rule needed all four of
these for protobuf:
- bytes within 1.15× D's;
- Chrome decode within 1.25×;
- Node encode within 1.25×;
- a bundle of 16 KiB gzip or less.

| Condition | Required | Measured | Met? |
| --- | --- | --- | --- |
| Bytes | ≤ 1.15× D | 1.59–1.83× | No |
| Chrome decode | ≤ 1.25× D | 0.75–0.90× | Yes |
| Node encode, wall | ≤ 1.25× D | 0.77–1.05× | Yes |
| Node encode, process CPU (36x18) | ≤ 1.25× D | 1.93–2.15× | No |
| Bundle, as shipped | ≤ 16 KiB | 18.1 KiB | No |
| Bundle, `long` stubbed out | ≤ 16 KiB | 14.9 KiB | Yes |

D's bundle is 4.75 KiB. Protobuf's encode uses CPU beyond its wall time, which means work on other threads.
The likely cause is V8's background garbage collector reclaiming protobufjs' per-encode allocations; that
was not profiled. Server encode runs once per view per tick, so process CPU is the cost that scales.

- **Where protobuf's bytes go.** With every number encoded the same way in both formats (the
  "D, exact as f64" row), protobuf is still **1.25–1.30×** D. That is the format itself: a tag per present
  field and a length per nested message, against D's presence masks and positional required fields. It
  adds about 9–11 bytes to each observed player or body. The rest of the gap, 1.27–1.44×, is the
  "exact number" fields (hit points, shield, cooldowns, shape radius). They have no fixed type: content
  makes hit points fractional (24.3), so protobuf must spend a `double` on each, 9 bytes with its tag,
  where D's per-value form spends 1–2 bytes on the integers they nearly always are. A `oneof` would recover
  those bytes, and 42.51 measured what a per-value `oneof` costs protobuf's decode (2.2–2.6×).
- **Decode speed favours protobuf slightly, and both beat JSON.** Fixed types removed D's Chrome
  slowness from 42.49. Chrome steady decode is D 0.57–0.72× `JSON.parse` and P 0.47–0.54×. In Node, D
  is 0.37–0.59× and P 0.33–0.48×.
- **Encode is level in wall time, but not in CPU.** Node steady encode is 0.77–1.05× D's wall time, and
  0.74–0.98× in Chrome. At 36x18, though, protobuf's process CPU for encode is 1.93–2.15× D's (1.00–1.45× at
  12x6): its CPU runs at about twice its wall time, while D's matches its wall time. D's writer reuses one
  buffer.
- **The napkin estimate** posted with the budgets (1.2–1.4×) was right about the format and missed the
  number mapping. It counted tags and lengths but not the `double` that "exact number" forces on
  protobuf.
- **Both are exact** on all 244 samples at each size, also with fresh codecs in shuffled order, and both
  refuse every truncation, trailing byte and corrupted header.

**Recommendation: D for #1131's per-tick state. Corey selected D on 2026-11-17 ([17.4](17.4-live-service.md) #17).** 42.51's separable protobuf roles are
unchanged and still unneeded:
- `.proto` as the schema source, generating D;
- protobuf wire for low-rate messages (welcome, lobby, replay index).

Neither is needed until a cross-language consumer exists. This study generated both backends from one schema
mechanically (`wire-typed-schema.mjs`), so the schema-source role stays open whichever wire is chosen.

**What would change the call.** Two things would narrow protobuf's byte gap, and neither is enough on its own:
- Integer types for hit points, shield and the cooldowns, which would need content to round them (24.3).
  That would shrink the "exact number" share, but the format's 1.25–1.30× would remain.
- Fewer fields per message. 24.3's accepted proposals 3 and 8 (constants out of the tick, dead fields
  dropped) are not yet applied (below). They shrink both formats.

## The type model

`tools/perf/wire-typed-schema.mjs` holds one typed model for the v4 slice. Field names come from the
projection owners (`wire-typed-fields.mjs`); types follow 24.3's inventory and producers, applying its
no-behaviour-change proposals 1 and 2:
- body `x`, `y`, `vx`, `vy` are float32 metres (`v / 40`, exactness checked on encode); `angle` and `omega` are
  float32;
- ticks, counters, countdowns, `playerIdx`, `generation` and the keyed IDs (#1164) are unsigned 32-bit;
  `hazardX`, `lastSeq` and `inputMargin` are signed;
- `heading` is float64;
- content-derived values are "exact number": hit points, shield, cooldowns, shape radius, the prediction
  motor and bodyless fallback poses;
- closed unions index `shared/enum-tables.ts`. `PlayerStatus` has no table there, so the schema declares
  one;
- the body owner and shape are discriminated unions;
- `null` and absent stay distinct, as today's wire has them.

24.3's proposals 3, 6 and the clear cases of 8 are accepted (17.4 #17) but land with #1131's schema closure,
so this study measures today's v4 message: match constants, `null` values and unread fields are still sent.
The scope comment on #1130 called proposal 6 undecided; that was wrong.

**Native objects.** The model implies protobuf-shaped native objects:
- enum indices and metres;
- a oneof member per union variant, with single-scalar variants flattened (`ownerActor: 3`);
- `x` or `xNull` for a nullable field;
- `{ items }` wrappers for optional lists, so absent and empty stay distinct;
- a layer record for the keyframe/delta envelope.

Both backends encode exactly these objects. This is Corey's "tightly integrated" reading (17.4 #17):
projections that build the typed model directly. A generic converter maps today's projection objects to
native objects and back, and validates what neither format enforces: required fields, one oneof member and
enum ranges. Every exactness check runs through it, but no codec timing includes it. Generic and unoptimized,
it costs about one `JSON.stringify` each way (Node steady 5.6–13.4 µs to native and 5.4–13.1 µs back), so
production projections should emit native objects rather than convert.

**Candidates**, each generated from the native model:
- **D:** the descriptor codec (42.49) with fixed field types. It gained `sint`, `f32` and `f64` scalars
  here. "Exact number" uses its per-value form: an integer varint, else float32 when exact, else float64.
- **D, exact as f64:** the same codec with "exact number" as a plain float64. It isolates the format: every
  number is then encoded as protobuf encodes it.
- **P:** `protobufjs` 8.8.1 with an Edition 2023 schema (explicit presence, packed repeated scalars); field
  numbers follow declaration order. Each field has one fixed type: `float`, `double`, `uint32`, `sint32`, enums,
  and oneofs for the unions and nullables. Framing is format, version, message id and body length, as in
  42.51. Node timing uses protobufjs' runtime codegen, the same generated encode and decode functions
  that `pbjs` emits as static code.
- **JSON:** re-measured in the same process, on the projection objects.

## Footprint

Deployable ESM bundles built by esbuild 0.28.2 (minified, browser target) and gzipped at level 9
(`wire-typed-bundles.mjs`). The converter is shared by both and in neither.

| Bundle | Contents | Minified B | Gzip KiB |
| --- | --- | --- | --- |
| D | the descriptor codec runtime and its schema as data | 15,240 | 4.75 |
| P, as shipped | `pbjs` static code (encode/decode only), `protobufjs/minimal`, framing | 89,105 | 18.13 |
| P, `long` stubbed out | as above without the 64-bit `long` package | 78,258 | 14.91 |
| Converter | the generic projection ↔ native converter (`wire-typed-schema.mjs`) | 9,434 | 3.59 |

- **As shipped, protobuf exceeds the 16 KiB budget.** Its generated static code is 45 KB minified for
  this slice alone. `protobufjs/minimal` always includes `long`, 11 KB minified, although this schema has
  no 64-bit field. Stubbing `long` out is an optimization protobufjs does not ship; it brings the bundle to
  14.9 KiB.
- **D grows more slowly.** D's schema is data that a generic runtime interprets: 5.3 KB of it for this
  slice. Protobuf generates a function pair per message, so its code grows with every record the full
  protocol adds. This slice holds 20 messages and 9 enums.
- **This settles 42.51's open footprint question for this slice.** 42.51's figures were upper estimates
  added from separately gzipped, unminified pieces.

## Semantics and malformed input

- **Exact:** 244 of 244 samples per size for D, P and D-f64, through the converter back to the JSON
  round trip of the projected objects, and again with fresh codecs in shuffled order.
- **Truncation:** every cut of 12 samples per size is refused. That is 5,478–5,837 cases for D and
  9,600–10,132 for P, whose messages are longer.
- **Trailing bytes and corrupted headers** (format, version and type bytes) are refused by both.
- **Crafted lengths:** a list count of 2^31 (D) and a length-delimited field claiming 2^31 bytes (P) are
  refused in under 0.1 ms.
- **Seeded single-byte corruption past the header** (2,000 cases per size):
  - D refuses 36% and P 36–37%; nearly all of the rest decode to a different valid message, against 22% for D
    in 42.49.
  - The rise is fixed-width floats: any 4 corrupted bytes are still a float32. Neither format has an
    integrity check, and transport integrity (#1095) covers this.
  - The worst decode was 4.0 ms (D) and 1.1 ms (P).
- String, `null` and specimen behaviour of each format is unchanged from 42.49 and 42.51 and was not re-run.
  The converter refuses lone surrogates for both backends, as 42.51's protobuf path did.

## Limits

- **The slice** is 42.49's families in their v4 form: header and prediction fields, `self` (with its
  discovery layer), observed players and the bodies layer. Items, tethers, flights, gates, traps,
  projectiles, effects, events and the seats roster are out, as before. Items are a large share of
  keyframes; their records are mostly small integers, as observed players are, so the ratio there is not
  expected to favour protobuf.
- **Bot traces**, 1,200 ticks of a 12,000-tick match. Discovery layers, inventories and reloads occur;
  tethers, hook flights, box and convex shapes and stack items do not.
- **Static code against reflection.** Node timing used protobufjs' runtime codegen. The `pbjs` static
  module gives identical bytes and exactness in Node, with the same corruption outcome to the case
  (`wire-typed-comparison.mjs --protobuf-static`), and Chrome ran the static bundle.
- **One protobuf library and declaration-order field numbers.** Renumbering the most frequent fields
  first would save the second tag byte on `self`'s fields 16 and above: at most 4 bytes per contestant
  message.
- **Allocation, capped packing and quantization probes** were not re-run. They did not separate the
  candidates in 42.49/42.51, and #1094 owns precision.

## Workload and provenance

Measured 2026-11-17 on Windows with Node v24.15.0 and Chrome 157.0.8103.51, on an AMD Ryzen 9 5900X. Branch
`claudecode/1130-field-typed` from `e06a73da`. The Node and Chrome timed runs were sequential under the
exclusive lock and uncontended: external busy was 4.8% and 5.0% in Node, 8.5% and 8.1% in Chrome. The source hashes in each report (LF-normalized) match the committed tools.

The caches were generated fresh at `e06a73da` (seed 4217, tuned content, `chain-live-2`), because #1153 changed
simulation and server sources since 42.47's caches. `loadCachedMatch` checks them against that revision. The
match runs with a fixed `wireKey`, so IDs are keyed and sized as in a live room (#1164). The corpus is
production `broadcast`'s state objects as handed to `JSON.stringify`: every twentieth tick of 1,200, across
four views, 244 samples per size.
