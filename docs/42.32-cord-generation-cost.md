# 42.32. Live-cord generation cost

Back to [42](42-performance-history.md). Issue #767, following [42.31](42.31-rubble-plant-live-cord.md)'s
cost finding: at `types-62` a 36-wide map took 51 s to generate, against 31 s before the live cord.
The coordinator is in [20.10](20.10-portal-cords.md). This records where the time goes and two exact savings.
Content is unchanged: no version bump.

## Method

`node tools/generation-time.mjs`: whole-map `generate(seed, params, undefined, 48)` on 42.31's panel,
`size-{12,24,36}-1` with #688's parameters, three sequential runs per map under the `bench` machine
lock with nothing else running. It prints a digest of each map's results, which must match across runs
and across the change. The cost split is from one `node --cpu-prof` run of size-36-1 (57.8 s profiled,
against 50.4 s unprofiled), with mesh inputs captured from the same run and replayed warm.

## Exact savings

- **Strictly simple pass.** Clipper's `DoSimplePolygons` splits a ring where it meets itself at a
  repeated point. It compares each vertex with every later one, so it is quadratic in ring length, and
  eroded rings with round joins are long. A ring with no repeated point is left untouched.
  `strictlySimpleClipper` (`shared/shape-construction.ts`) checks every output ring for a repeated
  point in linear time and runs Clipper's own pass only when one has one. The result is Clipper's
  either way. On the 3,877 captured inputs the rings are byte-identical, no ring repeats a point, and
  the union drops from 2.7 s to 0.8 s. All three strictly simple clippers in `shared/` use it.
- **Edge normalisation.** `geometricEdges` read every endpoint in a segment's x span to find the
  collinear ones, so a long horizontal run read nearly every endpoint. It now also keeps the endpoints
  sorted by y, reads whichever span holds fewer of them, and sorts what it finds in the same
  (x, y) order. The point set and the order are the same, so the edges are too.

Proof: `sweep --check` against `chain-baseline.json` shows no drift over 224 maps. Each panel map's
digest is unchanged: `f2d9ab979384f5a8`, `bba4537e0f602a77` and `c66dd86792501e71`.

| Map | Before | After | Saved |
| --- | ---: | ---: | ---: |
| size-12-1 | 5.11 s | 4.83 s | 0.28 s |
| size-24-1 | 22.67 s | 20.79 s | 1.88 s |
| size-36-1 | 50.39 s | 45.93 s | 4.46 s |

Runs agree within 0.4 s. The 36-wide map is 9% faster, still 15 s above `types-61`'s 30.8 s.

## What is left

- **Exact, small.** `discoverCordWitness` re-checks the region's cells and rebuilds its access mask on
  every call (about 1 s profiled). Caching them exactly needs either a cache keyed on a brief that
  callers could change, or a new option. Left for now.
- **Not exact.** These would change which cords are found, and so refusals and maps:
  - an incremental mesh, or anything else that builds fewer meshes;
  - checking once after several placements and bisecting to the failing one (Corey, 2026-11-01);
  - rubble and plant claiming an envelope and checking once at the claim, as park's fronts do, rather
    than once per commit.

  Under [31](31-verification.md#content-changes-one-bump-per-batch), each lands switched off and joins
  a batch.
- **Rollout.** The exact savings do not change 42.31's assessment. A live-cord move still costs about
  ten times the builder's frozen-route time. Moving depot, market and hall, which are large and have
  many portals, needs one of the inexact savings first, or acceptance of the cost.
