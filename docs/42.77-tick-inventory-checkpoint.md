# 42.77. Tick mechanic inventory checkpoint (#1279 step 1)

Up: [42](42-performance-history.md). Inventory: [27.1](27.1-tick-mechanic-inventory.md). Comparison: [42.76](42.76-state-flip-benchmark.md).

## Finding

**There is no change from 42.76.** The checkpoint runs the same runtime code as 42.76's current runs: `0eb41ff1` with 42.76's profiler labels, merged as `e0d4dcbe`. Everything changed since then is documentation. The first checkpoint run was 0.663 ms above 42.76's no-trap range. Every group in that run was slower, by 6–17%, which points to the machine's state rather than the code. The external busy share looked normal at 8–9%, so the contention stamp did not flag it. Four reruns on the same source and map fall back within 42.76's ranges.

**For later #1279 milestones:** one unpaired run on unchanged code drifted about 13%. A milestone bench "against 42.76's figures" cannot detect a change smaller than that drift unless it pairs its runs with a baseline in the same session, as 42.76 did. It should also record the map cache's hash, which 42.76 did not.

## Method and limits

Windows, Node 24.15.0 and release core WASM built from `e0d4dcbe`. The 24×12 map used seed 4217 and cache SHA-256 `b13d673b8b5fc101dca36b2b2d27cbc9d15c525a281a902d0b9f5b7a95c37ebe`. The reruns used a cache freshly generated at `e0d4dcbe` and checked against that hash. An older cache in another worktree hashed differently, so a stale cache can silently change the workload. Each headless workload ran five rounds of 300 warm and 600 timed ticks plus snapshots. The table gives the median of the round means for each group, and each rerun range covers two runs. External busy shares were 8.00% and 9.06% for the first runs and 5.4–7.3% for the reruns, all below the 25% cutoff. 42.76 records no map hash, so its map is assumed, not verified, to be the same; the reruns landing inside its ranges is consistent with that.
