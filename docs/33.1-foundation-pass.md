# 33.1 Foundation Pass

Up: [33. Maintenance rules](33-maintenance.md)

A Foundation Pass is a periodic, project-wide review of quality and
maintainability, taken between major feature efforts. It leaves the repository
able to carry the next foreseeable work while keeping its functional state. This
document says what a pass covers and where its decisions stop. It does not say
when to start one or in what order to work; the plan and the issue tracker own
that. Everything above [In this repository](#in-this-repository) is meant to
apply to any project.

## Conditions

- **Freeze.** A pass assumes a feature and defect freeze, held by the humans who
  manage the project so the pass works from a stable base. They may bring
  specific feature or defect work in; agents do not. A defect enters the pass only
  when it blocks foundation work or its acceptance. Record other defects for
  separate triage.
- **Behavior.** Preserve functional behavior as much as practical. A behavior
  change that an approved structural or architectural rework requires is approved
  with that rework. Land it as its own commit in the rework's pull request, after
  the behavior-preserving steps. Name it in the description, and make its
  compatibility, version and expected-output decisions explicitly under the
  project's verification policy. A human decides any other behavior change case
  by case.
- **Foreseeable work.** Work is foreseeable when the project's documentation or
  issue tracker states it or plainly implies it. If that work needs a foundation
  the project lacks, file the need as an issue with its purpose and rationale.
  This permits surfacing a missing layer, not building a speculative one.
- **Smells are evidence, not quotas.** Size, duplication, flags, comments and
  abstractions are signals to investigate. Change something when the result
  improves ownership, clarity or future work enough to justify the cost. When a
  clearer alternative does not fit, record the local reason beside the code.
- **Every finding gets a disposition.** Fix it within approved scope, file it as
  an issue, or decline it and say why. Act directly on clear cases. Where value
  or optionality is a judgment call, give the human the evidence, the
  alternatives and a recommendation.

## Concern tracks

### 1. Code health and composition

Look for dead or redundant code across the whole repository: production code,
tests, scripts and developer tools. Every file, module and construct should have
a clear identity and responsibility, and names that are hard to confuse with
others.

A large file is a strong smell. It often holds behavior that should be built from
narrower concerns. Repeated code suggests a shared abstraction when it expresses
one concept. A similarity that looks coincidental may still point to a useful
project or subsystem utility. Keep each abstraction with its real owner. Judge
behavior controlled by awkward or out-of-band flags case by case, against the
mechanisms and owners that already exist.

Keep comments that state what a function, type or structure is and should do.
They give it an identity, so changing the behavior means changing the comment
too. Keep non-obvious invariants and the reasons a design is right. Remove
comments that only restate self-evident behavior. Remove development history,
confessions and warnings drawn from past mistakes. Archive any that are still
useful.

### 2. Architecture and foreseeable work

Look across subsystem boundaries for unclear ownership, excess coupling,
duplicated responsibilities, concerns that are not separated, and modules that
are easy to confuse. Consider the shape of the whole system, not only local
cleanups. Compare it with the foreseeable work and surface each concrete gap as
an issue, under the condition above.

### 3. Documentation and decision history

Find documentation that is stale, inaccurate, conflicting, misplaced or overlong.
Split or redistribute material so each topic has a coherent owner and readers
load only what they need. Give each maintained fact one authoritative home.
Where duplication is warranted, the copy links back to that home.

Active documentation states what is: the current contract, requirement or status,
and the reasons that still matter. Verbatim captures preserve provenance, but
understanding and preferences change. Where a requirement has settled, state it
formally in its owning document. Then move the superseded captures and explored
paths out of active guidance into the archive, with their wording intact. The
archive keeps active context small. It also adds friction, so reopening a
settled choice becomes a deliberate act rather than a slide back down a path
already ruled out.

### 4. Optimization investigations

Optimizations are investigated, not implemented by default. Characterize each
candidate by its expected benefit and evidence (with the workload), its cost to
build and maintain, its effect on behavior, its risk, and the optionality it
keeps or gives up. A clear improvement can still narrow future choices, so weigh
that cost explicitly. End with a recommendation to pursue or defer, the reasons,
and the evidence that would change it.

### 5. Project entry points

The root README presents the project as it is now: what it is, who it is for,
its current state, and how to get started. It does not recount history. The
project names its primary audiences; give each of them:

- a quick start,
- a short summary of how the project works,
- current screenshots or video of the product and its tools,
- a brief architecture and repository overview with basic development guidance,
- the current contribution policy, and
- a short synopsis of current state and roadmap.

Detailed references, such as full command lists, tool catalogs and the complete
repository tree, belong in dedicated guides, summarized and linked from the
README. Secondary audiences, such as people building on the project as the base
of a fork or the maintainers' own workflow, get their own quick-start guides. An audience guide that belongs beside the README is
`README.<subject>.md`. Product, engineering and process material stays in the
project's documentation structure. Summaries link to their sources.

### 6. Tests and verification

Tests and verification tooling are part of the foundation, and their cost in time
and workflow is a quality concern alongside confidence and coverage. Look for:

- incorrect tests, which do not do what their names and assertions claim;
- dead tests, which pass but no longer check anything that matters, or whose
  purpose nobody remembers;
- redundant or superfluous checks;
- setup heavier than the behavior under test;
- granularity problems: a test that hides distinct claims and should be split,
  or related checks that could share an expensive setup without becoming opaque
  or order-dependent;
- safe shared or cached resources that other tests could start from;
- test sets too coarse for an agent to run only the checks that concern its
  change;
- coverage gaps.

Fix clear-cut waste and incorrect tests within scope. Give the human cost-versus-value
cases with their evidence and a recommendation. Prioritize coverage gaps in
contracts the pass changes or relies on; record other gaps for separate triage.

## Ending a pass

A pass ends when every track has been swept and every finding has its
disposition. The human managing the project then declares the pass closed, and
the next feature effort begins.
