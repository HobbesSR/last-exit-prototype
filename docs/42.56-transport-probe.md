# 42.56. WebTransport through a lossy relay, Node to Chrome (#1095)

Up: [42](42-performance-history.md). Design: [24.5](24.5-transport.md); the split it carries is
[24.2](24.2-lossy-transport-deltas.md), whose offline model is [42.50](42.50-lossy-deltas.md). This record checks
the transport itself: a real WebTransport session, the candidate server stack, Chrome's own QUIC and real packet
loss. It does not measure our codec, deltas or acknowledgements. The server stack measured here is the Node addon. The edge has since been
decided as Rust (27), so its own server-side numbers come from 24.5's stage 1. The browser's and QUIC's
behaviour recorded here does not depend on the server library.

## Finding

**The candidate stack works here, and real QUIC behaves as 42.50 modelled.** Datagrams lose frames, but the age of
the newest frame a client holds stays bounded. A reliable stream delivers everything, but its tail grows with
loss, because each loss holds every later frame until the retransmission arrives.
- **Staleness p95, datagrams against the reliable stream:**
  - typical: 111–112 ms against 121–126 ms;
  - wifi: 182–191 ms against 270–324 ms;
  - poor: 301–347 ms against 611–1,520 ms.
  - p99 widens the gap. On poor it is 350–440 ms against 743–1,900 ms.
- **Against 42.50:** its model gave split-delivery datagrams a p95 of 99 ms on typical and 249 ms on poor, and
  today's reliable layers 199–249 ms and 599 ms. Here a frame is sent whole every tick, so a lost frame costs one
  tick, as the model's acknowledged-baseline deltas do. The probe's staleness also includes the up-to-50 ms gap
  between ticks.
- **The cap.** Chrome 157 reported `maxDatagramSize` 1,211 bytes in every run. A 1,300-byte datagram written by
  the page resolved without an error and never arrived, so the sender must check sizes itself.
- **Connection setup** costs about two round trips without loss: 18–29 ms on lan, 99–116 ms on good, 195–238 ms on
  typical. Lost handshake packets wait for QUIC's probe timeout. That took 0.5–1.0 s on wifi and 0.8–3.5 s on
  poor. A WebSocket join pays TCP's and TLS's equivalents, which this loopback probe could not load with loss.

## Method

`tools/perf/transport-1095-probe.mjs`, Node 24.15.0, Chrome 157.0.8103.51 headless, on the development machine
under the bench lock. Three runs of 20 s per profile, seed 1095. Raw results:
`docs/reports/issue-1095/transport-probe.json`.
- **Server.** `@fails-components/webtransport` 1.6.12 with its prebuilt quiche binary, in the probe's Node
  process. It uses a self-signed ECDSA P-256 certificate, accepted by its hash (`serverCertificateHashes`).
- **Sending.** Every 50 ms it sends one 350-byte frame, the size of a 42.55 steady D message for a player view,
  on each of three channels:
  - a datagram;
  - a length-prefixed message on one reliable unidirectional stream;
  - a WebSocket message.
- **Relay.** A UDP relay between Chrome and the server applies 42.48's profiles (and 42.50's bursty one) to every
  QUIC packet in both directions: half the rtt plus exponential jitter, independent loss, and bursty outages per
  50 ms slot. Handshakes, acknowledgements and retransmissions all cross it.
- **Measurement.** Every 10 ms the page records the age of the newest frame each channel has delivered
  (staleness). Every 100 ms it sends a ping datagram, which the server echoes, for the round trip.
- **Relay timing.** The relay times packets with a timer followed by a short spin. Windows' `setTimeout` alone
  added about 10 ms per hop (lan's round trip read 26 ms instead of about 6 ms).

Medians of three runs, ranges where the runs differ notably. Staleness is p50 / p95 / p99 in ms. The WebSocket

The measured round trip exceeds each profile's nominal rtt by about twice the mean jitter, as the profile's
exponential jitter on both legs predicts. Datagram delivery tracks the profile's loss rate. The datagrams that
were not delivered are the ones the relay dropped. Lost ping datagrams likewise go unreplaced: the probe never
re-sends them.

## Limits

- **One machine, loopback.** Server, relay and Chrome share the CPU, and the relay shares the server's event loop.
  No real network path, NAT, or path MTU discovery was involved.
- **WebSocket under loss is not measured.** TCP loss cannot be injected on loopback from user space. The reliable
  QUIC stream stands in for it. Both are reliable and ordered, and TCP's minimum retransmission timeout (200 ms or
  more) suggests the WebSocket would stall at least as long.
- **Chrome only.** Firefox and Safari were not run.
- **Server CPU** per session and per datagram was not measured. It belongs to stage 1 of 24.5, under a real room's
  load.
- **Whole frames, one size.** 350 bytes never fragments. Fragmentation and 24.2's whole-frame recovery are stage 3's
  measurements.
