# 42.22. Server tick cost by stage and map size (#637)

Up: [42](42-performance-history.md). Parent checkpoint: [42.20](42.20-physics-p9.md#default-activation-checkpoint-523) (#635).
Harness: [31](31-verification.md) (`npm run bench:stages`). Siblings that act on this: #638 to #641.

Measurement only: no gameplay, wire or ordering change. Timers were added and nothing else.

## Method

**Timers, not a profile.** The physics coordinator had no timers, so about 60% of a physics tick was unattributed.
`shared/simulation/phased.ts` now times each phase (`sim.bots`, `sim.actions`, `sim.solve`, `sim.poses`,
`sim.projectiles`, `sim.pickups`, `sim.environment`, `sim.sync` with `sim.itemSync` inside it, `sim.discovery`,
`sim.rewind`) inside an inclusive `sim.step`, like the legacy step. The legacy step gained `sim.environment` and `sim.rewind`. `snapshot` is split into
`sim.snapshot.world` (the physics world copy), `.presentation` (body capture and item poses) and `.clone` (the
`structuredClone` of the whole state). Broadcast is split into `loop.encode` (layer and discovery encoders) and
`loop.serialize`, and every keyframe cut counts as `work.rekey.<layer>`. The profiler is off by default and every hook
returns before reading the clock. `profiler.frame()` now returns the frame's totals, so the harness keeps every tick
instead of the 600-sample window. One CPU profile (`--cpu-prof`, 800 ticks at 36x18) was used only to name the
functions inside a stage.

**Harness.** `tests/bench-stages.mjs` runs the body of the server loop (`server/room-service.js`) for each room in
turn: `match.advance()` (step and snapshot), the real replay writer with its gzip output discarded, `remember` (the
spectator history) and `broadcast` with fake sessions. It yields between ticks so compression keeps pace. Sessions
are attached to bot seats, so a viewed seat still runs its bot. Read every multi-viewer row as a full bot room plus
the views; it is an upper bound for that pairing. The harness also records GC pauses (`PerformanceObserver`),
which tick each overlaps, and v8-serialized sizes of the state and the history. The untimed remainder is
0.01 ms per tick at every size, so the stages cover the whole tick.

**Runs.** Seed 4217, Node 24.15.0, this machine, sequential under the benchmark lock, nothing else running. The
runs were driven by `tools/perf/stage-runs.sh`, and `tools/perf/stage-report.mjs` produced
[the tables](reports/issue-637/stage-tables.txt). Per-run summaries, including every over-budget tick (the first 80
per run), are in [stage-attribution.json.gz](reports/issue-637/stage-attribution.json.gz). Item counts below are the
generated map's items (893, 3,633 and 7,713). 42.20's 974, 3,853 and 8,608 count the same maps from the started
game. These are not capacity promises.

The harness mean is about 3.5 ms above `tests/bench.mjs` at 36x18 (32.6 against 29.4) because it adds recording
and encoding. Three physics repeats per size agree within 2% on mean and p99 (12x6 6.97 to 7.25 ms, 24x12 16.11 to
16.20, 36x18 32.38 to 32.77).

### Baseline and physics increment (deliverable 4)

At 36x18 physics costs 14.2 ms more than legacy (32.6 against 18.4). The two parts:

- **Shared baseline, about 18 ms, present on both engines:** the state clone (7.5 to 8.0), recording (2.9 to 3.2),
  the item scans in interact and pickups (3.4 to 3.7), bots (2.7 legacy), discovery (0.9), projection and encoding
  (0.8 to 1.1). Legacy alone is over the 25 ms P9 p99 target at 36x18 (30.9 in this harness).
- **Physics increment, about 14 ms:** `sim.solve` 6.85, `sim.sync`/`itemSync` 1.44, `sim.poses` 0.85, the world
  copy 1.00 and the presentation capture 0.88, which sum to 11.0. On top of that, bots cost 1.75 more (dynamic
  navigation observations, `dynamic-navigation.ts`), projection 0.35 more (bodies) and recording and clone 0.8 more
  (the physics state in the frame).

The ladder fits use the four or six points after 12x6 (with 12x6 they read 0.04 to 0.1 lower). The first 1,200
ticks are heavier than the whole match, which raises the ladder exponents a little.

**O(items) per tick today (exponent about 0.8 or more):** the state clone, recording, the interact and pickup scans,
item sync, item pose write-back, presentation capture, the physics solve, per-view projection and layer encoding. The
CPU profile names the scans. `automaticPickups` (`loot.ts:115`) tests every ground item for every contestant
each tick. `interact` (`interactions.ts:46`) filters every item for each interacting player.
`writePhysicalItemPoses` (`world-physics.ts:115`) and `synchronizePhysicalItems` walk every item. The solve
holds at most 128 dynamic bodies, so its growth goes with the static colliders (7,768 at 36x18); that link is
inferred, not shown. **Sub-linear:** repath (sliced, bounded), discovery, the physics world copy (dynamic bodies
only, `includeStatic: false`) and serialization (the payload is already a delta). Bots grow at 0.4 to 0.6 on real
maps; the profile places that growth in `decideBot`, which copies and filters every remembered item per bot each
tick and checks gates per item (`bots.ts:489`–`494`).

**Calibration of the ladder.** At the same item counts the tiled 24x12 and 36x18 match the real maps within about
10% in every stage except bots, which run 1.5 times (legacy) to 3 times (physics) higher on tiles. Repath is lower,
and legacy projectiles are higher. Tiles are joined only where their edges allow, so routes are not real topology,
and bot rows on the ladder are not evidence.

**Beyond 36x18.** Physics cannot be built past 36x18: `buildPhysicsGeometry` refuses extents above 51,840 by 25,920
world units (`MAX_WIDTH`/`MAX_HEIGHT`, `shared/simulation/physics-geometry.ts`), exactly 36x18. A larger physics
map needs that limit reviewed first. The ladder measured legacy at the synthetic sizes, first 1,200 ticks, with
bots inflated as above:

| Size (12x6 tiled) | Items | Legacy tick mean | `sim.snapshot.clone` | `loop.record` | Ticks over 50 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 48x24 (4x4) | 14,288 | 47.1 | 15.5 | 5.3 | 273 of 1,200 |
| 72x36 (6x6) | 32,148 | 115.4 | 35.5 | 11.6 | 1,200 of 1,200 |

Physics at those sizes is extrapolated, not measured. The stages with an exponent near 1 sum to about 30 ms at

(52 and 118).

## Ticks over 50 ms

Each over-budget tick is classified by its largest stages, whether a keyframe was cut on it and how much GC pause
overlapped it. "GC" below means a pause of more than 5 ms (kinds 1, scavenge, and 4, mark-compact).

**The 12x6 71 to 80 ms tick is tick 1, explained.** It is the only tick over budget at 12x6, and it is tick 1 in all three
runs (76.5, 70.9 and 72.5 ms): the first world step (`sim.solve` 43 to 47 ms), first pickups (12 to 15), item sync
(6) and bots (4). It is also tick 1 at 24x12 (106 to 110 ms) and 36x18 (141 to 148 ms). Encoding plays no part: the
rekeys counted on tick 1 are each view's first keyframe. Most of the first solve is paid once per process, not
once per room. With four rooms starting together in one process, tick 1's four first solves took 59.5 ms in total,
only 15 ms more than one room alone. A live server would pay it on its first room after start, and `tests/bench.mjs`
pays it in every run because each run is a new process. Whether it is engine warm-up or the first broadphase build
was not separated.

**36x18 physics: 45, 52 and 54 ticks over budget after tick 1 (0.46 to 0.55%).** Not periodic at a fixed
period. Many recur at the same tick in all three runs (10, 54, 110, 364 or 391, 634, 658, 710, 739, 752, 953), so
deterministic game events and allocation drive them.

- **GC:** 20 to 23 of them overlap a GC pause (35 to 124 ms for the largest). The pause lands in whichever stage was
  allocating: the clone, pickups, recording, presentation or projection. About two thirds of the over-budget ticks
  are still over without the GC time. GC averages 1.7 ms per tick (7,700 pauses per match); legacy averages 1.1.
- **Bot decision bursts:** `sim.bots` at 15 to 28 ms, often with `sim.repath` at 7 to 13, at the recurring ticks.
- **Solve spikes:** `sim.solve` at 16 to 30 ms (typical 7) with little GC, scattered through the mid-match. Cause
  not found.
- **Clone at double cost:** `sim.snapshot.clone` at 17 to 22 ms (typical 8) with no pause recorded, at intervals of
  roughly 215 to 230 ticks in the mid-match. V8's incremental marking charged to the allocating stage would fit,
  but that is an inference.
- **Keyframe cuts: none.** No over-budget tick after tick 1 had a cut. Cuts happen on 0.2% of ticks with one
  viewer. With eight player views they happen on 21% of ticks and on 19% of the over-budget ones, no more than
  chance. #640's keyframe hypothesis does not hold at these sizes.

**36x18 legacy: 3 ticks**, each with a GC pause of 16 to 40 ms, and none over budget without it. **24x12 physics:** tick 1 and 0 to 3
others (GC or a bot burst).

which lines their early matches up; staggered live rooms would line up less. GC hardly figures: 165 of those 191
ticks are over budget without it.

## Memory

v8-serialized sizes, a proxy for retained heap. The spectator history keeps 62 frames per room (`remember`,
`SPECTATOR_DELAY_TICKS` + 2), so its memory is state size times 62:

| Size | State (legacy / physics) | History per room (legacy / physics) |
| --- | ---: | ---: |
| 12x6 | 95 / 138 KiB | 5.8 / 8.4 MiB |
| 24x12 | 376 / 423 KiB | 22.7 / 25.6 MiB |
| 36x18 | 824 / 871 KiB | 49.9 / 52.8 MiB |
| 48x24 (tiled, legacy) | 1,679 KiB | 101.7 MiB |
| 72x36 (tiled, legacy) | 3,792 KiB | 229.6 MiB |

Linear in items. Sampled heap peaked at about 1.7 GiB in a 36x18 physics match. That includes uncollected garbage
from a high allocation rate (a full clone and a full JSON frame per tick), so it is not a retained-size figure.
Memory over longer sessions or across matches was not measured.

## Which sibling acts on which rows

- **#638 (snapshot copy):** `sim.snapshot.clone`, the largest stage, 8.0 ms at 36x18 (25% physics, 41% legacy),
  exponent 0.8 to 1.0, baseline. `loop.record` (3.2 ms, one JSON frame of the whole state per tick) and the
  history's memory are the same per-tick whole-state copy. The clone is also the main allocator behind
  GC-overlapped tail ticks.
- **#639 (in-server deltas):** the stages that walk every item each tick: interact and pickup scans (3.65 ms,
  baseline), item sync (1.28), pose write-back (0.85) and presentation capture (0.88; these three are the physics
  increment), encoding and recording. Together about 7 ms at 36x18 besides the clone, all exponent 0.8 to 1.1.
- **#640 (tails):** keyframe cuts ruled out as a cause; the 12x6 spike is tick 1's first solve (warm-up, mostly once
  per process). What remains is GC overlap (about 40% of over-budget ticks), bot decision bursts, solve spikes,
  clone at double cost, and rooms lining up when several run at once.
- **#641 (spatial partition):** per-view projection (0.8 ms per player view, 2.4 ms for the spectator view at 36x18,
  exponent 0.85 to 0.95), the per-contestant pickup scan and the interact filter (distance tests over every item),
  and bots' remembered-item filter. Admitting item bodies by distance would bear on `sim.solve` (6.85 ms, 21%) only
  if the growth there is the static colliders' and not the dynamic bodies', which is not established.
