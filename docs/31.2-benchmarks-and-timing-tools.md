# 31.2. Benchmarks and timing tools

`node tools/perf/wire-encoding.mjs --maps-cache=FILE --out=FILE --timing`
compares JSON, dictionary binary and field-specific quantization on production
broadcast state messages (#1093). `--generate --size=12x6` (or `36x18`)
creates a fresh worker-generated cache at an absent path. Runtime/generation
sources must be clean; cache source is checked against current sources.
Without `--timing` it runs correctness/byte checks under a shared lock; with it,
three alternating encode/decode rounds use the exclusive lock and report wall
and process CPU time. Workload, reproduction, raw evidence and limits are in
[42.47](42.47-wire-encoding.md). It is an opt-in design witness, outside test tiers.

`node tools/perf/wire-codec-selection.mjs --maps-cache=FILE --out=FILE [--timing] [--browser]`
is the #1130 backend comparison. It covers JSON, JSON+deflate, a schema-compiled descriptor/DataView
codec and msgpackr records on the players+bodies slice of production broadcast messages. It reuses a
retained 42.47 cache (sources are checked against it) and verifies every sample exactly, and with
fresh decoders. It then reports bytes, distinct-baseline variants and the capped-packing and
quantized probes. `--timing` takes the exclusive lock and adds Node wall/CPU timing and sampled
allocation. `--browser` adds the Chrome run (`wire-codec-browser.mjs`).
`node tools/perf/wire-codec-safety.mjs` runs the semantic-specimen and malformed-input suite on its
own. Results and limits are in [42.49](42.49-wire-codec-selection.md). These are opt-in witnesses,
outside test tiers.

`node tools/perf/wire-protobuf-comparison.mjs --corpus=FILE --out=FILE [--timing] [--browser]` is the
#1130 protobuf head-to-head. It reads a corpus written by `wire-codec-selection.mjs --corpus-out` and
compares stock protobuf (protobufjs, with its schema generated from the descriptor schema) with
JSON, the descriptor codec and msgpackr. Results and limits are in
[42.51](42.51-protobuf-head-to-head.md). It is an opt-in witness, outside test tiers.

`node tools/perf/wire-data-model.mjs --maps-cache=FILE --out=FILE` is the #1139 data-model probe. It
projects every player's own view and the directed view each tick with production `match.project` and
reports per field the value kinds, number class (integer, float32, scaled float32 or float64), the
float32-metre round trip, range, presence and string cardinality, with coverage against the
projection declarations. Results are in [24.3](24.3-wire-data-model.md). It is an opt-in witness,
outside test tiers.

`node --expose-gc tools/perf/relational-replay.mjs --root=PATH --mode=legacy|relational`
is #1162's retained-replay conversion witness. It uses shared source records across
3,500 frames (920 items, 90 gates, 12 players), roots both decoded source and result
through GC, and reports added heap plus wall/CPU time under the exclusive machine
lock. It measures timeline construction rather than parsing or drawing, and is
outside CI. Method, results and limitations are in [42.53](42.53-relational-projections.md).

Other agents' worktrees share this machine's CPU. `tests/helpers/machine-lock.js`
provides a shared/exclusive machine-wide lock using fixed loopback ports so the OS
frees every held port the moment a process exits or is killed, with no lock file
to go stale:

- **Exclusive (`47913` + draining `47914–47915`):** taken by benchmarks (`bench`,
  `bench:client`, `bench:stages`, `bench-session`), `test:times`,
  `BUILD_BUDGETS=enforce|report`, and timing/comparison tools. An exclusive holder
  takes writer-intent on `47913` first (blocking new shared holders) and waits for
  all shared slots to drain before running.
- **Shared (`47914–47915`, 2 slots):** taken by `npm test`, `test:slow`,
  `test:all`, `test:mapgen`, `brief.mjs`, `sets.mjs`, `sweep` / `sweep-briefs`,
  and non-timing audits. Up to two shared test runs execute concurrently when
  writer-intent is unheld; outer wrappers set `MACHINE_LOCK_HELD` so nested calls
  do not consume a second slot.
- **CI, waits, and contention:** `CI` / `FORGEJO_ACTIONS` skips the host loopback
  lock so isolated containers never block on host benches. `--no-wait` fails fast
  instead of waiting; waiting runs log who is waiting, behind whom, and for how
  long. Timed runs also record a contention stamp (`lock.contention()`),
  measuring external machine CPU busy share (`os.cpus()` minus process CPU) and
  marking runs contended above a default threshold (currently 25%, `CONTENDED`).
- **Policy for audit and evidence scripts:** separate correctness from timing via
  `--timing` (as `compound-cord-audit.mjs` and `hut-cord-audit.mjs` do), taking
  `exclusive` only under `--timing` and `shared` (or unlocked) for default
  correctness runs.

Timing tools (`bench`, `bench:stages`, `bench-session`, `bench:client`,
`generation-time`, `*-timing.mjs`, and `tools/perf/*`) report process CPU time
(`process.cpuUsage()`) beside wall time. Process CPU time includes V8 GC helpers
and worker threads (so for worker benchmarks it measures total work, not latency)
and is not steadier than wall time on a shared machine (on #868, three runs of
the same 36-wide `generate` read 152–217 s CPU and 122–177 s wall, while each
alternated pair's ratio held within 0.69–0.80); compare versions in alternated
pairs and judge by each pair's ratio (31, Gates). `test:times` stays on
wall-clock budgets (31, "Test cost").

Owner-probe socket resets are ignored: a waiting process may time out its probe
while the holder is CPU-bound, and that diagnostic disconnect must not crash the
holder (#437).

`npm run bench:client` runs a client render and network benchmark in Chrome.
Options include `--seconds=<N>`, `--headed`, `--location=dense|crowded|offscreen`
to arrange entity crowds, and `--spectator` (`node tests/bench-client.mjs --spectator`)
to benchmark rendering the unfogged, whole-arena spectator overview at full zoom-out.
`--viewport=WxH` and `--dpr=N` match a reported device's window, `--software-gl` draws
WebGL on SwiftShader, and `--diagnostics=FILE` saves the player-facing download.
`tests/bench-session.mjs` samples one long match every interval instead, optionally
roaming, at a native device scale, or against another checkout (`--root`); see 42.2 (#549).

`npm run bench:stages` (`tests/bench-stages.mjs`) attributes the server tick by stage: it runs
whole rooms through the server loop body (advance, recording, spectator history, broadcast with
projection, layer encoding and serialization) and keeps every tick of every `sim.*`/`loop.*` timer,
so each tick over 50 ms is classified by stage, keyframe cut and overlapping GC. It drains the recorder between
ticks, outside the measured time, and fails a run whose recorder drops a frame. `--rooms`,
`--clients`, `--spectators` and `--no-record` shape the load; `--tile=CxR` repeats a real map at
the same density for sizes the protocol does not serve. Each room keys its outward IDs as production
does (#1164); `--wire-key=none` projects internal ones. It takes the same lock.
`--maps-cache=<file>` reuses the production-worker geometry/navigation cache from
`room-startup.mjs` for sequential comparisons (use a fresh cache after generation/content changes).
The result's `run` records wall and process CPU milliseconds over the loop and inter-tick drains,
including worker CPU; per-tick timings still exclude those drains. Method and the
first results are [42.22](42.22-tick-cost-attribution.md) (#637). `--heap-profile=<file>` samples
allocations over the measured ticks (`--heap-interval=<bytes>`, default 32768), including objects already
collected, and writes a `.heapprofile` that DevTools opens. It also prints the top allocators, by function and by
the nearest frame in the repository's own code. A profiled run's times are slower and are not comparable with an
unprofiled run's (#727).

`node --max-old-space-size=12288 tools/perf/recording-compare.mjs --maps-cache=<file>
--out=<json>` is the whole-match recording witness (26, #901). It records one whole cached
match through the production writer and worker, reads the archive back with the shared
reader, and fails unless every rebuilt frame is byte for byte the authoritative frame's
JSON, every checkpoint holds and the published digest covers the stored lines. It refuses
any omitted frame and reports frames, keyframes, checkpoints and stored against full-frame
bytes; `--keyframe-every=N` overrides the cadence, and `--archive=FILE` keeps the archive. It takes the shared lock and drains the
writer between frames; it is exactness evidence, not a timing comparison. Run it when the
frame encoding changes. (Before #901 it compared #728's worker archive byte for byte with
an archived writer.) Simulation/view equality is separately checked by `frame-hashes.mjs`.

`node tools/perf/recording-payload.mjs --maps-cache=<file> --tile=2x2
--ticks=1200 --out=<json>` is a recording-only scaling probe when tiled geometry
exceeds physics admission limits. It records stable tiled item/gate lists and a
changing tick, without advancing a tiled simulation. `--baseline=<archived-writer-module>`
selects a comparison writer. It takes the lock and reports append latency and
run wall/CPU time, including draining, separately. Its results are not server
tick or capacity measurements.

`node --expose-gc tools/perf/recording-delta.mjs --maps-cache=<file> --out=<json>`
evaluates recording delta formats with periodic keyframes (#901) over one whole
cached match: a top-level-key and an entity-level prototype, at keyframe cadences
`--cadences=20,100,600`. It reports raw and gzip archive bytes, encoder time,
gzip/SHA-256 CPU per MiB from a sample, and reader parse, heap, playback and seek
cost. It rebuilds every frame and fails unless each equals the full-state line
(`--verify=N` checks every Nth; the run replays the match a second time).
`--kept=1` lets the entity encoder skip unchanged items and gates by their
owners' kept JSON, as the writer does; `--ticks=N` shortens the run. It takes the
exclusive lock. A 36x18 whole match needs `--max-old-space-size=12288` and about
six minutes. The prototypes are evidence, not a recording format.

`node tools/perf/room-isolation.mjs --size=36x18 --host=threads --pairs=3 --maps-cache=test-results/iso-36x18.bin --out=FILE`
is #1089's acceptance measurement: whether a second room's preparation and start disturb a room already
running. It runs the room service as production does (`--host=threads`, each room on its own thread) or
with every room on the host thread (`--host=inline`, the earlier shape), over real loopback WebSockets, a
real file archive in a temporary directory (so every room's recorder runs) and the production map handoff:
maps from the map worker stay packed and are handed to the room as a pooled one would be. Each pair is a
fresh service: room A starts with one recording dev viewer and settles for 2 s (`--settle-ms`); A's state
receipts are measured over a steady window (`--steady-ms`, default 3000), then over a startup window from
room B's creation through its readiness, join and first state frame plus 1.5 s. Each window reports A's
gap p50, p99, maximum and count over 75 ms, with process CPU (every thread, including the socket client
worker) beside wall time; recorder health is each archive's own count of dropped frames. Pairs run
sequentially under the benchmark lock (`--pairs`, default 3). `--maps-cache=FILE` saves the two packed
maps or restores them, checked by seed, size and content id; use a fresh path after generator or content
changes. Errors or dropped frames set a failing exit status. Results are in
[42.46](42.46-room-threads.md). `--profile` (threads only, #1119) is the threaded counterpart of
`room-startup.mjs`'s stage attribution. It turns profiling on and reads each room thread's own series
(#1115), resetting them between windows. The windows are: preparation to ready; tick 1 (from just before
start until the room has simulated a tick, with `simSteps` showing any catch-up tick in it); each room's
first 10 s after tick 1 (A's settle period is stretched to cover it, and B is observed past the startup
window); A's steady window; and A during B's startup. A's make/ready wall and process CPU are reported too.
The profiler keeps 600 samples per series, and a room's loop banks a frame on every wake (about 70–80 a
second). So the 10 s windows are read every 2 s and merged (sample-weighted means, largest maximum, no
percentiles), and a window over 600 frames fails the run. The console shows a condensed summary per
window, and `--out` keeps every series row. Profiling adds work, so isolation
figures come from a run without it. Results are in [42.22](42.22-tick-cost-attribution.md).

`node tools/perf/room-startup.mjs --size=12x6 --out=test-results/startup.json`
is the short startup diagnostic for #842 (also accepts `--size=36x18` and
`--seed`). It takes the benchmark lock, prepares two maps through the production
map worker before timing, and runs the real room service and scheduler with one
dev viewer per room and replay compression to a discard stream. After a cold
room's first tick, it advances through tick 400 with timer yields: ticks 1–200
cover the first ten simulated seconds, and ticks 201–400 form the later comparison
window. These advances are not paced in real time. The scheduler then runs that
room for one second before a second room is constructed and started; both run
for another 1.5 seconds. Construction/readiness,
start, the cold first tick, timer delays, delivery gaps and host wake work are
reported separately. `--out` retains raw wakes, all phases (including the 399
`window.tick*` entries), `preparationStages`, `coldTickStages`, per-tick
`startupWindow` attribution and the running-room profiler stages. Console output
omits the per-tick phases, startup window, running-room stages and raw series.
Each phase includes process CPU time, and the report includes the machine-contention stamp.
Recorder drops or lifecycle errors fail the diagnostic. The default uses direct
fake-peer delivery callbacks. Add `--sockets --viewers=9` for real loopback
WebSocket delivery and nine dev viewers per room, joined sequentially. Socket
clients parse their welcomes and frames on a separate worker, and the delivery
series then measures the first active viewer's parsed state receipt times.
Joins wait for the welcome, and starts wait for the initial state; server phases
and host wake measurements remain separate from these end-to-end waits. The
result includes lifecycle wall and process CPU time through replay drain and
transport teardown, excluding map preparation and transport setup. Process CPU
includes recorder workers and, in socket mode, the client worker.

`--root=PATH` selects an archived source tree's server modules plus its matching
navigation-cache and profiler instances. The harness and cached source maps stay
common, so alternate revisions adopt identical prebuilt navigation rather than
accidentally rebuilding it in only one version. Archive `server/`, `shared/`,
`map/` and `package.json` beneath the worktree (for dependency resolution).
No production disk throughput, remote network or worker map delivery/adoption
while live rooms run is measured here; `room-isolation.mjs` above measures the latter with threaded rooms. The short sample's
p99.9 is effectively its maximum; delivery gaps over 50 ms include normal cadence
jitter. This locates blocking work, not capacity or closure evidence for #635.
`--maps-cache=FILE` saves the two worker-prepared maps with their navigation and
tile data, or restores them on another run. Use a fresh path after generator or
content changes; the cache checks seed, size and content id, not source hashes.
`--profile=PREFIX` writes separate CPU profiles for the concurrent preparation,
join and start phases after map generation. Inspector start/stop and profile
writing also block the event loop, so profiled timings and delivery gaps are
diagnostic only and must not be compared with unprofiled runs.
`tools/perf/frame-hashes.mjs` also accepts this cache, for example
`--size=36x18 --contents=content-6 --seeds=4217 --views --maps-cache=FILE`.
It restores the worker's navigation data, then hashes a whole match and every
player/spectator projection as usual. Cache seed, size and content must match.
`--payloads` additionally exercises recording/live/delayed map payload queries
and hashes their JSON at tick 0, 600, 1200 and the end. It requests the recording
map before the first snapshot, as startup does. `--root=PATH` selects the archived
match and matching navigation-cache modules for exact before/after comparisons.

`node tests/measure-changes.mjs` (`--size`, `--content`, `--seed`, `--ticks`, `--out`) counts how much
of each published frame differs from the previous tick's, per collection and by entity id. It times
nothing, so it needs no lock and runs in parallel. Results are in
[42.22](42.22-tick-cost-attribution.md#change-fraction-per-tick-655) (#655).
