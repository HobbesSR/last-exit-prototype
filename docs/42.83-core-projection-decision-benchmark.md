# 42.83. The core decides each player view (#1357, stage 1b)

Up: [42](42-performance-history.md). Design: [27.2](27.2-tick-architecture.md#projection-and-knowledge-1343-1352), "The
core's projection". Previous point: [42.82](42.82-projection-from-core-output-benchmark.md).

## Paired room loop, eleven viewers

Player views now come from the core's decision (`match_admit`, one call per broadcast for every player view), assembled from
the frame store's records. The pair ran `tests/bench-stages.mjs --clients=11 --ticks=1500` (seed 4217, `content-12`,
recording on). Runs alternated this change with its base, stage 1a's head (`278ea1b3`), three times each on 2026-11-26.
No other work shared the machine.

| ms/tick, mean of 1500 ticks, 12x6 | Base, runs 2, 4, 6 | This change, runs 1, 3, 5 |
| --- | ---: | ---: |
| Tick | 2.80, 2.69, 2.69 | 2.54, 2.68, 2.64 |
| Tick p99 | 5.38, 4.59, 5.58 | 4.15, 5.16, 4.82 |
| Not under a stage timer (mostly the step) | 1.47, 1.42, 1.44 | 1.39, 1.44, 1.42 |
| `sim.playerView`, 11 views | 0.55, 0.53, 0.52 | 0.37, 0.40, 0.40 |
| `sim.admit`, the core's decision for 11 views | — | 0.11, 0.12, 0.12 |
| `loop.encode` | 0.24, 0.23, 0.23 | 0.18, 0.20, 0.20 |
| `loop.broadcast` | 1.16, 1.11, 1.09 | 1.00, 1.08, 1.06 |

- **Projection costs the same.** With the core's decision, assembly takes about 0.035 ms per view and the decision
  about 0.01 ms per view. Their sum, 0.49 to 0.52 ms, is within the base's 0.52 to 0.55 ms.
- **The base ran a little slower than 42.82** in the same code (0.52 to 0.55 ms against 0.48 to 0.50), so compare
  within this pair only.
- **`loop.encode` came out lower in every run of this change** (0.18 to 0.20 ms against 0.23 to 0.24). Nothing in the
  change touches encoding, and no cause was found. Treat it as unexplained.
- **The tick** is within the runs' spread.

## One pair at 24x12

The same command with `--size=24x12`: 830 items against 232, and 13,982 obstacles against 3,355. One run each.

| ms/tick | Base | This change |
| --- | ---: | ---: |
| Tick | 3.18 | 3.07 |
| `sim.playerView` | 0.54 | 0.39 |
| `sim.admit` | — | 0.11 |
| `loop.encode` | 0.21 | 0.17 |

The decision stays at 0.11 ms with 3.6 times the items. The core reads only the grid cells within a viewer's reach, and
the assembly picks records by ID, so per-view cost follows the viewers and what lies near them, not the map's size.

Two costs here are still the size of the whole frame:
- Building the frame. The frame store lists every body pose each tick, which is unchanged.
- One index per frame list. The assembly builds an index for each new frame list, by ID and shared by every viewer.
  The bodies list is new every tick.

  is still unexplained.
