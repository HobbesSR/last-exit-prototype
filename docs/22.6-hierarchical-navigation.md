# 22.6. Hierarchical navigation and optimistic bot planning

Status: proposed design for #353, 2026-10-15. Research and implementation plan;
none of the new behavior below is implemented. Up: [22](22-ownership.md).

The first research milestone (#364) is recorded in [42.1](42.1-navigation-experiment.md).
Its tooling validates swept edges but rejects the uniform 24-unit graph with every
boundary transition for adoption as written. The production design below remains
a proposal; revise its representation using that evidence before integration.

## Purpose and scope

Bake reusable navigation from completed collision geometry before play. Give
contestant bots only the pieces they have discovered, and let them hypothesize
routes through unknown space. Give gladiators the full static atlas. Keep actual
movement and interactions authoritative. The goals are believable exploration,
bounded local searches, and long detours that do not fail merely because they
leave today's start/target search rectangle.

Corey's direction in [#353](http://localhost:3000/corey/astra_test/issues/353)
is baked, hierarchical, progressively revealed navigation with support for map
changes. His addition on 2026-10-15 is verbatim:

> oh, one thing we might also want to do is "speculative" or optimisitic planning by the bots.

The choices here are engineering recommendations, not additional recorded product
answers. Existing knowledge rules remain in [15](15-information-rules.md).
This pass designs the system; it does not implement a new navigation engine,
change gameplay, select destructible materials, add floors, or change transit AI.

### Decisions to confirm before adoption

Two recommendations depart from the initial shape suggested in #353: using
192-unit discovery-aligned chunks instead of chain regions as the coarse unit,
and initially baking the atlas into memory while deferring saved-cache delivery.
The reasons are reveal granularity and physical crossings for the former, and
the canonical saving contract plus unmeasured startup/storage costs for the latter.
The first milestone may compare these alternatives experimentally; before it
hardens either into a production contract, record Corey's choice on #353 using
the evidence from #364. Merging this research/design document does not itself
settle those choices. Baking before play remains the direction in either case.

## Findings that constrain the design

- `shared/simulation/bots.ts` combines a legacy block graph and windowed local
  `gridRoute`. Chain maps have no populated legacy block graph. The local box
  spans the bot and target with padding, so neither search cost nor completeness
  is suitably bounded for long routes.
- `shared/map/navigation.ts` caches tile-center occupancy at 40-unit spacing,
  clearance 14/25 for contestant/gladiator, against actual geometry and gate
  state. `shared/map/route.ts` tests endpoint snapping, but does not sweep every
  neighbor link. Walkable endpoints alone do not establish a traversable edge.
  Straightening cannot repair an invalid underlying link.
- `shared/discovery.ts` reveals geometry in 192-unit cells using the view window;
  beacons can reveal isolated distant cells. Loot uses separate line-of-sight
  memory. Neither a whole generation region nor a route crossing it is therefore
  automatically known when one part is discovered.
- Bot planning and `accessible()` consult live gate locks. `exploreTarget()` also
  calls `insideMap` on unknown cells. Restricting only the route finder would
  leave these information channels in target selection.
- Generation portals are promises at region boundaries ([20.1](20.1-region-contract.md)),
  not an exhaustive list of physical crossings. Clear margins can cross ownership
  ([20.6](20.6-passable-margins.md)). Buildings, squeezes, and internal doors
  require finer connectivity. A single node per region loses that structure.
- Chain saves preserve decisions and derive views ([51.12](51.12-map-and-saving.md)).
  Navigation is derived. Playback restores frames, while snapshots include bot
  paths ([26](26-recording-contract.md)); new paths are a gameplay change even
  if tick order and RNG consumption remain unchanged.

## Chosen architecture

Use an HPA-style atlas of small local graphs plus a graph of their boundary
connections. A hierarchy does not require polygonal navmeshes. Start with the
existing 2D geometry vocabulary and a deterministic sampled graph; retain the
legacy 40-unit route path for `content-1` characterization.

| Concern | Proposed owner |
| --- | --- |
| Node/edge records, clearance and swept segment predicate, graph search | `shared/navigation/` (new portable runtime subsystem) |
| Pre-match baking and chain geometry adapter | `map/navigation/` (new); consumes the shared baker/primitives |
| Full atlas attachment at live assembly | `map/live.ts`; opaque runtime resource, not an enumerable `GameMap` field |
| Geometry reveal and gate observations | `shared/discovery.ts`; one source per contestant |
| Knowledge-filtered navigation view and query cache | `shared/navigation/knowledge.ts` (new) |
| Goals, exploration scoring, progress/stall policy | `shared/simulation/bots.ts` |
| Inspection and measurements | `map/tools/` and the existing Map Lab routes tool |

The shared baker accepts collision geometry and public dimensions, never a macro
import. Generation passes its finalized translated geometry through that same
entry point. Tests and explicit non-chain maps can bake from loaded collision
geometry without importing `map/`. This respects [22.2](22.2-map-generation.md)
and the dependency-free kernel. Atlas IDs are navigation IDs, never gameplay IDs;
baking consumes no gameplay RNG or ID stream and never changes generated bodies.

### Local units and safe edges

Use a 192-unit discovery cell as the initial navigation chunk. Split each into
8 by 8 sample squares: provisional spacing 24 world units, with sample centers
12 units from the chunk boundary. Unlike 40, this divides both the reveal unit
and 48-unit live map cells. This is an algorithm parameter to validate in the
first experiment, not a new movement grid or body scale. Larger clearance disks
may extend across several chunks.

Bake separate contestant/gladiator connectivity with clearance 14/25. A node
must fit; every cardinal and diagonal edge, endpoint connector, inter-chunk link
and smoothed segment must pass a swept-disk test at that same clearance. Include
the playable mask, voids, walls, circles/polygons and gate footprints. Use segment
versus shape distance/intersection through the shape owner, including segment
interior containment and tangency policy, rather than assuming finite occupancy
samples prove continuous clearance. Diagonal corner policy must be consistent
with that predicate. This is a shared geometry addition to review independently.

Snapping must find a clearance-valid connector from the actual position. No
fallback across a wall. Goals such as loot behind a window need reachable
interaction stands plus reach checks, rather than blindly connecting to an
obstructed item center. Return a distinct invalid-endpoint result when necessary.
The sampled graph is conservative: it is not a proof of connectivity of all
continuous free space. A narrow physically valid gap can be missed; diagnose and
add local refinement if the authored passage fixtures require it. Never silently
fall back to the omniscient old route finder for contestants.

Each primitive records its **support**: the discovery cells intersecting its
clearance-expanded segment/point bounds, including geometry and void there.
Local summary paths stay inside their chunk except for separately represented
crossings. The support of a summary is the union for its witness path. Bounds
may conservatively overestimate support. This makes "known path" mechanically
checkable, including disk overlap near chunk corners.

### Hierarchy and query

Preserve each legal boundary sample transition initially. Inside a chunk, cache
shortest transfer costs between its boundary nodes per body and effective local
barrier state; reconstruct the chosen witness with a small local search instead
of storing all polylines. Same-chunk queries still connect exact start and goal.
Disconnected components stay separate. Enumerate physical crossings from final
geometry, including incidental ones outside macro portal runs. Generation region
and portal IDs are optional diagnostic labels, never navigation permissions.

Insert query-local start/goal connectors, search the boundary graph across the
map, then refine only the leading corridor for execution. There is no fixed
600-unit detour box. Use stable coordinate ordering and explicit tie breaks.
An upper level grouping 4 by 4 chunks (768 units) is a later measured optimization,
not a prerequisite. Only fully supported, known summaries can enter that level.

Keeping all boundary transitions is the correctness baseline. Open-chunk costs
can be implicit; do not eagerly allocate dense matrices for empty/unvisited
chunks or duplicate static data per bot. Any later portal compression must show
that connectivity is preserved, measure path stretch, and retain a way to refine
ambiguous crossings. HPA-like abstraction does not by itself promise globally
shortest continuous paths or a speedup on this project's maps.

## Knowledge and optimistic planning

Maintain three distinct things: immutable truth atlas, private knowledge view,
and ephemeral speculative plan. Only the knowledge view and plan reach the
contestant planner. Its interface must not expose the full map, hidden region
membership, hidden component counts or hidden path costs. Gladiators use the full
static view but retain existing player visibility/sensor rules.

1. On geometry discovery, admit the newly known chunks. A baked node/edge/summary
   is usable as confirmed only when its entire support is discovered. Whole-region
   reveal is forbidden. Disconnected beacon chunks remain disconnected facts.
2. Unknown space uses a neutral **free-space hypothesis** inside public world
   dimensions. It does not read the actual playable mask, hidden walls, region
   types, door IDs or topology. The implicit 24-unit graph treats unknown geometry
   as empty, while checking all already known geometry. Boundary primitives with
   partially unknown support are reconstructed from known geometry and labeled
   speculative; their true baked blocked/open bit is not consulted.
3. Abstract unknown chunks analytically using the same movement metric and
   boundary convention, not their real atlas. Shortcuts carry their crossed
   unknown-cell supports. A speculative plan may pass through unknown chunks to
   an already discovered beacon or remembered objective. It may be wrong about
   a void or obstruction; that is intentional. It never invents hidden loot or
   targets an undiscovered charger by reading truth.
4. Return both a tentative full route and its confirmed executable prefix. Execute
   only the prefix ending at a reachable observation stand near the frontier.
   Discovery normally looks far ahead of movement. When revelation changes the
   hypothesis, replan from current position. Zero prefix means seek another
   reachable observation stand or await the scheduled discovery sample; it does
   not mean repeatedly try to walk through an unseen wall.
   Select the stand and its connector using only the knowledge view, with fully
   discovered clearance support. A stand does not guarantee future visibility of
   loot; local authoritative collision may still stop motion if remembered state
   has become stale.
5. Keep a speculative goal stable while progress is made. If one approach is
   disproved, try another frontier toward that goal. Do not permanently abandon
   a cell or objective because a hypothesis failed, a budget expired, or knowledge
   is disconnected. Reconsider temporary failures on relevant knowledge/barrier
   revision. Preserve the existing separate need to explore *loot sight* frontiers
   even when surrounding geometry is already discovered.

Initial route scoring uses known travel cost plus optimistic unknown travel
cost, without a new tuned risk penalty. This deliberately permits a tempting
unknown shortcut over a longer confirmed route. Tune penalties only with visible
playtest evidence and record that separately. Geometry discovery permits learning
walls through roofs under [15](15-information-rules.md); it does not permit
learning current door locks or loot through roofs.

**Information test:** two maps identical in a bot's observations but different
behind discovery must produce identical target choices, route estimates,
speculative plan and inputs until observation diverges. This includes failures,
cache hits/misses, candidate ranking, `insideMap`, and `accessible()`; timing may
vary internally but must never control gameplay search budgets. Authoritative
collision and interaction may reject an action; they must not become a remote
"is this route possible?" oracle.

## Doors and changing geometry

Bake static geometry without door blockers, but retain stable door footprints
and affected primitive/chunk dependencies. Each knowledge view overlays its own
last-observed door state, not live gate bits. Unknown/unobserved door state is
optimistic; a discovered door footprint is not proof that it is unlocked. Add bot
gate observation to the existing LOS/roof perception owner; static terrain reveal
alone does not update lock state. Actual interaction refreshes the attempted
barrier observation and replans as appropriate.

This is a proposed addition to bot memory: today's `DiscoveryMemory` has no gate
observations. Record open and locked as separate last-observed facts, sampled
only when the door is within perception range, LOS-visible and not roof-concealed,
or when an interaction reports its local outcome. Optimistic passability is a
private hypothesis, never an observation or a change to displayed gate memory.
Preserve F-10's uncertain/closed presentation for unobserved gates.

An open door is passable. A remembered closed unlocked door supplies an explicit
open action; a remembered locked door needs a key. Multi-door search state must
include remaining keys if it promises an executable route, since keys are
consumed. The next corridor ends at an interaction stand and is revalidated after
opening. A plan may retain an optimistic tail beyond an unobserved lock, but
cannot call that tail confirmed. Cache local transfers by body, geometry revision,
knowledge revision and effective observed barrier/capability state. One bot's
new lock observation must not change another's private costs. Gladiators' full
map geometry access does not introduce new knowledge of other players.

Door state only recomputes affected local transfers and summaries; it does not
rebake the world. Index affected chunks by expanded footprint, including halo and
crossing links, not just the chunk holding the door center. A barrier may affect
several edges and components; it is not necessarily one graph edge.

For future removed walls/props, provide a geometry-change operation with stable
obstacle ID, old/new bounds and monotonic revision. Rebuild nodes, crossings and
transfers for touched chunks plus clearance halo, then invalidate affected upper
summaries. Removal can create a previously absent connection, so toggling existing
edges is insufficient. Keep physical truth revisions separate from each bot's
observed revision; a distant removal must not silently update its known layout.
Until a gameplay removal mechanism supplies observations, this is a supported
extension contract, not implemented destructibility. No new destructible kinds
are required for #353. Do not silently accept in-place geometry mutation.

Queries report `complete`, `speculative`, `no-known-route`, `invalid-endpoint`,
`budget-exhausted`, or `stale` with a frontier/partial prefix where available.
Use deterministic expansion limits and resumable work for expensive searches,
never wall-clock cutoffs that make machines choose different inputs. A budget
failure cannot establish unreachability. Bounds/limits must be chosen from the
first experiment; no millisecond tick-budget claim is made in this design.

## Baking, saving and compatibility

Bake when finalized geometry is assembled before match ticks; a loaded map can
use exactly the same baker. The artifact identifies algorithm version, sample
spacing, body clearances, frame origin/dimensions and a canonical collision-input
fingerprint (including mask and gate identities/footprints, excluding gate state,
items and runtime actors). Translations must match `builtMapFrame`/live assembly.

Keep the chain's canonical Layout/results saving rule intact. Initially derive
and cache the atlas in memory. A separately saveable optional navigation cache
sidecar is the proposed extension for baked-map distribution, not a third source
of generation decisions or a silently saved `mapViews` view. It must be specified
in [51.12](51.12-map-and-saving.md) and [53](53-map-artifacts-and-tools.md) in its
implementation PR. Record version and input fingerprint; a mismatch explicitly
rejects the cache and requires an explicit rebake path. Validate lengths, IDs,
costs and support references on import. Canonical geometry remains authoritative.
Cache persistence can follow runtime adoption if startup measurements do not
justify its immediate cost. This resolves the issue's "baked and saved" direction
without contradicting the current no-derived-views-in-chain-saves contract.

Do not enumerate the atlas in player projections, snapshots or replay map headers.
Paths consumed by today's bots are tile steps; the new 24-unit graph must not
reuse that type or multiply its indices by `TILE=40`. Introduce explicit world
waypoints/new private corridor state and audit snapshot, replay and renderer path
consumers before adoption. Any serialized path representation change requires a
specific schema/min-reader decision under [26](26-recording-contract.md).
Replay playback must continue using recorded frames, without requiring the atlas.

Keep `content-1` on its existing planner and frozen `behavior-nav-1.json.gz`.
`content-2` already exists as the default with discovery enabled. Navigation
adoption intentionally changes gameplay: its PR must explicitly choose whether
to change the current default `content-2`, with a documented rules/version
decision, or introduce `content-3` for the new behavior. This design does not
select that version policy. Storage/cache-only work cannot move characterization.
Never regenerate the frozen fixture to make this pass.
New planner state and paths remain excluded from live player projections under
[15](15-information-rules.md). Full snapshots and recordings are a separate
contract: changing only path values/behavior needs the gameplay version decision;
changing serialized frame shape also needs the schema/min-reader decision.

## Alternatives and research

| Approach | Assessment for this project |
| --- | --- |
| Larger/full-map A* windows | Useful measurement control, but leaves omniscience, repeated grid work and thin-edge defects; not the solution |
| One node per macro region | Useful diagnostic hierarchy; too large/irregular and unsafe as a reveal unit |
| HPA-style local graphs and boundary transfers | Recommended: portable with current shape code, bounded local repair, explicit reveal support |
| Recast/Detour tiled polygon navmesh | Credible alternative if sample fidelity or cost fails; larger geometry/toolchain integration and still needs private reveal/door logic |
| D* Lite/incremental search | Potential later optimization for repeated replans; does not itself solve map abstraction, safe geometry or information access |

Primary sources checked 2026-10-15:

- The [Alberta authors' project page](https://webdocs.cs.ualberta.ca/~games/pathfind/)
  identifies HPA* and its 2004 paper. The [2010 DHPA*/SHPA* research paper](https://ojs.aaai.org/index.php/AIIDE/article/download/12397/12256/15925)
  describes offline clusters and cached boundary costs, local updates after terrain
  changes, and time/memory/path-quality tradeoffs. Those mechanisms inform this
  proposal; its reported speedups do not predict Last Exit performance.
- [Recast's official documentation](https://recastnav.com/) separates mesh baking,
  runtime queries and tile caching, and describes tiled meshes for large/dynamic
  maps. Its [tile-cache implementation](https://github.com/recastnavigation/recastnavigation/blob/main/DetourTileCache/Source/DetourTileCache.cpp)
  handles obstacle requests and tile rebuilding. My inference: it is a useful
  fallback candidate, not a way to obtain private knowledge filtering automatically.

## Implementation sequence and acceptance

#353 remains the umbrella until implementation and playability are accepted.
Each stage below should be a separately reviewable issue/PR; parallel work starts
only after the shared graph/knowledge contracts are settled.

1. **Evidence and safe local graph spike ([#364](http://localhost:3000/corey/astra_test/issues/364)).** Own shared sweep predicate and a
   read-only atlas experiment/tool; keep production bots untouched. Test thin
   off-grid walls, diagonal corners, circle/polygon tangencies, void holes,
   contestant squeezes, hunter doorways, invalid endpoints and interaction stands.
   Compare 24-unit sampling with the 40-unit control and locally refined variants.
   Compare reachability with authored continuous-clearance witnesses and an
   unrestricted reference search over the same safe fine graph.
2. **Atlas and hierarchy.** Own baker, stable boundary IDs, body profiles,
   support provenance and local transfer repair. Test same-cell disconnection,
   concave/holed regions, incidental crossings, routes leaving the old window,
   doors on chunk corners and geometry removal creating new crossings. Full
   knowledge and chunked search must agree on connectivity with the fine graph;
   record path stretch, do not assert optimality without proof.
3. **Private knowledge and optimistic planner.** Own geometry-delta admission,
   observed gates, implicit unknown graph and result states. Test hidden-map twins,
   isolated beacons, partly supported edges/smoothing, empty knowledge, known
   dead ends, stale doors, competing bots with different memories, multi-key
   routes, and repeated invalidation. Confirm no atlas leakage into every outbound
   projection, recording header or snapshot. No production AI switch yet.
4. **Bot adoption and playability.** Replace truth-dependent route costs,
   `accessible`, unknown-mask checks and path consumers together. Preserve fixed
   tick/discovery schedule and one input per tick; document the intentional
   gameplay/version choice: change the existing default `content-2` with its
   rules/version decision, or introduce `content-3`, as described above. Verify
   stable goal progress, obstacle disproof and recovery, roofed loot exploration,
   visible door interactions and extraction.
   Keep the legacy fixture untouched and verify `content-1` still matches it.
5. **Persistence and inspection.** Add explicit sidecar serialization if justified,
   import rejection tests, CLI/Map Lab agreement, and debug layers for confirmed,
   speculative and executable paths, observation frontier, revisions and expanded
   nodes. Show full truth only in existing authorized dev views. Explain failures
   with result states. Update 51.12/53 and replay docs if relevant contracts move.

The first experiment must publish seed/config/source revision and hardware,
counts and memory, cold bake/load/reveal times, per-query expansion counts and
latency distribution, local repair work, path lengths/stretch and failed-route
reasons. Use authored sizes 12x6, 24x12 and 36x18, both bodies, short and cross-map
queries, repeated queries, doors, isolated beacons and partial discovery. Include
an explicit worst case with empty knowledge and every bot requesting a
speculative cross-map route in the same early-match planning round. Measure
aggregate work/latency, peak private cache memory, budget exhaustion and progress
across subsequent deterministic planning slices, for cold and warm caches. This
case tests whether optimistic search degenerates into repeated near-full-map
searches; per-query medians alone do not establish acceptable match cost. Also
include adversarial long detours and thin walls, not only random reachable pairs.
Compare cold and warm old planner, unrestricted safe fine graph, and hierarchy on identical
inputs; the old planner's false successes are correctness failures, not wins.
Report worst cases as well as medians. Do not allocate all boundary-to-boundary
polylines: their memory can dominate the graph.

Stop and revisit representation if the atlas cannot meet passage witnesses,
knowledge independence, bounded local repair, or improve actual long-route cost
without unacceptable startup/memory cost. Escalate missing product choices about
new destruction, sharing knowledge or multi-floor rules; none are needed for the
first three stages. Do not tune away a correctness failure.

Implementation gates follow [31](31-verification.md): focused route/discovery/
geometry tests and `test:times` for new/grown test files, then `npm run check`,
`npm run typecheck`, `npm run test:all`, relevant browser/Map Lab checks and the
chain sweep where shared/generation changes require it. Use `npm run bench`
sequentially, three before/after runs for suspected regressions; run client
benchmarks when path presentation or transported state changes. Existing slow
bot-objective matches are necessary but insufficient: add reproducible default
live-chain, discovery-enabled neutralized matches and inspect representative
replays for exploration, door handling, completion and stalls. No performance or
completion improvement is claimed until those results exist.
