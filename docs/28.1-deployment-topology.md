# 28.1. Deployment topology direction

Status: proposed direction, not decided. Developed during #1119 (room startup on threads) as the
context that work is heading toward, after Corey asked how the server's pieces might be split into
processes and threads, "some processes potentially in other host environments" (2026-11-15,
[17.4](17.4-live-service.md) question 15). Decisions are tracked in #1121; the hosting model and
rooms per host are #907. The rule in [28](28-operational-limits.md#before-public-deployment)
stands: no process split or service registry before its ownership and failure contracts have
concrete consumers. This document says where the seams are, so that work done now does not close
them off.

## Pieces and where they could live

| Piece | Today ([22.3](22.3-server.md)) | Proposed home | Reason |
| --- | --- | --- | --- |
| HTTP API and static assets | host thread | stateless gateway processes, scaled out | No per-tick work; cheap to restart |
| Sockets, protocol validation, latency pings | host thread | the room host that serves them (below) | The room decides which state frames to drop from its sockets' backlog |
| Directory and matchmaking: room cap, unique names, queue | host thread | one authority, a small service once there is more than one gateway | Needs a global view; nothing else does |
| Room lifecycle and simulation | one thread per room (#1089) | room-host processes, each carrying N room threads | Already message-shaped: `room-thread.js` and `room-worker.js` exchange plain operations and byte payloads, so a process host is a swap |
| Map generation and pool | worker thread; packed, transferable output | a generation service, possibly on other hardware; the pool becomes its cache | A pure function of seed, size and content version on one platform ([51](51-generation-chain.md); across platforms, see the rules below); bursty and CPU-heavy; its output is already bytes |
| Recording: frame encoding and gzip | one worker per room ([26](26-recording-contract.md)) | stays beside its room | Runs every tick; must not cross a network |
| Replay store: publication, listing, download | host thread | a storage service over object storage | Already decoupled by `published(meta)`; archives upload once finished |
| Development tools and labs | same server under `DEV_TOOLS` | separate, never in a production process | Different trust and failure profile ([24](24-networking-privacy.md#dev-view)) |

## Where client sockets terminate

A room decides which state frames to skip from each socket's backlog, which the host reports
([22.3](22.3-server.md#room-threads)). If sockets stay on a gateway while rooms move to another
process or host, that feedback goes stale with every hop. The proposal is the model the netcode was
shaped for, Colyseus's: the directory answers a join with a room host's address and a seat
reservation, and the client connects to that host directly. The gateway admits but does not carry
traffic. The spectator delay is the known mismatch with that model ([22.3](22.3-server.md)). Transport
choices under #1092 (WebTransport, #1095) assume this endpoint.

## Rules for any topology

- **No boundary inside the tick.** Processes meet only at admission, map handoff, recording
  publication and directory summaries.
- **One build everywhere.** Processes should compare their compatibility domains before working
  together: content id, `PHYSICS_VERSION` and `WIRE_VERSION` for the simulation, and for maps
  the generator's own domains in [53](53-map-artifacts-and-tools.md) (region strategy content,
  macro algorithm, chain wire, library fingerprint, region result). Whether a mismatch is refused
  or routed around during a rollout belongs with content rollout and draining policy
  ([28](28-operational-limits.md#before-public-deployment)).
- **Remote generation ships bytes, not seeds.** 53 promises the same map from the same seed only
  with the same engines and library; it does not promise bit-identical generation on different
  hardware or runtimes. `shared/math.ts` makes the simulation's math exact across platforms
  ([22.1](22.1-shared-simulation.md)), but map generation also calls native `Math` trig outside
  that boundary (for example `map/micro/parcel-area.ts`). So a room plays the map bytes a
  generator sent; it never regenerates a map from its seed and expects a match. Treating maps from
  different hosts as interchangeable by seed (a shared cache keyed by seed, or a generator on other
  hardware) needs that equality validated first, or generators confined to one platform.
- **Rooms per process is a cost question.** In #1087's profile about 40 ms of a cold first physics
  step was one-time first use of the engine's code, which a second match in the same process did
  not pay ([42.22](42.22-tick-cost-attribution.md#statics-only-preparation-step-1087)). Room threads
  in one process share that warmth. Only the process's first room thread paid it: about 37 ms more
  statics step and 0.35–0.8 s more preparation CPU at 36x18. Later threads started warm even after the
  earlier ones had ended ([42.22](42.22-tick-cost-attribution.md#room-startup-on-threads-1119)). One
  process per room would pay it every time.
- **A crash reaches its process.** A room-host crash ends its rooms. Their recordings remain as
  `.partial` files; salvaging them is still a separate follow-up ([26](26-recording-contract.md#verification)).
- **Observability aggregates.** Each room thread reports its own profiler series (#1115); across
  processes the same rows would go to a collector.

## Order

Each step is reversible and has its own issue once its consumer exists:

1. One process, a thread per room (done, #1089).
2. Room-host processes on one machine behind the existing room interface; the gateway still forwards.
3. Direct connect: the directory returns a room host address and a seat reservation.
4. Map generation as a remote service.
5. Replay storage remote; archive ownership and lifetime are #1074.

Steps 4 and 5 do not depend on 2 and 3, and can come first if generation load is the pressure.
