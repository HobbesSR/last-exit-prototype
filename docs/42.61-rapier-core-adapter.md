# 42.61. Rapier in the Rust core: the physics step through the batched adapter (#1192)

Up: [42](42-performance-history.md). Design: [27](27-rust-path.md#physics). The engine is `rust/core/src/physics.rs`
and its adapter is `shared/physics/world.ts`. They replaced rapier.js (`@dimforge/rapier2d-compat` 0.21.0), which
is built from the same parry2d and nalgebra. Both runs passed the frozen fixture unchanged.

## Finding

**The physics step costs about half as much; the whole tick does not visibly change.**
- **Method.** `tools/physics/bench-step.mjs` runs the same seeded live match in each checkout, under the machine
  bench lock: content-7, seed 4217, the default live size, with bots. It takes 1,000 ticks after 100 of warmup,
  and three games per run.
  - It times each `step(s)` and, inside it, `PhysicsWorld.step`.
  - The baseline is #1192's first PR (rapier.js, with Rapier already in the core's module), so the trees differ
    only in the engine path.
  - Runs alternated rapier.js, core, rapier.js, core.
  - Machine: Ryzen 9 5900X, Node 24.15.0, Windows 11, 2026-11-19.

| Engine | `PhysicsWorld.step` mean | p50 | p95 | Whole tick mean | Tick p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| rapier.js | 0.334–0.351 ms | 0.302–0.319 ms | 0.393–0.444 ms | 2.69–2.88 ms | 6.3–7.2 ms |
| Rust core | 0.153–0.187 ms | 0.149–0.173 ms | 0.197–0.298 ms | 2.46–2.94 ms | 6.3–8.0 ms |

- **The step.** Each of the six core games beat each of the six rapier.js games, by 0.15–0.20 ms a tick.
  - What went: rapier.js's wrapper calls, several per dynamic body each substep (velocity reads and writes, force
    resets, pose reads for paths), each building JavaScript objects for vectors. The handle-map re-sync was already
    skipped (42.22).
  - The core makes one crossing for the whole step, reading and writing two flat buffers.
- **The whole tick.** The ranges overlap. Physics was about 12% of this tick, so its saving is within the run-to-run
  spread of the rest (sight, bots, projection inputs). Tick-level gains wait for the phases the state flip moves
  next (27, #1210 onward).
- **Not measured here:**
  - the client's prediction replay, which steps the same adapter;
  - larger maps;
  - contention. The lock's contention sample was not recorded, so the per-run spread is the only noise measure.

## Budget

Rule 3 of [27](27-rust-path.md#the-core-and-its-adapter) asks each port to measure its crossings. As in
[42.58](42.58-sight-core-adapter.md), the crossing is not the cost. The remaining per-call adapter work is one pose read
per body per projection (`getTransform`), unchanged from rapier.js in count. If projection ever shows it, the
batched step's output could carry final poses too.
