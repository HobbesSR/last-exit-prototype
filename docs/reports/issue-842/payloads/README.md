# Reusable map payloads (#842)

Measured 2026-11-08 on Node v24.15.0, content-6. Baseline is
`9f589877c3ee064776332da9c0477fcc29e0f24c`; implementation is `706d7e4`.
The timing source is pinned above; final file hashes also cover subsequent
diagnostic additions and validation of the ordinary-JSON fallback. Prepared map
objects follow the same encoding path as in the measured implementation.
Ownership and preparation rules are in [22.3](../../../22.3-server.md).

## Method and retained data

The same `tools/perf/room-startup.mjs` drives each revision's production room
service, match, recorder and WebSocket adapter. Its navigation-cache adoption
and profiler use the selected revision's module instances. It uses real loopback
sockets; a separate client worker parses messages and stamps receipt times.
Clients are dev viewers, sharing one directed state projection per room, rather
than the eight distinct player projections and spectator required by #867.

Both maps (4217, 4218) are freshly generated by the production worker under the
baseline generation source, then cached identically for each comparison. Map
generation, worker transfer/adoption and transport setup precede timing. One
room is running before the second is constructed, welcomed and started. Runs
are sequential under the benchmark lock, with no competing verification from
this session. Each size/viewer case has three pairs in base/changed,
changed/base, base/changed order. Profiling is disabled.

`summary.json` retains all 18 run summaries, source/cache/map SHA-256 values and
map counts. `startup.json.gz` retains phases, every host wake and client receipt,
stage summaries, recording drops and errors. Local absolute source paths are
replaced with revision names. Lifecycle wall and process CPU include both room
recorders, the socket client worker, replay drain and transport teardown. More
elapsed preparation/join time also means more active simulation ticks, so these
totals are not matched-tick throughput comparisons. Output is compressed to a
discard stream; production disk throughput and remote networking are unmeasured.

## Remaining scope

Welcomes and recording starts get substantially cheaper, with more cooperative
preparation and extra memory for the static copy plus serialized data. Overall
delivery maxima do not establish startup isolation; first-tick work and recorder
startup/backlog remain. Final string assembly, UTF-8/socket work and a very large
individual preparation record can still block. Worker map handoff/adoption under
live load and synthetic-size startup are not established here. Neither #842 nor
#867 closes on these results. #867 still needs its distinct player-view,
whole-match, post-follow-up capacity measurement.

## Compatibility and recurring cost

Seed 4217's full content-6 matches retain identical snapshot, every-player/
directed-view and map-payload hashes before/after: 3,417 frames at 12x6 and
10,234 at 36x18. The four retained `hashes-*.txt` files contain the digests.
Map queries include the recording map before the first snapshot, then recording,
live and delayed maps at tick 0, 600, 1200 and the final tick. This exercises the
new publication path as well as private preparation, rather than only hashing
simulation that never requests a map payload.

`archive.json` records the exact baseline/current full 36x18 recording comparison:
10,234 frames, identical metadata, retained-frame digest and entire gzip archive
(1,200,925,211 bytes), with zero omitted frames in both writers. That unpaced
comparison drains both recorders between frames; it proves storage compatibility,
not healthy paced recording. Only digests/metadata are retained, not the huge
duplicate archives. Its commands list is empty in both versions, as specified by
the comparison tool; the cheap room regression covers join/start command order.

The final fast gate passes 1,507 tests; syntax checks and both typechecks pass.
The selected frozen bot characterization and both default-size whole-room replay
files pass (six cases). No fixture, generation source, content or format version
changed. Four new helper regressions and two small physics/room cases stay in the
fast tier: `room-map-payload` takes 0.2 s and `physics-match` 1.1 s in isolation,
both below 15 s. Synthetic records and a small arena cover format/immutability,
current/delayed privacy, queued-start lifecycle and archive headers; no large-map,
long-match or socket diagnostic is added to recurring CI.

The legacy browser suite fails its mobile `simultaneous move and aim` assertion

## Reproduction

Archive baseline `server/`, `shared/`, `map/` and `package.json` beneath the
worktree so dependencies resolve. Generate each cache once from the pinned
generation revision. The same current harness is used on both sides:

```powershell
node tools/perf/room-startup.mjs --sockets --viewers=9 --size=36x18 --maps-cache=test-results/payload-36.bin --root=test-results/base-9f58987 --out=test-results/base.json
node tools/perf/room-startup.mjs --sockets --viewers=9 --size=36x18 --maps-cache=test-results/payload-36.bin --out=test-results/changed.json
```

Repeat with `--size=12x6` and a separate cache; run `--viewers=1` for the large
single-view comparison. A failed health check exits 1 after saving evidence.
Inspect drops/errors before proceeding to the next explicitly failed stress run;
do not treat that exit as a passing check or silently enlarge the writer budget.

Compatibility diagnostics (run sequentially; these are not timing comparisons):

```powershell
node tools/perf/frame-hashes.mjs --size=36x18 --contents=content-6 --seeds=4217 --views --payloads --maps-cache=test-results/payload-36.bin --root=test-results/base-9f58987 --out=test-results/base-hashes.txt
node tools/perf/frame-hashes.mjs --size=36x18 --contents=content-6 --seeds=4217 --views --payloads --maps-cache=test-results/payload-36.bin --out=test-results/changed-hashes.txt
node tools/perf/recording-compare.mjs --baseline=test-results/base-9f58987/server/replay-writer.js --maps-cache=test-results/payload-36.bin --out=test-results/archive.json
```
