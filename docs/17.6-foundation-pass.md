## Scope interview (2026-11-07)

Corey answered a Codex interview, then follow-up questions from Claude Code while
PR #874 was reviewed. The questions are summarized; the answers are verbatim.

1. What is the phase for, and what does it cover?
   - "I think it's time to make sure the repos foundation a solid before building more on top of it. And I have a specific list of concerns you can probe me for that will be fairly standard for this "cleanup" phase of development where there is feature freeze and the focus is on stabilizing the quality and maintainability of the project (a separate set of concerns and even something I consider pushes addressing irrelevent defect work outside of)."
   - "stream of consciousness, dead code, overly verbose comments, stale comments, innacurate comments, comments that over share what was learned, mistakes, bad directions, or way things could go wrong or once were, instead of being explicit and concise about what is right and why. duplicated code, code that should be used as abstractions, behavior controlled through awkward flags that are out of band of a more appropriate existing or needed mechanism. Stale information in documentation. Innacurate or conflicting details. Verbatim captures of requirements that may conflict or be stale where my understanding or other human contributors may have evolved as the project and or our preferences have changed. Maybe those sources should be archived and more formal expressions of the requirements put in their place where they seem presently stable. Documentation that has grown too long and needs to be split out into their own files. Documentation that is misplaced or needs to be redistributed. Documentation that serve as multiple sources of truth for things that need to be maintained. Architectural needs that should be addressed because we haven't seen the forest for the trees. Optimization opportunities. Code that needs to be reorganized. Concerns that aren't properly separated. Overly coupled code. Code files that have gotten to large. Issues with names being ambiguous or easy to conflate. Code files that don't have a real identity to what scope they cover. Making the README presentable for multiple audiences, perhaps subdividing it, as there are different stakeholders both for my private workflow, external contributors through GH, consumers that wish to run the game, consumers that wish to author content for the game using the tools, consumers that wish to fork the project to take it in their own direction, using it as a foundation / starting point for their own vision."
2. Does a defect enter the pass only when it blocks foundation work or its acceptance?
   - "Yes"
3. Preserve older verbatim captures as archived history, making only reconfirmed requirements normative?
   - "yes"
4. Should the pass preserve observable behavior by default?
   - "Behavior changes are allowed on a case by case basis. They're implicitly approved if they are required for an approved rework, especially structural or architectural changes that have been approved for the foundation. However, the intent is that we are intending to preserve the functional / behavioral state as much as possible, while preparing for the next set of features."
5. Whole-project view of foundational gaps, or only visible issues?
   - "Yes, there is an intent to take a holistic view of the project and foreseeable work. It is often difficult to weigh the value of a clear improvement that reduces optionality against that cost of that optionality, which is why optimization opportunities are investigative. We want to surface potential optimizations and characterize their costs and implications. We want to maintain optionality. Separate from that though, with work that is clearly slated, or largely unambiguous to infer, we should look to prepare foundations to support that work, although that is not license to create a new system layer. Rather, it is license to surface its need and slate the work as an issue."
   - "Let's just say clear slated foreseeable work either because it is explicit or patently inferrable is sourced from the project documentation and issue tracker system"
6. Are file size, duplication and awkward flags signals rather than targets?
   - "Yes. They are smells to be investigated and addressed, and if necessary, some local documentation explaining why they don't use a clear alternative, if there is one."
   - "And a large file tends to be a smell. If a file is monolithic, then it may be covering behavior that is not properly decomposed into compositions of narrower concerns."
7. Shared abstractions for repeated behavior; which README audiences are first-class?
   - "I believe some should be secondary audiences routed to their own guidance so the main readme in the repo is a concise presentation of what the project is, who it is for, and how to get started, with first class audiences having quick start information and quick start for secondary audiences directed to their respective documentation. And yes to your question about duplicated code, although coincidental similarities may still suggest there is something to extract into general utilities for the project or the subsystem."
8. Which audiences get a quick start in the README itself?
   - "People who want to run the game, both as a host, and as a client. A basic run down of the rules. Screenshots and videos capturing what the game looks like both as a game and editor / lab. A general run down on the architecture and repository structure and basic development guidance. Contribution guidance (while presently not accepting contribution). And a brief synopsis of the games current state and roadmap."
   - On keeping detailed controls, the lab catalog, verification commands and the repository tree in dedicated guides: "yes exactly"
   - "I assume those guides, unless more appropriately directed to the docs/ structure, would be README.<subject>.md files"
9. Should active docs and comments state the current contract, keeping history only where it explains a decision?
   - "Yes for the README level, we are expressing what is."
   - "We've been moving it to archive as time goes on and things stabilize or solidify. I guess as things crystalize around a decision, the friction in changing it can help alleviate needing to ward off compulsions to change it by going down paths we've already ruled out."
10. Should an optimization investigation end with a recommendation weighing benefit, cost, optionality and what would change it?
    - "yes"
11. Keep comments that explain invariants or rationale; trim those that restate code or recount history?
    - "recount history yes. Restate code... if a comment is declaring what the bahavior is / should be, no don't remove that. It gives functions and classes and structures their identity. There's subtle discretion here. Don't remove things that help secure what a coding construct is supposed to be (making mutation an explicit change to the comment as well). But if it adds nothing but an explaination of what is patent, yes it can be removed. And yes keep non-obvious invariants or design rationale in place, just ditch recounting development history and warnings from that experienced history. Be explicit about what it's supposed to be, and if it helps why it's right, but archive the conffessionals."
12. One authoritative home per maintained fact?
    - "Yes. We prefer single sources of truth across code and documentation. Where duplication is warranted, back reference the source of truth."
13. Behavior behind awkward flags?
    - "I think we'll let AI discretion and case by case analysis handle that."
14. Are tests and verification tooling in scope?
    - "That's absolutely in scope and I knew I forgot something. I'd make that another track of concern. That would make it track 6 I believe after project entry points."
    - "yes. And let me do some stream of consciousness on this track. There's a time cost versus value consideration. Looking for superfluous tests. "dead" tests that pass but don't validate anything of concern anymore. Test granularity. Shared test resources. Tests that technically cover multiple validations or can cover multiple at once, especially if they have a large setup. Cached resources that could serve as setup for other tests. And of course incorrect tests. Tests that don't do what they say they do. Surfacing potential coverage gaps. and yea redundant checks, tests we don't understand the purpose of anymore. Tests that should be decomposed, or tests that could be joined. Tests that are heavier than the thing their validating needs ("lazily" written essentially). Splitting test sets up into more groups or sub groups to help an agent iterating run subsets of concern without paying the cost of unnecessary tests. And yea as I said in the beginning test cost versus value is a clear concern, while deeply subjective. But I think some cases are patent one way or the other, and others need to be surfaced for human discretion."
15. Coverage gaps outside approved work go to separate triage, prioritizing contracts the pass changes?
    - "yes"
16. Does the dead-code review cover tests, scripts and developer tools?
    - "yes"
17. Where does the charter live?
    - "While this might be something I want to turn into a "skill" generically for agents, I think we want to just incorporate it into the project documentation for now as a new subdocument in the appropriate place."
18. Should the charter state a feature freeze?
    - "An intent and assumption that there is a freeze. Feature and defect work may be brought in at human discretion, but the intention is for human management to hold space for the foundation pass to work from a stable place. We should not mention any specific tickets in 33.1. It is supposed to describe what a foundation pass entails to guide agents in effecting it. It is something we expect to do periodically, and while the charter may be slightly tailored to the current workflow and project, the closer we can make it to being something you could drop into any project repository the better."
19. What ends a pass? Corey chose: every track swept, every finding fixed, filed or declined with a reason, then the human declares it closed.
20. Where do superseded captures go?
    - "Are you sure there is no precedent for archived content in the docs/ tree? We're looking to reduce context here so moving it out to docs/archive/ I think is a good idea. Whether it is referenced in its original location or not I think would be at the agent's discretion, if unsure, ask human."
21. How does a behavior change required by an approved rework land? Corey chose: in the same pull request as its own commit, after the behavior-preserving steps, named in the description, with its version and fixture decisions under [31](31-verification.md).
