# 42.48. Input spend policies under latency, jitter and loss (#1096)

Up: [42](42-performance-history.md). Rules under test: [24](24-networking-privacy.md)
(client authority, lag compensation), [29.2](29.2-physics-state-networking.md) (exact
restore), [22.1](22.1-shared-simulation.md). This is a model of the input path, not a live
measurement and not a protocol change. Accepted background and the binary-input
boundary: [24.1](24.1-wire-encoding-design.md), #1093 closeout on #1096.

Reproduce: `node tests/bench-input-timing.mjs --seconds=600` (about a second, no physics, no
machine lock; seed 1096, 8 clients per cell, 20 Hz). Node v24.15.0, 2026-11-16.

## What is modelled

Each client sends one input per tick on a free-running clock. One-way time is `rtt/2` plus an
exponential jitter. Profiles (rtt ms / mean jitter ms / loss): lan 4/1/0, good 40/4/0.2%,
typical 80/12/1%, wifi 120/35/3%, poor 220/70/5%. Two transports: a **reliable ordered
socket** (today's WebSocket; a loss holds every later packet for `max(200, 1.5 rtt)` ms) and
**unreliable datagrams** (real loss, reordering; what #1095 would add).

- **A** is today's queue: the real `queueInput`/`consumeInput` (`shared/simulation/input.ts`).
- **B** is tick-stamped input with a server jitter buffer (#1096 option 1, or option 3 with
  rewind kept for hits). The client stamps an input with the server tick it expects to arrive
  by plus a lead; the lead rises by one on any late input and falls after 20 inputs with margin
  of two or more. The estimate is the minimum of the last 20 one-way times (the shape of the
  server's ping figure, 24). Late inputs are discarded, never rewound; a stamp more than 10
  ticks ahead is refused; stamps are monotone so one tick spends at most one input.
- **C** is delayed sealing (option 2): stamps with lead zero, a late input inside window `W`
  forces a resimulation from its tick. Only the resimulation load is modelled, from
  [42.22](42.22-tick-cost-attribution.md) tick costs.

Limits: the client learns each arrival instantly (a real client learns it a round trip later,
so B's adaptation is optimistic); no clock drift or time-sync error; symmetric paths; no
physics, so no divergence between prediction and server is measured, only when and whether an
input is spent.

## Findings

**1. The arrival queue never drains.** Send and consume rates are equal, so a burst leaves the
queue deep for good (`MAX_DEPTH` is 4, trimmed oldest first). On a reliable socket one
retransmission stall pins the mean depth near the cap:

| profile (reliable socket) | spend delay mean / p95 ms | mean depth | starved ticks |
| --- | --- | --- | --- |
| lan | 35 / 60 | 1.26 | 0.0% |
| good (0.2% loss) | 194 / 215 | 3.90 | 0.2% |
| typical | 215 / 237 | 3.68 | 1.2% |
| wifi | 240 / 275 | 3.04 | 4.9% |
| poor | 332 / 466 | 2.20 | 21.8% |

LAN matches the existing 24 observation (one input in flight, no stalls). On the other links the
queue holds roughly 140 to 170 ms more input than the network needs. This is the strongest
defect found; its effect on corrections is not measured here (no physics).

**2. The sequence guard fails on datagrams.** Over unreliable datagrams the queue rejects
inputs that arrive after a newer one (`input.seq <= receivedSeq`): 0.8% typical, 11.8% wifi,
24.4% poor, on top of real loss. Either transport change needs redundancy (resend the last
few inputs per datagram) or a different admission rule; the arrival queue alone cannot move to
datagrams.

**3. B turns lateness into a bounded, explicit cost; it is not cheaper.** B's spend delay is
higher than A's on the same link because it buys a margin that A does not:

| profile | A reliable | B reliable | A datagram | B datagram | starved A / B (datagram) |
| --- | --- | --- | --- | --- | --- |
| good | 194 | 237 | 69 | 83 | 0.2% / 0.2% |
| typical | 215 | 274 | 107 | 167 | 1.7% / 1.0% |
| wifi | 240 | 365 | 131 | 284 | 14.7% / 3.2% |
| poor | 332 | 641 | 190 | 468 | 29.3% / 5.6% |

Mean spend delay, ms. B's late-discard rate stays at or below 0.3% up to wifi and 0.8% on poor.
B pays for the margin; A pays with starved ticks (a repeated input, then a correction). Lead is
a tunable: B's target here is near zero discards, and a looser target would sit between the two.
B on a reliable socket is no better than A because the retransmission stall, not the jitter
buffer, sets the floor: it needs datagrams (#1095) to pay off.

**4. C is not affordable at the sizes that matter, and not needed.** With lead zero, any jitter
makes an input late. Share of ticks that resimulate (8 clients, window 4 = 200 ms): good 8%,
typical 51%, wifi 78%, poor 56%. Ticks that exceed the 50 ms budget:

| profile (window 4) | @7.4 ms (12x6) | @17.8 ms (24x12) | @34 ms (36x18) |
| --- | --- | --- | --- |
| good | 0.0% | 1.7% | 8.2% |
| typical | 0.0% | 8.8% | 50.9% |
| wifi | 0.0% | 40.7% | 78.4% |
| poor | 0.0% | 44.9% | 55.9% |

At 12x6 only an 8-tick window goes over budget, on wifi (0.9%) and poor (9.3%). Correction to the
issue's arithmetic: the "about 7 ms per tick" figure is 12x6; 36x18 is about 34 ms (42.22), so a
200 ms window is about 136 ms of resimulation per late input, not 28. C also needs exact
Rapier snapshot and restore, which 29.2 marks unsupported in production, would reverse outcomes
other players have seen, and would restrict recordings to sealed ticks. Resimulation cost
grows with players and size; the jitter buffer in B costs nothing in CPU.

## Recommendation (for Corey)

1. **Do not build delayed sealing with resimulation.** It is unaffordable at 24x12 and above,
   rests on an unsupported engine capability and changes what other players see after the fact.
2. **Adopt option 3 when #1095 (datagram transport) lands:** tick-stamped inputs, a jitter
   buffer with a bounded adaptive lead, late input discarded, one input per tick and the
   sequence ordering kept, and the existing hit rewind unchanged. Pair it with redundant
   inputs per datagram and a decoder limit (the binary-input boundary #1093 left here).
3. **Separately and sooner, change nothing on the wire:** the queue never draining (finding 1)
   is a server-side defect worth a small reviewed change, such as trimming to a target depth
   after a burst. It would be measured here first and would need the fixed-tick order and
   replay compatibility checks in AGENTS.md.
4. **Bound claimed ticks by measured latency.** In B a claimed past is never honoured, so the
   rewind cheat in #1096's constraints does not arise; a claimed future is bounded by the 10 tick
   cap. This matters only if a later design honours past stamps.

Open for Corey: the lead's target discard rate, which is a feel decision (1 to 3 ticks of extra
delay against a few percent of corrections), and whether the queue-drain change (3) goes ahead
before #1095.
