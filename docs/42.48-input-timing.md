# 42.48. Input spend policies under latency, jitter and loss (#1096)

Up: [42](42-performance-history.md). Rules under test: [24](24-networking-privacy.md)
(client authority, lag compensation), [29.2](29.2-physics-state-networking.md) (exact
restore), [22.1](22.1-shared-simulation.md). This is a model of the input path, not a live
measurement and not a protocol change. Accepted background and the binary-input
boundary: [24.1](24.1-wire-encoding-design.md), #1093 closeout on #1096.

Reproduce: `node tests/bench-input-timing.mjs --seconds=600` (about seven seconds, no physics,
no machine lock; seed 1096, 8 clients per cell, 20 Hz, first 10 s discarded). Node v24.15.0,
2026-11-16. Section R, [the implementation](#the-implementation-1096), was added after Corey's
decision; A, B and C are unchanged.

## What is modelled

One-way time is `rtt/2` plus an exponential jitter, drawn per input and independent of when it
is sent. Profiles (rtt ms / mean jitter ms / loss): lan 4/1/0, good 40/4/0.2%, typical
80/12/1%, wifi 120/35/3%, poor 220/70/5%. Two transports: a **reliable ordered socket**
(today's WebSocket; a loss holds that packet and every later one for `max(200, 1.5 rtt)` ms)
and **unreliable datagrams** (real loss, reordering; what #1095 would add).

- **A** is today's queue: the real `queueInput`/`consumeInput` (`shared/simulation/input.ts`),
  the client sending on a free-running 20 Hz clock.
- **B** is tick-stamped input with a server jitter buffer (#1096 option 1, or option 3 with
  rewind kept for hits). Input `k` is stamped `stamp0 + k`, so one tick spends at most one input
  and sequence order is kept. Each acknowledgement reaches the client a return trip after the
  tick it arrived for, and reports the input's margin: how many whole ticks before its stamp it
  arrived. The client adjusts its **send rate** (time dilation): 10% faster while any of the last
  three margins is late or the minimum of the last 20 is below the target margin, 5% slower
  while the minimum of a full 20 exceeds the target, otherwise exactly the tick rate. Late inputs
  are discarded, never rewound; a stamp more than 10 ticks ahead is refused.
- **C** is delayed sealing (option 2): B's client and stamps at the same target, but a late input
  inside window `W` is applied by resimulating from its tick instead of being discarded. Only the
  resimulation load is modelled.

**C's cost baseline** is 42.22's 2026-11-09 multi-room check (main `a837cc0`, content-7, 36x18,
whole matches, 8 clients plus a spectator per room, recording on), upper end of each range:
one room's simulation alone, 3.7 ms (tick mean 7.70 less `loop.broadcast` 3.68 and
`loop.record` 0.33); one room's whole tick, 7.7 ms; two rooms on one loop, 16.1 ms. A
resimulated tick re-runs the simulation, not broadcast or recording, so the first is the closest
estimate; the others bound it. Restore cost is not included, because no production exact
restore exists (29.2). 42.22's earlier #637 figures (about 34 ms at 36x18) predate the
optimizations recorded later in that document and are not used.

**Limits.** The stamp origin comes from a time-sync estimate (the best of the first 20 one-way times), not input 0, which a datagram link may lose. No clock drift or time-sync error; symmetric paths; margins are whole ticks, so B
settles anywhere within one tick of its target (a deterministic check, below, settles 23 ms later
than its start); no physics, so prediction divergence is not measured, only when and whether an
input is spent.

## Findings

**1. Today's queue never drains on a lossy reliable socket.** Send and consume rates are equal,
so the backlog a retransmission stall leaves is never spent down (`MAX_DEPTH` 4, trimmed
oldest first):

| profile (reliable socket) | spend delay mean / p95 ms | mean depth | starved ticks |
| --- | --- | --- | --- |
| lan | 39 / 60 | 1.32 | 0.0% |
| good (0.2% loss) | 195 / 216 | 3.94 | 0.2% |
| typical | 220 / 239 | 3.72 | 1.1% |
| wifi | 244 / 276 | 3.10 | 4.7% |
| poor | 331 / 465 | 2.19 | 21.9% |

LAN matches the existing 24 observation (one input in flight, no stalls). On the other links the
queue holds roughly 140 to 180 ms more input than the network needs. This is the strongest defect
found; its effect on corrections is not measured here.

**2. The sequence guard fails on datagrams.** The queue rejects any input arriving after a newer
one (`input.seq <= receivedSeq`): 0.8% typical, 11.6% wifi, 24.4% poor, on top of real loss.
Moving to datagrams needs redundancy (the last few inputs in each datagram) or a different
admission rule; the arrival queue alone cannot move.

**3. B with time dilation removes the backlog and trades delay for starvation explicitly.**
A deterministic check (20 ms each way, one 275 ms stall on a reliable socket) shows the offset
rising during the stall and returning within about 50 ticks (2.5 s); target 0 settles at 63 ms
spend delay against 40 ms before the stall, the sub-tick slack from whole-tick margins. The
model without rate control kept the added five ticks forever (review on PR #1132); it is not
used. Mean spend delay in ms, starved ticks in brackets:

| profile | A reliable | B reliable, target 0 / 1 | A datagram | B datagram, target 0 / 1 |
| --- | --- | --- | --- | --- |
| good | 195 (0.2%) | 75 (0.7%) / 125 (0.5%) | 71 (0.2%) | 69 (0.2%) / 119 (0.2%) |
| typical | 220 (1.1%) | 155 (2.7%) / 205 (1.5%) | 108 (1.8%) | 118 (1.5%) / 168 (1.0%) |
| wifi | 244 (4.7%) | 296 (2.9%) / 345 (1.1%) | 132 (14.5%) | 235 (4.4%) / 284 (3.3%) |
| poor | 331 (21.9%) | 549 (5.1%) / 594 (5.9%) | 190 (29.4%) | 423 (6.7%) / 472 (6.0%) |

B's late-discard rate is at most 2.9% up to wifi at target 0 and at most 1.5% at target 1. On
good and typical reliable links B is both faster than today's queue and comparably steady, so
it does not depend on #1095. On wifi and poor links B is slower because it holds a margin for
the jitter tail, where A starves instead; the target is the tuning knob between them. Each
target step costs one tick (50 ms). On a poor reliable socket the 10-tick lead cap refuses 1–10% of stamps (the lead must cover
a 330 ms retransmission stall); on poor datagrams, at most 1%. A constant cap is too tight for the
stall case and would need to follow the measured latency.

**4. C's resimulation is affordable for one room; its gain is small.** With a 4-tick (200 ms)
window and 8 clients, 1.6% (good) to 14% (poor) of ticks resimulate, mostly one or two ticks.
Ticks over the 50 ms budget:

| profile, window 4 | target | 1 room, sim only | 1 room, whole tick | 2 rooms on one loop |
| --- | --- | --- | --- | --- |
| good | 0 | 0.0% | 0.0% | 1.5% |
| typical | 0 | 0.0% | 0.0% | 4.5% |
| wifi | 0 | 0.0% | 0.0% | 2.0% |
| poor | 0 | 0.0% | 0.0% | 4.2% |
| typical | 1 | 0.0% | 0.0% | 1.2% |

CPU is therefore not the decisive objection for one room per loop. It grows with rooms per
loop and size, and the deepest resimulations (p99 4–7 ticks) collide with the cold-tick and
route-planning spikes 42.22 already records. What C buys over B is the inputs B discards:
0.7–3.9% per client at target 0, 0.5–2.0% at target 1. Its costs stand independently of CPU:
exact Rapier snapshot and restore, which 29.2 marks unsupported in production; outcomes other
players have already seen being reversed; and recordings that may write only sealed ticks.

Correction to the first revision of this document: the issue's "about 7 ms per tick at 36x18"
is consistent with 42.22's #728 measurement (6.66–6.87 ms, one bot-seat view); it is not a size
mix-up.

## The implementation (#1096)

Corey chose option 1 with option 3's stamp bound ([17.4](17.4-live-service.md) #16), and it is
built ([24](24-networking-privacy.md#tick-stamped-input)). The bench's section R runs the real client
clock (`shared/input-clock.ts`) and the real buffer (`shared/simulation/input.ts`) over the same seeded
networks as A, with feedback as the server sends it: each frame carries the worst margin among the
inputs that arrived before its tick, and takes the network's return delay. The lead bound is
`inputLeadFrom(rtt)` with the profile's round trip as the measurement. Reliable ordered socket:

| profile | A spend delay (starved) | R target 0: spend delay mean / p95 (starved, late, over cap) | R target 1 |
| --- | --- | --- | --- |
| lan | 39 (0.0%) | 36 / 50 (0.0%, 0.0%, 0.0%) | 86 / 100 (0.0%, 0.0%, 0.0%) |
| good | 195 (0.2%) | 78 / 151 (0.7%, 0.7%, 0.0%) | 128 / 201 (0.5%, 0.5%, 0.0%) |
| typical | 220 (1.1%) | 180 / 314 (2.3%, 2.3%, 0.0%) | 230 / 364 (1.2%, 1.2%, 0.0%) |
| wifi | 244 (4.7%) | 343 / 485 (1.8%, 1.8%, 0.0%) | 393 / 534 (0.6%, 0.6%, 0.0%) |
| poor | 331 (21.9%) | 674 / 912 (1.6%, 1.6%, 0.1%) | 723 / 963 (1.0%, 0.8%, 0.2%) |

- **Against the model.** Good and typical links match B within a few milliseconds and tenths of a
  percent. On wifi and poor links R holds one to three ticks more than B (393 against 345 ms, 723
  against 594 ms at target 1) and discards about half as much (0.6% against 1.1%, 0.8% against
  2.0%). The difference is the feedback: B steered by every input's margin, R by each tick's worst,
  which is more cautious. Two clock rules were measured and changed on the way. Stepping back when
  six ticks ahead of the time-sync estimate made wifi and poor links discard 13% and 55% of
  inputs, because the estimate is optimistic and those links need more lead; the clock now steps
  back only beyond what any server buffers (a new map's ticks), and leaves being too far ahead to
  the dilation. Jumping forward when certainly late changed nothing measurable and stays, for the
  ticks a player was not active.
- **The lead bound.** At twice the round trip plus 4 ticks, poor links overran it on 2.1% (target
  0) and 4.8% (target 1) of ticks, and starved 3.9–5.6%; at three round trips, 0.1–0.2%, starving
  1.0–1.6%, for 14–16 ms more delay. Three is what is built: 7 ticks on lan and good, 10 typical,
  13 wifi, 19 poor, at most 28.
- **Against today.** On today's socket the stamped buffer spends a good link's input sooner than the
  arrival-order queue (128 against 195 ms) and starves far fewer ticks on wifi and poor links
  (0.6% and 1.0% against 4.7% and 21.9%), but holds more delay there (393 and 723 against 244 and
  331 ms): the margin for the jitter tail and the retransmission stall, which the queue spent as
  starvation instead. The target margin trades between them, 50 ms a step.
- **Datagrams.** R on datagrams starves 15% (wifi) and 30% (poor) of ticks, half of it inputs the
  sequence guard refuses because a newer one overtook them (finding 2). Datagrams stay #1095's,
  with redundant inputs per packet.

**Prediction.** `tools/physics/prediction-network.mjs` now stamps with the real clock on its fixed
send schedule (so dilation is not exercised there). Against main at `8688632a`: pre-correction
error p99 is 0 on every network profile, as before; the hidden-contact and stale-door profiles keep
their deliberate 5.06 and 5.63 units. The prediction now runs one tick further ahead of authority
in every profile (9 units at this speed): the target margin. The burst-and-stall profile mispredicts
for the first time (p99 5.63): inputs sent during its 360 ms stall reach the server late and are
discarded, which prediction cannot know until the next frame. Two predictor fixes came out of this
check: a cut must not forget inputs the server will still spend, and a replayed gap must stop
repeating when the server's repeat does (10 ticks).

## Recommendation (for Corey)

1. **Adopt option 3**: tick-stamped inputs, a server jitter buffer, client time dilation toward a
   target margin, late input discarded, one input per tick and sequence order kept, the existing
   hit rewind unchanged. It removes finding 1 on today's socket and is the shape #1095 needs.
   On datagrams, pair it with redundant inputs per datagram and a decoder limit (the
   binary-input boundary #1093 left here).
2. **Do not build delayed sealing now.** One room's CPU would allow it, but it recovers only the
   0.5–4% of inputs option 3 discards, at the price of an unsupported engine capability, visible
   reversals and a recording change. Revisit only if discarded inputs prove noticeable in play.
3. **If option 3 waits, a smaller interim fix is possible:** trim the queue to a target depth
   after a burst. It would be measured here first and would need the fixed-tick order and replay
   compatibility checks in AGENTS.md.
4. **Bound stamps by measured latency.** Option 3 never honours a claimed past, so the rewind
   cheat in #1096's constraints does not arise; the lead cap should follow the server's measured
   round trip (24) rather than a constant, so a poor reliable link's stall is not refused.

Decided 2026-11-16 ([17.4](17.4-live-service.md) #16): option 1 built with option 3's stamp bound
(4), no delayed sealing (2), target margin 1 tick as a tunable default, and no interim fix (3).
