## What exists

One Node process does everything. Since #252, `server/room-directory.js` owns room
creation, the cap, matchmaking and the room list; `server/room-service.js`
([22.3](22.3-server.md)) owns admission, sessions, the start countdown, tick debt and
lifecycle; `server/match.js` owns the simulation. A "lobby" is a room that has not
started: its map is generated when the room is created, and every slot already holds a
bot that a joining player takes over. That is why the lobby looks pre-generated with
players already placed (#213). Rooms have no names, and the client does not list them yet
(`GET /api/rooms` exists for #254): you reach one by its link, by matchmaking, or by
creating it. Matchmaking (14) looks only at
unstarted matchmade rooms in this process. At most eight rooms run at once (28). Since
#253 the map is generated on a worker thread, so other rooms keep ticking meanwhile, and
since #258 the room and its link exist at once: players wait in its lobby, which says the
arena is generating, and the start waits for the map. Generation varies widely by seed:
2 to 6 s was measured at 24 × 12 and 36 × 18 (#184), and one 36 × 18 seed took about
28 s (42).

## How lobby-based games are usually arranged

#237 asks whether this is how real games are set up, and whether the parts are separate
processes or threads. Usually three jobs are kept apart. They need not be three programs.

- **Matchmaking and lobbies** (sometimes called the directory or the lobby service): who
  is looking for a game, parties and named lobbies, and which room each player is sent
  to. It holds no simulation. It is typically a stateless web service in front of a
  shared store, so it can run as several copies.
- **Allocation**: handing out a game server for a match and reclaiming it afterwards.
  Hosted products do this job (Agones on Kubernetes, AWS GameLift, Hathora, Edgegap);
  small games often have the matchmaker start processes itself.
- **Game servers**: the authoritative simulation. Engines built around heavy dedicated
  servers (Unreal, Unity) usually run one process per match. Lightweight room frameworks
  (Colyseus, Photon, Nakama) run many rooms in one process and scale by adding
  processes, with a shared store recording which process holds which room.

Threads are rarely the unit. A Node process runs its rooms on one event loop, so a slow
room delays the others (map generation did exactly that until #253 moved it to a
worker). Scaling means more processes, and worker threads help only for isolated CPU
jobs like generation.

The pre-game "lobby map" in battle royales such as Zombs Royale or Fortnite is, as far
as is publicly known, a warm-up phase on the match's own server: players arrive in the
match before it starts. It is not a separate lobby server. Matchmaking has already put
them in that match.

## Shape for this game

This game's rooms are light: twenty ticks a second of a 2-D simulation, about a dozen
players. That suits the many-rooms-per-process model, which is also the shape the
netcode was built for (a Colyseus-style room). So:

1. **Directory** (new): the list of rooms with a public summary of each (id, optional
   name, kind, phase, size, player count by role, created time), room creation, and
   matchmaking, meaning choosing a room for a player or creating one. It answers with a
   room id, and later an address. It never touches a match.
2. **Room** (today's room-service, minus matchmaking): admission into one room, the
   pre-start phase (roster, roles and kits, the countdown, and the waiting map if #236
   goes ahead), then the match, recording and finish. One room host runs many rooms.
3. **Match** (`server/match.js`, unchanged): the simulation.

The roadmap's rule stands (41): do not build a service registry or split processes
before something needs them. Every stage below runs in one process. The directory is a
module boundary with the contract a network service would have: summaries are plain
data, and joining is "here is a room id; connect to it". Splitting it into its own
process later then means moving code, not redesigning it. Your 17.4 #2 answer ("the
lobby server and then there are the spawned game server") is that later shape, and it
is where a client reconnecting to a new server version would update.

### Kinds of room

| Kind | Created by | Listed | Starts |
| --- | --- | --- | --- |
| Private | `POST /api/rooms` (the deploy dialog) | Only if it is given a name (17.4 #9) | Owner presses start |
| Matchmade | The directory, for "find a match" | Yes, while it is filling | 15 s after the first join, bots fill the rest |
| Dev | A dev tools policy that allows it (24) | Only to sessions that policy admits | As private |

A named room is a private room with a name, which makes it findable rather than only
reachable by link. "Auto" in the browser is matchmaking.

### Lobby browser

The deploy dialog gains a list of open rooms from `GET /api/rooms`: name or id, size,
phase and players by role, with **Join** (choosing a role where the room allows it, see
#235) and, under a dev tools policy, **Dev view** for any room including live ones. The
"find a match" checkbox becomes the browser's Auto button. Rooms that have finished
leave the list. The list is polled, about every 2 s while the dialog is open, so the
directory has no push channel to maintain.

### Before the match starts

#235 (choosing a role and kit in the lobby) and #236 (a waiting map) both belong to the
room's pre-start phase, not to the directory. Two consequences:

- Generating the real map overlaps that phase (#253, #258): the room is joinable at once
  and starts only when the map is ready, so players wait in the lobby rather than for the
  room to exist. Recording still begins at the start, from the generated map, so replays
  and the frozen fixture are unaffected ([22.3](22.3-server.md) has how seats taken
  before the map are carried into the match).
- A waiting map, if wanted, is a separate small simulation the room runs until the start,
  with movement only. It is never recorded and never shares IDs or RNG with the match,
  so determinism is untouched; at the start, players move into the match's own spawns.
  What players can do there is open (17.3 #15).

## Stages

Each stage is an issue.

1. **Room directory** (#252; no product decisions needed). Done: `server/room-directory.js`
   ([22.3](22.3-server.md)) owns the cap, creation and matchmaking, and `GET /api/rooms`
   returns public summaries. There is no separate dev kind yet, so, pending 17.4 #9, the
   list shows matchmade rooms still filling to everyone, and every open room (private and
   live too) when `DEV_TOOLS=all`, since that policy already admits anyone to any room's
   dev view. Under `owner` admission needs a room's key, which a listing request lacks.
   Optional room names wait on 17.4 #9.
2. **Generate the map off the event loop** (no product decisions needed). Done: #253
   runs live map generation on a worker thread, so other rooms no longer stall (42), and
   #258 creates the room at once, admits players while the map generates, and starts only
   once it is ready. Summaries carry `ready`.
3. **Lobby browser** (#254; after 1; names wait on 17.4 #9): the list, Join, Dev view and Auto
   in the deploy dialog.
4. **Role and kit in the lobby** (#235; waits on 17.3 #14).
5. **Waiting map** (#236; waits on 17.3 #15, after #258).
6. **Separate processes** (deferred until hosting; 17.4 #1–#2): the directory as its own
   service, room hosts as processes it allocates, a shared store for summaries, and
   addresses in join answers. Not filed as an issue until deployment is planned.
