# 42.68. The drop planner's spiral search in the Rust core (#1228)

Up: [42](42-performance-history.md). Design: [27](27-rust-path.md#the-state-flip), step 5c.1. The work is
`rust/core/src/scatter.rs`, driven by `scatterInCore` in `shared/simulation/boundary.ts`. `characterization-physics`,
its `-bots` variant and `tests/tick-phases.test.js` passed unchanged.

## Finding

**A search costs about 2.2 µs more in the core than it did in TypeScript, but a match makes only a handful, so the
tick does not change.** The relative figure is over 42.58's 10%; the step is within
[42.58's state-flip exception](42.58-sight-core-adapter.md#the-budget).

| 24x12, seed 4217, 330 real drop origins | TypeScript (before #1228) | Core |
| --- | ---: | ---: |
| One search, median of 7 rounds, three runs | 2.80–2.88 µs | 4.97–5.20 µs |
| Searches in one whole bot match (8,564 ticks) | 7 | 7 |
| Added cost per tick, averaged over that match | — | about 0.002 µs |

- **The relative budget.** The crossing adds about 77% to a search. The search is short: on these origins it tests
  1.2 spots on average, because a dropper usually stands in the open. The crossing's fixed costs are therefore most of
  it:
  - the open-gate mask, written once a call (about 0.55 µs for 421 gates, 42.66);
  - the ground records within the spiral's reach, packed once (`itemsNear` at 405: 0.44 µs, against 0.18 µs for the
    TypeScript's one query at 32 per spot);
  - the actors' disks, and the input and output views.
- **The exception holds.** The packed state is JavaScript's (the ground and the actors), and the callers are the game's
  own records, so no flat view helps. Even a tick that made a search would pay about 0.05% of the mean tick (4.3 ms,
  42.67). Averaged over the match, the cost is about 0.00005% of the tick.
- **Where the search time goes.** On these origins, `canOccupy` is about 0.8 µs and `reachClear` about 0.9 µs in
  TypeScript. The prop query (`overlapsProp`) is about 0.25 µs, since nothing moves between searches.
- **Both answered all 330 identically.** None was refused.

## Method

- **Environment.** The development machine (Windows 11), Node 24, the core built with `npm run core:build`.
  2026-11-20, under the exclusive bench lock, with no other tests running.
- **The script** was ad hoc, not committed. It built the 24x12 live map for seed 4217 with the shipped content and its
  prebuilt tiles, called `createGame`, and stepped 600 bot ticks, taking a snapshot after each as a room does. Every 20
  ticks it took each active player's position as a drop origin, at the game's `scatterSerial`. The reference was the
  TypeScript search with `physicalDropPlacementClear`, as `tests/drop-scatter-core.test.js` keeps it. There were five
  warm-up passes, then seven rounds of 20 passes in alternating order; the run reports the median. Three runs.
- **The count** stepped a whole match on the same map with a temporary counter in `scatterInCore`, which was then removed.
- **A pitfall: snapshot each tick.** Without a snapshot no ground record is frozen. Every record then stays in the
  grid's loose list (`ground-items.ts`), and every `itemsNear` scans all 816 records, about 34 µs. That hid both
  searches' real costs behind a figure about 54 µs on each side.

## Limits

- **Node only.** The browser plans no drops.
- **One map and content.** Drops into crowded corners test more spots; there the core's queries, each about a quarter
  of the TypeScript's (42.66), would close the gap.
- **The stage is a leaf.** Once the phase 3 loop runs in the core (5c.2, #1238), its drops call the search with no
  crossing of their own, and the mask and the actors are already there.
