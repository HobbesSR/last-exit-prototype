# 42.51. Stock protobuf head-to-head with the descriptor codec (#1130)

Up: [42](42-performance-history.md). Earlier comparison: [42.49](42.49-wire-codec-selection.md).
Accepted direction: [24.1](24.1-wire-encoding-design.md). Corey asked for protobuf to be pursued
alongside D until either is clearly shown not to be viable (#1130, comment 15345), and then chose
to measure stock protobuf head-to-head against D before deciding on combining them
([17.4](17.4-live-service.md) #17). Scope, budgets and stop rules were posted on #1130 (comment
15382) before any measurement. Nothing live changed: no protocol, `WIRE_VERSION`, simulation,
recording or fixture.

## Finding

**Shaped for it, stock protobuf is viable, and D leads on every measured axis.** The binary
encoding is meant to move the wire away from JSON-shaped data, so the comparison that answers
Corey's test (comment 15382) is the library-only one: objects already in protobuf's shape. Feeding
today's JSON-shaped projections through an adapter answers a question nobody is asking. An earlier
version of this finding judged protobuf on the adapter rows and called it not viable. Corey
corrected that reading in a session on 2026-11-16, recorded on #1130.

- **Natively shaped** (library-only), Pn is 26–29% larger than D (35–38% of JSON against 27–31%).
  - **CPU:** it meets the Node budgets (encode 0.73–1.17× JSON, decode 1.43–1.57×), against D's
    0.63–0.98× and 0.71–0.88×.
  - **Chrome decode** sits at the edge of the budget, at 1.74–2.07× against D's 1.05–1.15×, and
    allocates 1.5–2.3× what D's does.
  - **Footprint:** without the adapter, protobufjs' minimal runtime plus generated code is about
    16.7 KiB before the generated code is minified, against D's 8.7 KiB.
- **Pn's number oneofs are themselves a JSON habit.** Choosing integer, float32 or float64 per value
  is what brings Pn to 35–38% of JSON, smaller than M on contestant and gladiator views. But
  library-only, it also makes Pn's decode 2.2–2.6× slower than P64's in Node. A schema designed for
  protobuf would type each field once (for example `sint32` counters and `float` Rapier positions),
  with no oneof. **That case was not measured.** Splitting out 32-bit members (Pn32) made Pn neither
  smaller nor faster: the extra members push field numbers past 15, where tags take two bytes.
- **Behind today's projections** (with the adapter), protobuf fails budgets that D meets by more
  than 25%: Node encode, Node and Chrome decode, encode allocation and footprint. That measures the
  adapter, not protobuf.
- **P64** (every number a `double`) is larger than msgpackr (M) in every view, adapter or not, so it
  is not viable on bytes. Library-only, it is the fastest protobuf decoder (Node 0.55–0.73× JSON,
  Chrome 0.82–1.11×).
- **Semantics and safety are sound** once the frame carries a body length.
  - Every truncation and trailing byte is refused, crafted lengths are refused before allocation,
    and nesting is bounded.
  - Lone surrogates are refused explicitly on encode, as protobuf strings must be UTF-8. Budget 7
    allows an explicit refusal, but D preserves them.
  - Unknown fields are skipped silently. That is protobuf's compatibility rule, not a defect here.

**What protobuf would add** is a standard schema language, field numbers with unknown-field
skipping (old and new clients across a rolling deploy), generated code for other languages and a
specified wire format. None of these is needed by a current consumer: the browser and server share
one checked contract, and `WIRE_VERSION` refuses mismatches. They would matter for a native client,
for a Go or Rust transport gateway that decodes messages (#1095), or for external tools.

**Recommendation (for Corey's decision).** On the measured evidence D remains ahead for #1131's
per-tick state: about a fifth fewer bytes, faster client decode and half the footprint. Protobuf
stays viable, so per Corey's rule (comment 15345) it is not ruled out. A per-field-typed protobuf
schema is the unmeasured case that could narrow the gap, and it is the next measurement if
protobuf is to be pursued further. Corey asked for the two to stay separable. Two combinations
keep D's measured performance while doing so, and neither was designed or measured here:
1. **Protobuf as the schema source only.** The `.proto` file is the reviewed contract, carrying
   D's types (number narrowing, nullable, layers) as annotations, and D's descriptor is generated
   from it. This study generated protobuf from D's schema mechanically for the whole slice. The
   reverse direction would need D's types carried as annotations, and other languages would
   still need a D decoder.
2. **Protobuf wire for low-rate messages only**, such as welcome, lobby, replay index and map
   delivery, where compatibility and tooling matter more than bytes. That would mean two codecs to
   maintain.

## Candidates

All protobuf candidates use `protobufjs` 8.8.1 (light build, reflection with runtime codegen),
Edition 2023 semantics (explicit presence, packed repeated scalars, UTF-8 verified on decode) and
64-bit varints decoded to JS numbers.

- **One schema source.** The protobuf schema (a protobufjs JSON descriptor, 38 messages and
  enums) is generated mechanically from D's descriptor schema, `sliceSchema`. That schema takes
  its field names from the projection owners (42.49). No field list is written by hand, and field
  numbers follow declaration order.
- **The adapter.** Projections are JSON-shaped and protobuf's data model is not, so a generic
  adapter compiled from the same schema maps between them (`wire-protobuf-codec.mjs`, 205 lines
  against D's 273):
  - nullable values become a oneof with a null member;
  - an ID (string or number) becomes a oneof of a `string` and an `sint64`;
  - enums become proto enums;
  - a const takes no field and is restored on decode;
  - a union (the player list's observed/own records, body shapes) becomes a oneof of the variant
    messages;
  - list elements that need a oneof are wrapped in a message;
  - an optional list or map is wrapped in a message, because protobuf cannot tell an absent list
    from an empty one;
  - a frame-layer becomes a message with presence-carrying list wrappers.
  Decode returns plain objects without prototype defaults, and a missing required field refuses,
  as in D.
- **Framing** is format, schema version, message id and a varint body length. Protobuf has no end
  marker: a message cut at a field boundary, or with fields appended, is still a valid message.
  The first run without the length decoded four truncations of the `input` specimen without error.
- **P64:** every `num` is a `double`, the natural stock mapping.
- **Pn:** every `num` is a oneof of `sint64`, `float` and `double`, chosen per value exactly as D
  chooses. This is D's narrowing expressed in protobuf, and the best per-field typing could do.
- **Pn32:** as Pn, with additional `sint32` and `uint32` members. protobufjs decodes 64-bit
  varints through a slower long path, so this tests whether 32-bit members recover decode speed.
- **Library-only** rows encode objects already in protobuf's shape and decode without the
  back-transform. They show what protobuf would cost if the projections were rebuilt in its data
  model, which would be a protocol-wide change. **Adapter-only** rows time the encode-side
  transform alone.
- **Controls, re-measured in the same process:** JSON, D and msgpackr-provisioned (M).

Notes on the table:
- **Framing.** P's framing is 4 bytes for bodies under 128 bytes (ping, input) and 5 bytes for
  state messages, because of the body length. The transport already marks message boundaries, so
  the length is an integrity check rather than framing that would be missing otherwise. It is still
  counted.
- **Footprint.** The static figure is protobufjs' minimal runtime (8.5 KiB, minified) plus the
  generated encode/decode code (4.9 KiB for P64, 8.2 KiB for Pn) and the adapter (5.3 KiB). The
  generated code and the adapter are unminified, as is D's 8.7 KiB, and no minifier is installed.
  The light (reflection) build that this study ran is 24.1 KiB on its own. It also compiles code
  at run time with `new Function`, which a strict content security policy forbids. Production would
  therefore ship static generated code.
- **Pn32** is between Pn and P64 on every row and better on neither. Its bytes are 35–43% of JSON
  and its Node decode 2.97–3.92×.
- **Library-only Node allocation** was not sampled. Most of the full codec's allocation is the
  adapter's intermediate objects.

Against the stop rules posted with the budgets:
- **Pn shaped for protobuf (library-only) is viable.** It fails no CPU budget by more than 25%. The
  steady Chrome decode reaches 2.07× against 2×, and the footprint without the adapter is about
  16.7 KiB against 16 KiB, before the generated code is minified. Bytes, CPU, allocation and
  footprint all favour D.
- **P64 is not viable on bytes.** They are worse than M's in every view (45–48% against 34–47%).
- **Behind the adapter**, Pn fails budgets that D meets by more than 25%: Node encode by up to 90%,
  decode by 30–100%, encode allocation at 2.5–3.5 times its budget and footprint by 17–37%. This
  measures the conversion from JSON-shaped projections, which the move to binary is meant to
  remove.

## Semantics and malformed input

This is the #1130 suite (`wire-codec-safety.mjs`) on 10 real samples and the two specimens of each
size, with protobuf's own crafted inputs.

- **Exact** on every one of the 244 real samples per size, for all three forms, again with fresh
  codecs in shuffled order (732 checks per size). Specimens covered: nulls, omitted and `undefined`
  keys, ID types, -0, safe-integer limits, float64 extremes, float32 values, BOM, astral
  characters and `__proto__`/`constructor` map keys.
- **Lone surrogates** (8 specimens) are refused on encode. protobufjs 8 encodes them as invalid
  UTF-8 and then refuses that on decode (Edition 2023 verifies UTF-8), so the adapter refuses
  first. A production rule would refuse them where names enter, as M would also need.
- **Truncation:** every cut is refused, 15,302–19,107 cases per form, including the four cuts that
  decoded without the length.
- **Trailing bytes** are refused, and so are wrong format, version and type headers.
- **Crafted inputs:** 2^31 and 2^32 lengths are refused in at most 0.03 ms. 100,000 nested
  unknown start-groups hit protobufjs' recursion limit. 200,000 unknown fields are skipped in
  1.0–2.2 ms before the missing required field refuses. An empty `state` refuses, naming the
  missing required field.
- **Random corruption** (2,000 seeded cases): Pn throws on 82% and returns a different message on
  18%; P64 returns a different message on 38–39%; D on 22%. No case hangs, and the worst decode
  is 2.2 ms.
- **What protobuf accepts by design:** unknown fields are skipped, and a repeated singular field
  takes its last value. Both let a non-canonical encoding decode.

## Limits

- **One library.** Only protobufjs was measured. `@bufbuild/protobuf` (Apache-2.0/BSD-3) passes
  the protobuf conformance suite but is reflection-based, and is likely slower. Static generated
  code (`pbjs`) was not built; the reflection codegen stands in for it.
- **One mapping.** The adapter is generic and compiled from the schema, not hand-tuned per record,
  so a hand-written adapter could be faster. The library-only rows bound what any adapter could
  save.
- **Library-only is optimistic.** It assumes the projections already build protobuf-shaped objects
  at no cost. They do not, and reshaping them would change every projection owner.
- **42.49's limits apply:** the same players+bodies slice, bot traces, and no GC-pause, capacity or
  loss study. The capped-packing and quantized probes were not repeated.

## Workload and provenance

Measured 2026-11-16 on Windows with Node v24.15.0 and Chrome 157.0.8103.51, on an AMD Ryzen 9
5900X. Branch `claudecode/1130-protobuf` from `5fda8a0`. Both final runs were sequential under the
exclusive lock and uncontended (external busy 6.7% and 5.6%). The source hashes in each report
(LF-normalized) match the committed tools.

The corpora were written by `wire-codec-selection.mjs --corpus-out` from 42.47's retained tuned
caches (seed 4217, content-7, source `5cdcd5c`). The driver checks those caches against their
sources, as in 42.49. That gives 244 samples per size: every twentieth tick of 1,200, across four
views. The corpus holds each sample's JSON round trip, so `undefined` and -0 are already gone from
real samples. Those cases are covered by the specimens instead.

Earlier untimed runs and timed previews shaped two changes: the body length in the frame (after
the truncation finding) and the Pn32 variant. The previews were discarded, because the driver was
edited while one of them ran. Their bytes and ratios matched the final runs.
