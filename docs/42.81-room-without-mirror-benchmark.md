## Paired room loop

A room no longer runs the mirror's record applier. Its roster reads the frame store's player records. 42.80's bench
steps an in-process game, which this change leaves alone, so this pair uses the room loop instead. `tests/bench-stages.mjs`
runs the server's loop body with no sockets: the match advances, the frame is recorded and remembered, and one player
view is projected, encoded and serialized.

| ms/tick, mean of 1500 ticks | `main` (`6b040a5b`), runs 1, 4, 5 | This change, runs 2, 3, 6 |
| --- | ---: | ---: |
| Tick | 1.822, 1.771, 1.857 | 1.792, 1.743, 1.817 |
| Tick p99 | 4.24, 3.09, 4.26 | 4.25, 3.13, 4.14 |
| Not under a stage timer (mostly the step) | 1.423, 1.386, 1.448 | 1.395, 1.352, 1.412 |
| `sim.playerView` | 0.131, 0.126, 0.139 | 0.130, 0.128, 0.136 |
| `sim.tick.memory` | 0.036, 0.034, 0.036 | 0.051, 0.051, 0.051 |
| `loop.broadcast` | 0.242, 0.231, 0.252 | 0.242, 0.239, 0.248 |
| `loop.record` | 0.152, 0.148, 0.151 | 0.149, 0.147, 0.151 |

**The tick.**
- The median tick is 1.792 ms against 1.822, about 1.6% lower. Each change run is below its neighbouring base run, but
  the ranges overlap (1.743–1.817 against 1.771–1.857), so this is a small change within the runs' spread. As in 42.80,
  the applier was a small part of the tick.
- The share not under a stage timer, which holds the step, is about 0.03 ms lower.

**Memory refresh (`sim.tick.memory`).** It rose from 0.035 to 0.051 ms in all three pairs, which is larger than the
spread. The code is the same `TickKnowledge`. The only difference is that it now runs without the mirror, with its own
`Context`, which caches nothing. A guess, not measured: `writeMemory` and `groundOf` get less JIT warmth without the
mirror's calls. The rise is smaller than the tick's drop. #1352 D2 decides how memory reaches the projection, and that
replaces this path.

**Projection.** `sim.playerView`, which 42.79 left outside its timer, is about 0.13 ms per view per tick here, with one
viewer. This is the number #1352 D1 asked for.

Against the earlier points, 42.80 measured an in-process tick plus private frame at 1.84–1.87 ms on 42.79's map.
The cutover was 2.886 (42.78) and the end of the flip 5.831 (42.76). Those used different maps, a different loop and a
different bench, so they place this change on the series rather than measure it.

## Method and limits

- Windows, Node 24.15.0, release WASM.
- The baseline is `git archive 6b040a5b`, which is `main` with #1350 merged. Its `node_modules` are junctions to this
  tree's, and its `shared/core-wasm.generated.ts` was copied from this tree, since the change touches no Rust.
- Each run is `node tests/bench-stages.mjs --size=12x6 --ticks=1500 --seed=4217`: one room with 232 ground records,
  one player view and recording on, under the bench lock. The base runs used the base tree's own copy of the script.
- The runs alternated: base, change, change, base, base, change. Outside load was 6.9–9.8% of the machine, below the
  25% threshold.
- The result is one map and its bot trace.
