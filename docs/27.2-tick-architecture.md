# 27.2. Tick architecture (#1282)

Up: [27](27-rust-path.md#the-state-flip). Tracker: #1279. Inventory of today's tick:
[27.1](27.1-tick-mechanic-inventory.md). Corey's answers: [17.7](17.7-tick-resolution.md). The design debate that
settled the details: #1288 (ledger in comment 18000, confirmed in 18001). Resolution model: #1276, which this
document closes.

This is the governing design for the simulation tick. Every mechanic enters through it. It replaces the seven
phases that grew one mechanic at a time and their stops, resumes and "removed earlier this tick" checks. Built as
[Build approach](#build-approach) describes, it replaces the old tick in one cutover.

## Principles

- **Earliest consistent tick.** A thing happens at the earliest tick consistent with this model. No exception to
  the model is made for performance unless the player's experience truly depends on it (Corey, 17.7 follow-up 3).
- **Simultaneous resolution.** Everything a tick resolves reads one frozen state and is applied together. No
  outcome depends on the order actors, traps or items are visited in.
- **Nothing new is visible until the next tick**, except what an actor's own command creates in intake (A1).
- **Qualitative over exact equivalence.** Behaviour changes where this design says so. The old tick is a source
  for what must be covered, not a target to match.

## Stages

Each tick runs four stages (#1288 A1).

1. **Intake.** Validates each command in the inbound queue against the state before intake, and writes only:
   - carried events from T−1 that change tick-start attributes, such as the gladiator kill reward (level +1 up to
     4, max HP +20, HP +45, skill cooldown reset);
   - an actor's own equipment and aim: aim, slot selection, slot rearrangement, and a reload whose deadline has
     passed;
   - the deadlines and resource spends of accepted commands: weapon and skill cooldowns, ammo, reload start, a
     utility's charge (its heal or shield is an effect, merged in apply);
   - projectiles and hook tips created by commands, which take part in T's solve and sweep;
   - inputs to the solve: motor, boost, hook cancel, pulling hooks' tether shortening and revalidation, and the
     impulses queued by T−1.

   Manual drops, interaction, pickups, extraction and casts are validated here and carried to resolve as intents.
   **S0**, the state after intake, is frozen.
2. **Solve.** One batched Rapier step produces post-solve poses and swept paths.
3. **Resolve.** Reads S0's discrete state, the solved paths and the rewound view (R3). It emits events and effects
   and writes nothing. The framework enforces this.
4. **Apply.** Merges effects, settles conflicts and writes the next state, S1, in a fixed order ([Apply](#apply)).

Bots produce commands like players do, from the state before intake, which is T−1's applied state (R11). Today's
two calls a tick (27, D4) become one: phase 1's work moves to T−1's apply (respawns, arrivals) and to intake
(hook prepare, carried events). Timers stop being decremented at all ([State](#state)).

## Commands, events and effects

Three kinds of thing (#1288 A2; Corey, 17.7 follow-ups 1–2):
- **Command:** an intent, validated in intake. A rejected one-shot command emits a rejection event, so the client
  learns why. A held `attack` that loses to another weapon action emits none.
- **Event:** an immutable fact of tick T: a hit landed, a contact, a pulse, an elimination, a kill credited, an
  escape, a placement. Resolve and apply both produce events. **They are published only after apply commits**, in
  canonical order (A6), to the projection, the recording and the bots. A resolve event whose effect lost in apply
  (a pickup claim that lost its contest, say) is published as the outcome that happened, never as a success.
- **Effect:** a typed write to state, with one merge rule per target field:

| Merge class | Effects | Rule |
| --- | --- | --- |
| Additive | damage, heal and shield, impulse | summed; heals and shields first (clamped to their maximum), then damage from shield, then HP |
| Status | `ExtendStatus(kind, untilTick)`, `ClearStatus(kind)` | latest deadline wins; a clear outranks a same-tick extend of the same kind (firing breaks cloak) |
| Exclusive claim | pickup or transfer, extraction slot, placement, gate state | arbitrated in apply step 3 or 4 |
| Lifecycle | spawn, despawn, warp | applied in apply steps 4–5 |

The vocabulary stays this small. A new mechanic uses these classes. A new class needs a reason this document
records.

**The cascade rule.** Within T, only the fixed chain in [Apply](#apply) runs. Any other consequence of an event
goes onto T+1's inbound queue: the kill reward, a trap's reaction, anything that needs a new query. There is no
recursion within a tick.

## Apply

Apply runs in this order (#1288 A3):

1. **Merge** additive and status effects per target.
2. **Eliminations.** An actor whose HP reaches zero is eliminated. One kill-credit holder is drawn (A6 hash) from
   the sources of lethal hits, whether or not each source is still alive. Other hitters get assists. Mandatory
   death drops are requested.
3. **Exclusive claims, survivors only.** Survival is settled before anything is allocated (Corey, 17.7 follow-up
   8), so a contestant killed on the tick they extract does not escape.
   - **Extraction slots:** closest eligible contestant, then the A6 hash.
   - **Pickups:** all (claimant, item) pairs sorted by (claim class, current record distance, A6 hash). Explicit claims
     (interact, swap) come before automatic pickup. Each pair transfers what fits the claimant's remaining
     capacity and the item's remaining count, which covers partial stacks and magazines.
   - **Swaps:** a swap's outgoing drop is validated and its spot reserved when its pair is reached. If no spot or
     capacity exists, the swap fails and the ground item stays available to the next pair.
   - **Gates:** R8. A gate close commits here, before placement.
4. **Placement** of the remaining spawns, per R4: death drops, manual drops, respawns, arrivals, trap shots. Spots
   reserved by swaps are excluded.
5. **Removals and status changes**: escaped, eliminated, transit. Rapier bodies, gates and invalidated hooks are
   synchronized here, so S1 and the physics world agree.
6. **Deadlines** are written.
7. **T+1's carried events** are queued, then the terminal check runs (R12).

## State

(#1288 A4.)
- **Stored:** per-kind tables in the core, keyed by stable ID: actors, items, projectiles, hooks, gates, traps,
  stations. They follow [24.4](24.4-relational-data-model.md)'s relational model.
- **Timers are deadlines:** `readyAt`, `activeFrom`, `expiresAt`, as absolute ticks. Nothing is decremented per
  tick. An N-tick cooldown is `readyAt = setTick + N` and is ready when `T >= readyAt`.
- **Derived, never truth:** spatial indexes, occupancy, visibility, rewind history.
- **Shared:** the map and its static geometry, immutable for the match.
- **One copy.** No mirror. Per-tick cost follows the active set, never the map's size.

## Boundary

(#1288 A5; Corey, 17.7 follow-up 2.)
- **In:** T's inbound queue holds three kinds of item:
  1. player and bot commands stamped T, under the existing stamp, acknowledgment and hold contract
     ([24](24-networking-privacy.md));
  2. events carried from T−1;
  3. observations: measured view lag, input lead, join, leave, dev teleport.

  All are recorded except first-class bots' commands (Corey, 2026-11-23). What enters through the receive boundary is
  recorded: a person's input, that of a bot controlling a player, and the measurements. A first-class bot's command is
  the match's own computation from the history the recording holds, so it is derived. A seat's `leave` and `join`
  mark where derivation starts and stops.

  Lag stays server-measured, but enters as a recorded observation and no longer as a write to player state
  between ticks (today `setViewLag`, `server/match.js`). A per-command view tick (#1282 N10) is deferred.
- **Out:** events, per-viewer projections, recording frames (S1 plus T's inbound queue plus apply's physics
  discontinuity markers), and snapshots on request. Apply also emits the change list: changed records whole, removed
  IDs, and events. Node's frame store builds the frames from it ([Frames](#frames-3d3)), and until #1284 removes the
  mirror, the mirror applies it too. It is one list, so the mirror's per-phase appliers and their ordering rules go.

**Wire and recording.** The nominated interaction target (R8) adds an optional `PlayerInput` field, which bumps
`WIRE_VERSION`. Schema 21 records legacy observations as commands. Schema 22 records each live frame's spent inbound queue. See [26](26-recording-contract.md#schema-22-the-inbound-queue-as-commands-1283).

## Determinism

(#1288 A6.)
- **One canonical order per kind,** everywhere:
  - actors by (kind, numeric stable ID), replacing both the string sort and roster order (D24);
  - traps by authored map index;
  - gates by authored gate index;
  - projectiles and ground items by numeric ID.
- **IDs are allocated only in apply,** in canonical event order.
- **Tie-breaks** use a stateless hash, `hash(matchSeed, tick, contestKey, entityId)`. Drop scatter phases use
  `hash(matchSeed, tick, "scatter", dropperId, slotOrFamily, copyIndex)`. Neither consumes the match RNG, so a
  refused plan never shifts a later one.
- **Publication** follows canonical order. Event retention is unchanged.

## Rules

Each rule below is agreed in #1288; the D-numbers are 27.1's rows.

- **Commands in one input record (R1; D05).** At most one weapon-slot action per tick, with precedence
  drop of the selected slot > reload > slot change > attack. Dropping another slot, or `dropAmmo` of another
  family, is independent. Within one family, `dropAmmo` beats reload. A skill is independent of weapon actions.
- **Newly active actors (R2; D01).** An actor activated in T's apply first spends input stamped T+1. Input
  stamped T for an inactive actor is discarded, never held. Held-input repeat starts after the first spent
  input.
- **Lag compensation (R3; D11, D13).** One query, `rewound(viewer, targetTick)` with
  `targetTick = T − clamp(viewLagTicks, 0, MAX_REWIND_TICKS)`. It returns target poses and gate states at
  `targetTick`; static geometry is current, and the caster's own origin is its post-solve pose.
  - It decides **eligibility** (range, arc, line of sight) for instant attacks (gladiator melee, Warden pulse)
    and interactions. **Contention** uses current post-solve positions.
  - It is captured after apply. Missing history falls back to the target's current pose.
  - Melee target ties use the A6 hash. The Warden is one pulse for now. Travel-time projectiles stay
    uncompensated (24).
- **Spawn and placement (R4; D02, D06, D18, D25).**
  - Physical bodies are placed without overlap. Query-only shapes (bullets, hook tips) may overlap.
  - Requests are ordered by a seeded permutation (A6 hash), then placed greedily at the nearest valid point within
    each kind's radius.
  - **Failure:** respawns and arrivals stay pending, with the actor inactive, and retry next tick. Manual drops
    and swaps are refused with a rejection event, and the item stays held.
  - **Death drops** are mandatory: they bypass ground capacity and fall back to the death origin when no clear
    point exists. The fallback record can overlap. Its body still goes through admission (D25).
  - A drop made in T first enters the claim queries at T+1 (A1), even while its body awaits admission.
  - Transit does not reserve its landing. Motor-surface and floor-drag overlaps use highest priority, then
    authored surface ID.
- **Physics cutoffs (R5; D07, D08, D22).**
  - Impulses from resolve feed T+1's solve. A mine blast reaches surviving bodies in S0, not same-tick death drops.
  - Warps (a transit landing, a teleport) commit in apply. T's queries use T's solved paths.
  - A hook tip that hits in T's resolve attaches and starts pulling in T's apply, and its rope acts in T+1's solve.
    `PHASE_PENDING` is retired.
  - A hook whose endpoint is eliminated or departs in T detaches in apply.
- **Projectiles (R6; D09).** `expiresAt = spawnTick + life − 1`, which keeps today's `life − 1` sweeps and so
  today's range. A projectile sweeps while `T < expiresAt` and is removed in the apply of its last sweep tick.
  - Command-fired projectiles and hook tips have `spawnTick = T`. Turret shots have `spawnTick = T + 1`.
  - Geometry wins an exact tie with an actor, and ties between actors use the A6 hash.
  - An actor eliminated in T still counts as first contact and consumes a one-hit projectile.
- **Casts (R7; D10).** Every accepted cast in T resolves against S0 and the solved paths, including a skill and an
  attack together, and including a caster killed in T. Their effects merge, so no order within the actor is
  needed. Stun on a lethal hit counts as applied, with `activeFrom = T + 1` (17.7, 17:47).
- **Interaction (R8; D13, D16, D17).**
  - `PlayerInput` may nominate a target ID. If it does, the server validates only that target (R3 eligibility,
    S0 availability) and rejects it on failure without falling through. Clients omit targets they know are
    ineligible. A nomination the receive boundary cannot map (malformed, or naming nothing on the map) reaches the
    core as `unresolved`, which is never eligible, so a pressed interact is rejected and no rail destination is
    taken (3d.4a).
  - With no nomination, eligible targets are ranked by **provisional** priority tiers (tier 1: extraction,
    charging start; tier 2: gates, rail transit, full-inventory swap), then distance, then the A6 hash. The tiers
    may be rearranged from feedback (Corey, 17.7, 18:14).
  - Opposing requests on one gate are an exclusive claim, decided by the A6 hash. Gate-close occupancy checks the
    post-solve poses of surviving, non-departed actors and dynamic props.
  - A key collected in T cannot pay for T's attempt. A failed attempt emits an event, and discovery learns the lock
    at T+1.
  - Explicit claims outrank automatic pickup.
- **Charge, detection and cloak (R9; D19).** Charging starts in T's apply, first progresses at T+1, and a charge
  completed in T first funds extraction at T+1. Active charging cancels in apply, without progress, on movement
  beyond jitter, lost reach or line of sight, extraction, transit or elimination. Sensors read S0's cloak and sneak
  and the post-solve position. A reveal applies in apply with `activeFrom = T + 1`.
- **Hazards and traps (R10; D20, D21, D22).**
  - Wall and area damage both apply and sum.
  - Traps read S0's deadlines and active targets and the post-solve positions. Nearest-target ties use the A6
    hash, and a trap never retargets within T.
  - A spider computes its step and grapple from its stepped pose inside its own resolve; other queries see it at
    S0, and its move commits in apply. Its grapple effect lands at the victim's post-solve pose, lethal or not.
  - Turret shots are placed in apply and first sweep at T+1.
- **Bots and cues (R11; D04, D26, D27).**
  - Intent reads the state before intake. What is observed in T first affects intent at T+1.
  - Discovery staggers by the canonical contestant index. Route updates and detour work stagger by roster slot.
  - Blocker distance ties use stable actor labels and authored prop order. Remembered loot and frontier ties use
    first-observed order, with the sample's cell and item order deciding ties within each sample.
  - A cue emitted in T is published in T's events and reaches bots at T+1.
- **Terminal, rewind and recording (R12; D23).** A started tick always completes. The time limit gates the next
  tick, and also ends the match at the close of the final one.
  - At the end of apply, if no slots remain, no contestant is active, or time is up, remaining contestants are
    stranded and their bodies removed.
  - Then, in order: the rewind frame is captured, discovery samples surviving active contestants, and the frame
    is recorded and the projections built.
  - Per-tick frame and latest-state delivery are unchanged.

## How a mechanic enters

(#1288 A7.) A mechanic declares:
- the commands it accepts and how intake validates them;
- whether it writes inputs to the solve;
- each query, and the view it reads: S0, solved paths, or rewound;
- the events it emits;
- its effects and their merge classes;
- the exclusive resources it claims;
- its deadlines and its spawns.

These declarations are the mechanic's module structure and its tests. They are not a registry or a framework of
their own, unless one is later shown to be needed ([DOOR](#door)).

## Test API

(#1288 A8.)
- A scenario builder arranges state. A test submits stamped commands, steps the tick, and asserts on the events
  first, then on the state.
- Resolve is testable as a pure function: (S0, solved paths, intents) → (events, effects).
- #1282's acceptance examples (comments 17961 and 17968, with 17.7's corrections) become tests.
- Test cost statements follow [31](31-verification.md#test-cost).
- **Reading state** (#1345). `stateOf(s)` ([`tick.ts`](../shared/simulation/tick.ts)) gives a started in-process game's
  state as of its last completed tick: the frame store's records ([Frames](#frames-3d3)), its phase and that tick's events.
  `now(s, p)` (`tests/helpers/scenario.js`) is one player's record by roster place. After the start, the `Game` holds only
  the roster and its arrangement, the clock and phase, the receive boundary's per-player state, and knowledge
  ([Node adapter](#node-adapter-3d2)). A record is a copy, ground records included, so editing one changes no later
  read or frame (review 1105); read again after each step.
- **Arranging** happens on the `Game` before the first step, which the loader reads. A contestant's knowledge is arranged
  with `Player.knows` (`know` in `tests/helpers/scenario.js`): surveyed discovery cells and remembered doors. The setup
  carries it (`MatchSetup.known`, `Scenario::know`, adapter version 52), and the opening discovery adds to it. A room
  never sets it. `p.discovery` is the core's memory written back for projection, not an input (#1358). Mid-match, arranging goes through commands:
  stamped input, a dev teleport (`boundary.teleport`), or `framesOf(s).arrangeEvent` for an event on the last frame. A write
  to the `Game` after the start never reaches the core. A retained TypeScript rule (#1241) called on a `Game` is a unit
  test of that rule, on an unstarted game.

## Build approach

**Decided (Corey, 2026-11-22, 17.7 follow-ups 9–10): build dark, cut over once.**

1. **The new tick is new code in the core,** not wired into the game. It merges to `main` in pieces that compile
   and pass their own tests, written against the test API. `main` stays green for everyone else.
2. **The old tick is frozen and keeps the game playable.** It is not updated or compared against. It is kept only
   to check that everything it did has been accounted for. The feature freeze keeps everything else off it.
3. **An accounting ledger drives completeness.** Every mechanic in 27.1's census and every D-row maps to new code
   or to a recorded behaviour change. It lives in [Accounting](#accounting), and each build PR updates its rows.
4. **One cutover PR** switches the game to the new tick and deletes the old one. It also:
   - bumps `WIRE_VERSION` (3c already took the recording schema to 21);
   - triages the old tests once, porting, rewriting or deleting each one (Corey, 2026-11-17, [17.4](17.4-live-service.md) #18);
   - re-baselines the frozen fixture once, deliberately, for the intended gameplay changes;
   - benches against [42.76](42.76-state-flip-benchmark.md), with a paired same-session baseline as
     [42.77](42.77-tick-inventory-checkpoint.md) requires.

This relaxes #1279's "the game stays playable throughout": `main` stays playable, on the old tick, until the
cutover. Comparing outputs would mostly flag the changes made on purpose, which is why the build does without it.

**Staging for #1283:**

- **3b. Mechanics, in groups.** Each group is a PR that updates its ledger rows:

  1. **Setup and core surface,** unwired ([below](#live-adapter-3d1)).
  2. **Node adapter:** receive boundary, bot commands from the mirror, and one applier of the change list.

  4. **The switch,** in four PRs (comment 18317):
     1. core changes before it: the opening discovery and the unresolved nomination ([below](#core-changes-before-the-switch-3d4a));

### Framework entry point (3a)

[`rust/core/src/tick`](../rust/core/src/tick/mod.rs) is the native Rust entry point for the new tick.
`Scenario` seeds the tables and Rapier bodies. A match takes admitted stamped commands and observations,
and returns each completed tick's inbound records, solved paths and committed events. The adapter will supply
receive-side sequence, lead and supersession handling when it builds those records for room wiring (3d.4c). The core
spends one command per active actor, updates acknowledgment on spend and repeats only held movement, aim and sneak.

Intake reads the pre-intake tables and plans its writes. Resolve borrows the post-intake tables and the paths from
one Rapier step. A single apply merges numeric and status effects, marks eliminations, passes survivors' claims
to the rule set, commits placements and lifecycle changes, writes deadlines, queues carried events, and checks
the terminal condition. Rules supply typed intents, claims and placement requests. Event publication and runtime
ID allocation use canonical keys even when arbitration visits placements in another order.

The native tests exercise these stage boundaries with a small rule set and real Rapier bodies. Mechanic rules
and their player-visible acceptance examples enter with 3b. Output adaptation enters in 3c ([below](#output-3c)).

### Movement and hooks (3b.1)

[`tick/movement.rs`](../rust/core/src/tick/movement.rs) builds motors from the actor's pre-solve position,
stamped or held input, and status deadlines. A ready Overdrive press sets its boost window and skill deadline
in intake and affects that same motor. Idle actors get bounded braking. Authored motor and drag rectangles use
the same priority and ID ordering. Each query considers local surface candidates from an index built at setup.

Intake cancels, revalidates and shortens existing tethers. A new tip has a command-local identity through its
first sweep, so it can hit in T. Apply gives a surviving hook its stable ID and commits it directly as pulling
when it hits. The first tether force is in T+1. A cap contest among eligible launch commands uses the A6 score
after intake releases have freed their places. [`tick/hook.rs`](../rust/core/src/tick/hook.rs) shares the swept
geometry query with the old tick. That query uses the native state's current gate rows and solved solid prop
poses for tip flight. Tether preparation uses pre-solve poses and the same solid geometry policy.

[`tick/solve.rs`](../rust/core/src/tick/solve.rs) feeds motors, impulses and bounded ropes to one Rapier batch.
It decodes paths, stable contact IDs and broken tethers. Apply drops hooks whose endpoints depart or relocate.

### Combat (3b.2)

[`tick/combat.rs`](../rust/core/src/tick/combat.rs) composes combat with movement and hooks. Intake spends a
round from an equipped firearm, sets its weapon deadline, and gives each pellet a command-local ordinal.
[`tick/projectile.rs`](../rust/core/src/tick/projectile.rs) sweeps both new and persistent projectiles against
shot-blocking geometry and solved actor paths. Apply allocates stable IDs to surviving launches in spread
order. A first hit consumes the projectile even if other effects eliminate that target in the same tick.

Melee and Warden use [`tick/rewind.rs`](../rust/core/src/tick/rewind.rs) for historical target poses and gate
states. Their origin is the caster's post-solve pose. Melee ranks eligible targets by current distance and
then the A6 score. Warden stun and Specter reveal start at T+1. Shooting clears cloak in apply.

[`tick/apply.rs`](../rust/core/src/tick/apply.rs) merges damage, records aggression and marks deaths before
claims. For a fatal merge, the A6 score draws credit from opposing or friendly player sources that dealt
positive damage to the victim in T. Other player hitters receive assists. The same ranking rule, with its own
contest key, selects a single aggressor for a target hit by several players. Credit can go to an eliminated
source. A credited gladiator's reward is carried to the next intake and can reset a skill before its command
is validated.

### Items (3b.3)

[`tick/inventory.rs`](../rust/core/src/tick/inventory.rs) owns the six slots, item identities, loaded rounds,
family reserves and selected-slot reload. [`tick/items.rs`](../rust/core/src/tick/items.rs) completes due
reloads before eligible fire, arbitrates R1 commands and spends utility units. Fire consumes a round from the
same inventory, and utility health and shield merge with the tick's damage. Reloading and quality damage use
the match's selected rules.

Claims read the ground item record. Its current position is the body's post-solve position when it has one
and the stored `unplaced_at` otherwise. Automatic pickup uses current reach. Nominations and default
full-inventory swaps use R3 reach against loot available in S0. R3 uses historical gate state and item poses
when available, with bodiless items read at their stored spot. A failed nomination produces a rejection
without selecting another interaction. Apply ranks surviving claimants by class, current distance to the
item and the A6 score. Transfers respect the remaining capacity, preserve the identity of whole pickups and
keep the root of split stacks. A swap commits its outgoing spot, incoming take and held inventory together.

[`tick/placement.rs`](../rust/core/src/tick/placement.rs) plans item drops at the solved origin, using seeded
bounded scatter and the current occupancy. Optional drops require room for every copy. A death drop can
exceed the logical cap and fall back to the death origin. It retains its value as a pending item when the body
budget is exhausted. Drops created in T first enter S0 claims at T+1 even if their bodies have not been admitted.
The one-second pickup lockout applies to the dropper alone. The shared placement and retry rules are below.
Rewind capture is in 3b.7.

**Automatic pickup cost (3d.4b, review 1057).** Resolve rebuilds the pickup grid each tick from every ground
record, including bodiless loot. The 3d.4d cutover bench measures the grid build and nearby queries separately
from discovery, comparing ticks with similar active contestant counts at different ground-record counts.
This cost also applies with proximity-based body admission. A retained index queried around active contestants
is a possible way to keep pickup cost tied to the active set.

### Interactions (3b.4)

[`tick/interaction.rs`](../rust/core/src/tick/interaction.rs) selects one interaction from S0. An explicit
nomination validates only that target. An explicit rail destination takes precedence over a targetless
Interact. Default Interact ranks extraction and charging first, then gates, rail and full-inventory swaps.
Candidates use the same rewound sight and reach view and rank by solved distance and the A6 score. Access
keys live in the same inventory as other pickups, outside its six slots.

Apply allocates extraction slots to survivors by distance and the A6 score and spends the named cell on
escape. Opposing gate requests use the A6 score. A successful unlock spends an S0 key, and the attempted
gate state is carried to T+1 for discovery. Close occupancy uses solved surviving actors and solid dynamic
props, after escapes and timed departures. Gate changes constrain placement immediately. Gameplay queries
and the Rapier solve see the new state beginning in T+1.

Charging tracks a held cell by identity. Start commits in apply and first advances in T+1. Solved travel
above the jitter threshold, lost reach or sight, loss of the cell or departure ends the session. A completed
charge first funds extraction at T+1. Sensors look at S0 cloak and sneak and the solved pose, with reveal
effective at T+1.

Timed rail departure checks clearance and records the destination, origin and due tick without reserving
space. Instant landings warp in apply. The rail cooldown starts at landing.

### Hazards and traps (3b.5)

[`tick/hazards.rs`](../rust/core/src/tick/hazards.rs) advances the wall from the tick and grace period
and indexes authored hazard areas. Environment and traps resolve against S0 gates and the solved actor
poses. Wall and area damage combine with trap and player damage in the vital merge before survivor
claims. Overlapping area boxes contribute one area hit per damage interval.

Mines trigger on solved travel by an eligible actor. Apply marks the mine spent and carries blast impulses
to surviving dynamic bodies from the solve. Turrets aim at the nearest eligible target, use an absolute
fire deadline and spawn their shots in apply for a first sweep at T+1. Flame traps derive their warning and
damage phases from the clock and authored offset. Turrets and spider acquisition rank nearest targets by
solved distance and the A6 score. A spider retains a target within its leash and checks its step against S0
geometry and gates. Grapple uses the stepped position, applies stun from T+1 and records the victim's
solved position even on a lethal hit. Heard gunfire is in 3c.

### Respawn, arrival and placement (3b.6)

[`tick/placement.rs`](../rust/core/src/tick/placement.rs) uses one seeded order for due respawns and arrivals,
instant rail landings, drop requests and pending item bodies. It checks solved survivor occupancy, committed
gates, existing bodies and spots and body capacity reserved by swaps and earlier placements. An unavailable
actor placement stays due and retries on the next tick. A mandatory drop without a legal body placement
keeps a logical record at its stored `unplaced_at` position. Its body retries there, while the item is claimable
from S0 beginning at T+1.

Gladiator deaths set an absolute respawn deadline. Respawn prefers the westmost eligible transit station
ahead of the wall and away from surviving contestants. The shared actor search finds a clear position near
the station, with the next eligible station available if that search fails. On admission the actor retains
earned upgrades, restores HP and resets shield, boost, stun and action cooldowns. Due rail arrivals search
near their destination, clear the transit record on success and start the rail cooldown then.

[`tick/apply.rs`](../rust/core/src/tick/apply.rs) and [`tick/solve.rs`](../rust/core/src/tick/solve.rs) remove
departing bodies, synchronize gates and warps, and admit the accepted bodies within the same apply stage.
An actor admitted in T has no solved path in T and can first spend a command stamped T+1. Held input clears
on departure. Carried mine impulses stay with solved bodies that survive apply.

### Terminal, rewind and discovery (3b.7)

[`tick/mod.rs`](../rust/core/src/tick/mod.rs) checks the terminal predicates at the close of apply, after every
claim, placement and removal has committed. The match ends when the time limit is reached, the extraction slots
are spent or no contestant is active. A final-tick escape, kill or landing stands. Contestants still active
are then stranded and their bodies removed, and the runner refuses later records and steps. Gladiators keep
their state.

The rewind frame is then captured from the committed world, so it includes same-tick admissions and warps and
omits escapes, departures, eliminations and strandings. [`tick/rewind.rs`](../rust/core/src/tick/rewind.rs)
stores every active actor's pose, plus only the ground items and gates that changed in the tick, each with its
value before the change. A lookup rebuilds any retained tick from the changes around it, so the cost of capture
follows the active set and not the map.

[`tick/discovery.rs`](../rust/core/src/tick/discovery.rs) then reports what contestants learn. The first part is
the direct gate observations carried from T−1's attempts, contestants only. The second is the periodic samples.
Each sample's eye is the committed pose. A contestant at canonical index i samples when `(T + i)` is a multiple of
`DISCOVERY_INTERVAL`. That rotates the canonical order's starting point and replaces the roster offset. 3c applies
it to memory. Anything learned at T first affects intent at T+1.

### Output (3c)

[`tick/output.rs`](../rust/core/src/tick/output.rs) builds a completed tick's outputs once apply commits.

- **Change list.** `CompletedTick::changes` is the one list Node applies, in the frame store and the mirror. It holds each changed record
  whole, the IDs of removed ground items, projectiles and hooks, the committed poses of dynamic bodies whose pose
  changed or that entered, and T's events. A pose is the body's whole pose: position, rotation, velocity, spin and
  whether Rapier put it to sleep (3d.3). Actors, projectiles and hooks are compared with their tick-start records.
  Ground items, gates and traps are read only where a fact or lifecycle change names them, so the cost follows the
  active set. A test build checks every table, then folds each tick's list into the first snapshot. Any scenario
  whose fold differs from the match fails.
- **Recording frame.** T's inbound queue as spent, the discontinuity markers and S1. S1 is the previous frame with
  the change list applied, which is the delta form 26 stores. A keyframe is `Match::snapshot`. A marker names a
  body placed, warped (a dev teleport included) or removed in T.
- **Observations.** Intake applies them from the queue. View lag sets the rewind lag. Join and leave set the bot
  flag and clear the lag, the held input and the spent sequence, since a resumed connection numbers from the start
  (3d.2). A teleport moves its body before the solve. Input lead stays with the
  receive boundary. Node records changed lag as `viewLag` and `inputLead` commands, which is recording schema 21
  ([26](26-recording-contract.md#schema-21-observations-as-commands-1283)). Joins, leaves and teleports were
  already recorded as commands.
- **Discovery memory.** [`tick/discovery.rs`](../rust/core/src/tick/discovery.rs) applies
  `CompletedTick::discovery` to each contestant's `Memory` through `crate::discovery::DiscoveryMap`, the rule
  `shared/discovery.ts` runs. Gate observations come first, then samples. A human learns the view window. A bot
  also samples with line of sight. It learns seen and surveyed cells, items and doors in sight, and forgets a
  remembered item whose spot it sees empty. Remembered items are keyed by ID. A projection of T pairs T's snapshot
  with the memory after T's discovery, since both are the close of T. `foldDiscovery` now staggers a replay by
  the canonical contestant index. Shipped rosters list contestants first in seat order, so for them it equals the
  old roster index, and old recordings fold unchanged.
- **Hearing.** [`tick/hearing.rs`](../rust/core/src/tick/hearing.rs): resolve emits one `Fact::Heard` per
  listener. It uses the shooter's pre-solve origin and S0's active listeners at their pre-solve poses, as intake
  fired it. The cue store takes it when T's events publish, so `Match::heard` first gives it to a bot's intent
  for T+1. Each cue names its listener, and a projection shows it only to that listener.
- **Cost.** A bot's line-of-sight sample scans the ground items for those in reach, once per tick that has such a
  sample. The cutover bench measures it, and a spatial index is the fallback if it shows.

### Live adapter (3d.1)

[`tick/codec.rs`](../rust/core/src/tick/codec.rs) is the one word layout between the new tick and JavaScript,
and [`shared/simulation/tick-codec.ts`](../shared/simulation/tick-codec.ts) mirrors it. The layout follows
[27](27-rust-path.md#the-core-and-its-adapter)'s rule 1, with flat `f64` words.
- **Rows are fixed length per kind,** so a reader steps by stride. An optional value is a presence word followed
  by its words, which are zero when absent. An enum is a tag word with its payload padded to the widest variant.
- **Every word is finite.** No NaN or infinity stands for a missing value, and both decoders refuse one. The core
  follows suit: a match without a wall has no `hazard_x` (an option, not negative infinity), and an unset body
  damping is an option, not NaN. Only the old world's row format, read once by the loader, still marks it NaN.
- **IDs.** An actor is one word, `actor_word`. A body or entity is a tag word and a value word.
- **One table encoding.** Setup, the change list and the snapshot share the state rows, so a snapshot's tables
  decode as a valid setup. Round trips in both languages pin the layout.
- **Setup** holds the seed, the time limit, the tables, the bodies (`BodyId` followed by the spec's fields,
  from the TS spec builders), the motor surfaces and floor bases, hazard areas and the wall, and the tuning for `Combat`. The map's
  swept, sight, gate and discovery uploads are the existing handles. The core copies them, so the gate mask that
  JavaScript writes for the old tick never reaches the new one.
- **Exports** are `match_new`/`match_free`, `match_input` and `match_submit` (a batch of inbound rows, with a flag
  for each row), `match_step` (the encoded `CompletedTick`, or nothing once finished), `match_snapshot`,
  `match_memory`, `match_heard` and `match_acknowledged`.
- **The loader** ([`shared/simulation/tick-match.ts`](../shared/simulation/tick-match.ts)) packs a freshly created
  `Game` into a setup and keeps the ID maps: player ID to actor, gate, trap and station strings to indices. It
  refuses state that a match start cannot hold, such as a projectile, hook, charge, transit or reload already in
  progress. Station IDs number the chargers first, then the transit stations, each in map order. Countdown fields
  become deadlines at the game's tick. Every ground item starts unplaced, so the new tick's own placement admits
  the map's loot at T1, under the drop reserve. Content values that the core still bakes in, such as magazines,
  reload times and utility amounts, are checked against the content, and a mismatch is refused.

Nothing in the game calls the adapter yet. 3d.2 adds the receive boundary, bot commands and the mirror applier
([below](#node-adapter-3d2)).

### Node adapter (3d.2)

[`shared/simulation/tick-boundary.ts`](../shared/simulation/tick-boundary.ts) is the receive boundary, and
[`shared/simulation/tick-mirror.ts`](../shared/simulation/tick-mirror.ts) is the mirror applier and runner. The
opt-in room uses both from 3d.4c.

- **Receive boundary.** Player input keeps [24](24-networking-privacy.md)'s contract by keeping its buffer, under
  the one policy the old tick uses:
  - `queueInput` admits on sequence, stamp and lead, gathers the margin, supersedes on arrival what is queued for the
    new stamp's tick or later, and holds unstamped input first in, first out to its depth.
  - `takeQueued` takes the input the next tick spends, and only that becomes T's `Command` row.

  The core never holds a player row ahead of its tick. So a seat change (whose reset empties the buffer), a
  supersession, an inactive tick or an overflow never meets a row already queued there (review 1040). The core
  spends, holds and acknowledges.

  A measured round trip becomes `viewLag` and `inputLead` rows, each compared with the last one reported, so a
  correction before the next tick is kept. The lead stays at the boundary. Resume and leave reset the receive
  state and become `join` and `leave` rows. A dev teleport of an active player becomes a `teleport` row, and the
  core refuses a point the body could not stand on: outside the bounds, in geometry, a closed gate or a solid prop,
  or on another active actor (`Match::teleport_clear`, the old dev rule). Static geometry keeps `canOccupy`'s 0.01
  tolerance, so a point one radius from a wall stands; gates and props may be touched, not entered
  (`SweptMap::disk_clear`). Acknowledgment comes from
  `TickMatch.acknowledged` after each step.
- **Bot commands.** The Rust planner reads committed T−1 state (R11) and emits one
  `CommandSource::Bot` row per active bot in roster order for T. A seat relabel observation
  carries its lexical rank immediately after binding the new label. The core applies these ranks
  in observation order, including when multiple seats are relabeled for the same tick.
  - `utilitySlot` is the input's own field.
  - `discardSlot` is a drop of that slot, which outranks a selected-slot drop.
  - Since 3d.4b, a preferred slot is sent only when it differs from the selected slot. Under R1 a slot request takes precedence over attack.
  - A transit nomination is sent only under `transit: 'selectable'`.
  - The sequence is one past the last spent, so a seat handed back from a player keeps spending.

  A bot sends a targetless `interact` every tick, and the core answers each with a rejection event where the old
  tick ignored it.
- **One applier.** `TickMirror.apply` writes `CompletedTick::changes` onto `Game`, replacing the per-phase
  appliers on this path. No session runs it any more: since #1345 an in-process game keeps only its clock, phase and
  knowledge, and is read through `stateOf` ([Test API](#test-api)), and since #1346's first part a room reads its roster
  from the frame store ([The room-facing match](#the-room-facing-match-3d3)). Only its own checks below construct it,
  until #1346 removes it. One tick's sequence is `stepTick` ([`tick-step.ts`](../shared/simulation/tick-step.ts)) for
  the room, its replay (which passes the recorded rows in place of the boundary's buffer), in-process games and the
  mirror's checks: submit what is due, step the core, apply the mirror if there is one, write knowledge, acknowledge:
  - Changed records are written whole, removals follow, and a moved body writes its pose whether or not its record
    changed.
  - The ground list goes through the ground-list helpers, as records the core already holds.
  - Gates go through `writeDoor` and the sight gate set, so the bots' queries see them.
  - Decisions:
    - **Countdowns against deadlines.** The mirror keeps its readers' countdown fields, each the deadline less the
      mirror's tick and never below zero, which is the loader's inverse. Unchanged records are not resent, so it
      recomputes them each tick from the deadlines it last received: every actor (the roster), the traps still
      counting and the projectiles (the active set). A passed deadline reads as zero. A bot reads readiness one tick
      late, since its countdown is relative to T−1, which is qualitative.
    - **Presentation from facts.** Effects and `GameEvent` payloads are built from T's facts after the records
      apply, with the old kinds and radii at committed poses. `escaped` gives `pod_powered` with the slots left after
      that escape, which `Fact::Escaped` carries so each actor keeps its own count through canonical order. The new
      word is adapter version 44 (`ADAPTER_VERSION`, `CORE_ADAPTER_VERSION`), so a 3d.1 module is refused at load.
      `eliminated` takes its source from T's `killCredited`, and `finished` gives `match_finished` and ends the
      phase.
    - **Identity.** A core item ID is the mirror's `ItemId`, as the loader keeps them, so `MatchIds` needs no item
      table. `itemSerial` follows the largest seen. Actors, gates, traps and stations go through `MatchIds`.
    - **Frames are not the mirror's.** Hooks, every dynamic body's whole pose and the bodies' lifetimes are kept by
      the frame store ([3d.3](#frames-3d3)), which follows the match's completed ticks itself (#1344). The mapping from
      core records to Node's records is one module, [`tick-records.ts`](../shared/simulation/tick-records.ts), which
      the store and the mirror both call.
    - **Acknowledgement is the boundary's.** After each step, `TickBoundary.acknowledge` writes each
      connection's spent sequence, stall count and margin onto its player, where the receive boundary keeps the rest
      of its per-player state (#1344).
    - **Presence is the boundary's own.** Whether a player is active, which decides whether its input is due, whether
      its stall count grows and whether a teleport is admissible, comes from the actor records of the completed ticks:
      the boundary follows the match for them, as the frame store does, and never reads the mirror's `status` (#1345).
  - **Knowledge** ([`tick-knowledge.ts`](../shared/simulation/tick-knowledge.ts)) is split from the record applier:
    every started game writes each contestant's memory and every player's cues onto its `Game` player, which
    `playerView` reads until #1343 moves it to the knowledge cache
    ([Projection and knowledge](#projection-and-knowledge-1343-1352)). The mirror runs it too.
  - With discovery off in the content, the mirror keeps no memory, as the old game attaches none. A bot without
    memory plans with full-map knowledge. The core still learns gate attempts without a sampler; the mirror ignores
    them.
  - Memory is written for the contestants a tick's discovery names, into the bots' own `SeenCells` and
    `ItemMemory`, adding and setting so first-met ties hold until #1215. The core's revision counts only what plans
    read, as `discover` does, so every sample is written. Cues are read for every player each tick.
- **Check.** `TickMirror.mirrorOf` maps a whole snapshot as the applier maps changes. Every tick, a test holds the
  mirror's view equal to it, memory and cues included:
  - on a small arena in the fast tier;
  - for a whole match with today's default content on the fixture's arena 9 in `tests/slow/`.

  The whole match found #1301. Only 69 of 926 items had a body, claims required one, and no contestant armed.
  In 3d.4b, claims read records, and the match test requires contestants to arm and fire. Proximity-based
  admission is #1301 step 2 after cutover.
- **Gaps for 3d.3 and the cutover.**
  - ~~The core's memory starts empty.~~ The core makes the opening discovery at setup (3d.4a).
  - A memory refresh decodes that contestant's whole memory. The cutover bench measures it, and a change export is
    the fallback.
  - Rewind history keeps item poses keyed by ID across pickups. An item picked up and dropped again with a body
    within the rewind window can therefore pass R3 reach at a pose from its previous time on the ground (review 1057).
    Tracking ground lifetimes in the change-only history would let this case fall back to the current pose.
  - The bots' detour blockers read prop states from the old world, which this path does not step.
  - ~~A dev teleport's reply.~~ 3d.4c reports the committed T warp from the frame's discontinuities and publishes a
    paused pose only when the warp committed (review 1041).
  - ~~A player joining after the start.~~ 3d.4c maps actors through stable roster seats, allowing a live join and
    connection ID changes without replacing the actor mapping; it adds a live-join acceptance case (review 1040).

### Frames (3d.3)

[`shared/simulation/tick-frame.ts`](../shared/simulation/tick-frame.ts) builds each tick's frame from the core's output
(#1344): the `Snapshot` the recording writer stores and `playerView` projects. The frame store follows the match
(`TickMatch.follow`) and takes each completed tick as the step decodes it. It keeps the records it last received, so the
frame of T is the previous frame with T's change list applied ([Output](#output-3c)). `TickFrames.frame` gives the frame
of the last completed tick. The store does not read the `Game` mirror.

- **What comes from the game.** The core does not hold everything a frame carries. At the start, the store reads the
  content's constants, the traps' static fields, the order of the map's loot, and where an actor without a body
  stands. Each frame, it reads the roster's identity (`name`, `role`, `kit`, `seat`) and the receive boundary's
  per-player state (`lastSeq`, `inputStalled`, `inputMargin`, `inputLeadTicks`). `end` records the room finishing the
  match, and `relabel` a seat's new label for the ground records that name their dropper.
- **Seat changes show at once** (review 1102). The receive boundary hands a seat over when a join, resume or leave
  arrives, but the core spends the observation at the next tick. The store also follows the rows the match queues
  (`TickMatch.follow`'s second argument). Until the tick that spends a queued `join` or `leave`, a frame shows that seat
  under its new controller, with its lag and held input cleared, as the core will clear them. So a finish or a capture
  before the next tick archives the new controller. The completed tick's records then replace the overlay.
- **Records** are mapped by [`tick-records.ts`](../shared/simulation/tick-records.ts), which the mirror also calls. Each
  countdown is the deadline less the frame's tick. Effects and events come from T's facts, written by
  [`event-records.ts`](../shared/simulation/event-records.ts)' writers, which own serial assignment, event retention and
  effect lifetime for the store's stage as for a `Game`. Players are written in one
  field order, so a frame's JSON does not depend on the history of writes. The receive boundary's internals (its queue
  and sequence counters) are not frame fields ([26](26-recording-contract.md#schema-26-frames-from-the-cores-output-1344)).
- **The ground** is the store's own list, kept with the ground-list helpers, published and then indexed once
  (`indexGround`), so its frozen records enter their cells at once rather than one by one on the first query. Its grid
  follows each copy, so `framedItems` gives a viewer's nearby items from the newest list without the game's. An older
  frame's list is filtered whole, as before.
- **Poses.** A pose row carries the body's whole pose, which is adapter version 45: position, rotation, velocity,
  spin and the sleep flag. The change list lists a body when any of these changed since the step began, so a crate
  that turns in place is drawn turning. The store keeps every dynamic body's pose. A ground item whose pose changed
  only its rotation, motion or sleep keeps its published record.
- **Body identity** (`BodyLives`, kept by the store). A presentation body ID names one lifetime of a body, as the
  old world's identities did: a new ID when it enters the world, kept until it leaves. A removal ends a lifetime
  before a placement starts one, so a body that leaves and enters in one tick gets a new ID. Body IDs count across
  the match, and the wire key maps them outward (#1164).
- **Generations count within a lifetime:** 1 on entry, renewed by a warp. So `(id, generation)` changes whenever a
  viewer must not interpolate ([24.4](24.4-relational-data-model.md)). The old world's generation was one counter for
  the match, which no wire key maps, so a client could count placements and warps it never saw. A placement also
  marks the body `placed` on that tick's frame.
- **Shapes** are the specs the loader uploads: the actor templates, the loot template and the authored props. They
  are copied once and frozen, vertices included, so no frame can change another's shape or what the loader uploads
  (review 1046). A prop's `propId` is its authored index plus one.
- **Hooks.** A hook pulling is a tether from caster (`a`) to target (`b`). A hook flying is a flight at its tip. The
  tether ID is the hook ID, which the core allocates from 1 and keeps for the hook's life (review 1047).
- **No private `physics` block.** The old frame carried the old world's state beside its presentation; this one
  carries only the presentation. `playerView` reads `predictionTethered` and `hookActive` from the frame's whole
  tethers and flights when the block is absent. No reader of a recording reads the block
  ([26](26-recording-contract.md#schema-21-observations-as-commands-1283)).
- **Check.** `TickFrames.recordsOf` maps a whole core snapshot as the store maps changes. The fast bot match holds the
  store's records equal to it every tick, and the slow whole match every tenth tick, since a drift persists. A
  deliberately broken fold of moved items and traps fails the slow match at tick 800, which the small arena never
  reaches. Every tick of both matches, the frame's bodies are also held to the snapshot's poses and a view is projected
  from it: every player's in the fast match, one player's in turn in the slow one. The fast match also round-trips
  each frame through the recording's delta encoder and reader, and checks body identity across ticks. A hook case
  holds the flight, the tether and the caster's view, and that a teleport keeps the body's ID and renews its
  generation. A unit case holds lifetimes across removal and readmission, and another holds frozen, detached shapes.

### The room-facing match (3d.3)

The room-facing adapter in [`server/match.js`](../server/match.js) landed with a per-match opt-in through 3d.4c.
Inline and threaded service modes use it for every match from 3d.4d.

- **Setup.** `start()` sets up the core after the lobby's seats are taken and before the room records or publishes
  the first frame, so that frame is the core's tick 0 (review 1049). The loader reads the prepared seats and measured lag. Once started, a measurement queues an observation for the next tick.
- **The receive boundary.** `acceptInput`, `setViewLag`, `teleport`, `resume` and `leave` go through
  `TickBoundary` and record nothing themselves. They return the admitted input, the observation rows, the queued
  teleport row and the seat, or null when refused. A teleport's outcome is the next frame's (review 1041). What the
  match hands out is detached: the admitted input and `spent()` are copies.
- **Recording.** `spent()` gives the last tick's inbound queue as recorded commands
  ([26](26-recording-contract.md#schema-22-the-inbound-queue-as-commands-1283)). 3d.4c's room appends
  that queue to the matching tick's frame after its room-owned commands, and stops recording what the boundary queues.
  Rooms write schema 22. Schema 21 remains readable.
- **The roster** (#1346). Before the start, who holds each place and its status are the game's players. After it:
  - **Who controls a place** stays the game player's `bot`, the receive side's roster: a join, resume or leave changes
    it at once, as does each recorded join a replay applies. The frame store's overlay learns only the rows the boundary
    queues, and a replay's recorded joins reach the core only when the tick is stepped. So two joins applied in one tick
    take two places only because the first one's controller change is already visible (review 1109).
  - **Whether a place is active** is the core's status, from the frame store's player records (`TickFrames.players`),
    and after disposal the last frame's.
  - Open places, the role a join is offered and a join's admission share one selection (`openSlots` in `server/match.js`):
    a place a bot controls whose status is active. `joinGame` takes the slot chosen, so availability and admission
    cannot disagree (review 1108). The roster lists the places people control, and the result counts escaped statuses.
  - Names, roles and kits stay the game's roster, as the frame store reads them too.
- **Maps after the start.** A player's map payload takes its gates and items from the frame it is sent with, every item
  at its place. The `map()` query also takes the frame's traps. The recording's map stays the opening state (26).
- **Frames** are `TickFrames`', without `rng` and `scatterSerial` (review 1047). Old frames keep them for the frozen
  fixture.
- **The nominated target.** `PlayerInput.target` (`WIRE_VERSION` 12, [24](24-networking-privacy.md)) names an
  extraction, a gate by slot, a station by ID or an item by outward ID. `inputOf` maps it, the item through the
  match's wire key. A nomination that fails allows no other gesture, since R8 never falls through: the interaction
  and any rail destination go, and movement and combat stand (review 1049). It fails when it is malformed (the
  sanitizer) or names nothing on the map (the boundary). An item's ID must lie in the wire's ID domain, keyed or not,
  so it always fits the codec. No client sends a target yet; choosing one in the client is its own work.

### The opt-in room tick (3d.4c)

- **First frame.** Players keep the waiting yard until the core starts. Watchers receive the match map and core

- **Input admission.** Protocol validation sanitizes transport input once. Both the match and waiting area admit

  warps. An admitted teleport while paused explicitly steps one T for acceptance or refusal and recording; a paused
  scheduler wake adds no ticks. The room replies from the committed result and publishes a frame while paused
  when the warp commits or the match finishes (reviews 1041 and 1060). 3d.4c raises the adapter to version 47.

### Core changes before the switch (3d.4a)

Two core changes agreed in reviews 1049 and 1050 landed in adapter version 46.

- **The opening discovery.** [`tick/mod.rs`](../rust/core/src/tick/mod.rs) `Scenario::start` samples every active
  contestant at its starting pose before the first tick, as the old game discovers when it creates a player
  ([`state.ts`](../shared/simulation/state.ts)). The mirror loads the core's memory at the start, so tick 0's frame
  and T1's bot intent agree on what each contestant already knows. A test holds the core's opening memory equal to
  the old game's: cells discovered, seen and surveyed, and the items remembered.
- **Before the session starts.** `createGameRecord` can sample opening discovery for setup projections when given
  a sight binding. `snapshot(game)` can still produce a setup frame before a session exists, and
  [`tests/discovery.test.js`](../tests/discovery.test.js) checks that a projection from a bare record includes the
  viewer's opening discovery. Starting a session replaces the setup memory with the Rust match's opening memory.
- **Samples read the ground records** (#1301's rule that the record is truth). A line-of-sight sample sees an item
  where its body is, or at its stored spot while it has none. The map's loot starts bodiless, so the opening sample
  would otherwise see none of it, and the old game's sees all of it.
- **An unresolved nomination.** The codec's `Target` gains `unresolved` (tag 4): a nomination the receive boundary
  could not map, malformed or naming nothing on the map. A pressed interact with it is rejected with
  `Rejection::Interaction(Some(Unresolved))`, and nothing else is tried, a rail destination included (R8). Unpressed,
  it asks nothing and is not rejected, but still takes the rail away. Movement and combat stand.
  - The sanitizer marks a pressed, malformed nomination `{ kind: 'unresolved' }` and clears the button for the
    old tick. Validated admission preserves this marker ([3d.4c](#the-opt-in-room-tick-3d4c)).
    From the wire the mark is malformed like any other target, so a released button never becomes a press (review
    1055). A test sends malformed nominations through both, pressed to the core's rejection and released to nothing.
  - The recording names it as sent, `target: { kind: 'unresolved' }`
    ([26](26-recording-contract.md#schema-22-the-inbound-queue-as-commands-1283)).
  - The rejection reaches T's events. Presenting rejections to a client is not done on either path yet.
- **Cost, for the cutover bench.** Bots now remember the map's bodiless loot, as the old game's bots do. On arena 9's
  whole match the slow test went from 13 to 30 s. The test's oracle now decodes memory only for the contestants a
  tick's discovery names, plus everyone every hundredth tick; before that it took 59 s. The rest is in play: the
  core's discovery takes 4.2 s of the match (the line-of-sight ground scan over every record), and the mirror's
  refresh decodes and rewrites a contestant's whole memory. 3d.4d's bench measures both against 42.76. A change
  export of memory and a spatial index over the ground records are the fallbacks.

### The cutover (3d.4d)

`createMatch` and the shared in-process `step` both use `createTickSession`. The room starts it after seating
and publishes tick 0. In-process scenarios start it on their first step, or explicitly to capture tick 0.
The seven-phase driver and `tick_begin`/`tick_finish` exports are removed. WASM adapter version 48
identifies the reduced API. Wire version 13 identifies the live cutover. The recorded schema is 22,
and the minimum replay reader stays at 20.

The setup world validates and synchronizes positions while preparing a match. Live bots read
authored prop poses from the mirror. A committed developer warp clears the actor's route and releases
hooks at either relocated endpoint before the solve. The physics lab directly exercises a separate test
world for contact diagnostics, impulses and spring rigs.

Native tests hold the rule and ordering choices. The adapter cases hold changes, frames, stable IDs,
projection privacy and recordings. The retired phase-wrapper parity and store-reconciliation tests
are superseded by the native rule tests and the whole-match mirror comparison. The accepted order and
timing differences are exercised in the recaptured [characterization fixture](../tests/fixtures/README.md).
The paired benchmark is under [42.78](42.78-tick-cutover-benchmark.md).

### Core bot intent (4e)

The match derives built-in bot commands in roster order from committed T−1 poses, visible props,
discovery memory, gates, and cues. A queued seat change selects T's controller before intent is
derived. Gameplay observations such as developer teleports take effect during intake, after
planning. Commands still go through the core's one-command spend and held-input rules. The Node
boundary stamps and admits client input, including external bot clients.

Private snapshots query remaining bot routes in a batch when requested (#1338). The completed tick,
ordinary room frames and new recordings omit these routes. Core route and memory queries also
support scenario witnesses. Frames are built from the core's output (#1344, [3d.3](#frames-3d3)). No session runs the
mirror (#1345, #1346); its own checks remain until #1346 removes it.

## DOOR

The direction follows the [DOOR primer](references/door-primer.md)'s ideals, as Corey asked on #1276. The primer
creates no requirements; this section records how this design draws on it.

- **System events versus model events.** The inbound queue admits system events (commands, observations) in
  order. Events are model events, published only after apply commits.
- **Bounded cascades.** The cascade rule fixes the one chain within a tick and sends everything else to T+1.
- **No two authoritative copies.** The mirror goes (#1284).
- **Determinism through ordered admission and controlled writers.** Resolve cannot write; one apply writes.
- **Data-oriented where the work is repeated.** Per-kind tables, the batched solve and projectile sweeps.
- **Relational where it's an association.** Ownership, carried items and hook endpoints, per 24.4.
- **Cohesive behaviour per mechanic.** Each mechanic is a module with its own declarations.

**Where DOOR cautions apply, and the guardrails here:**
- **The uniform pipeline needs a reason.** DOOR warns against making every mutation a command when it solves
  nothing. Here the reason is recorded: 27.1's 27 order-dependent rows and the flip's stops are exactly the
  ordering problems the primer names as justifying intents and a controlled writer.
- **Immediate results stay direct.** Intake writes directly where an actor's own command needs its result at once
  (aim, slots, spends), and a mechanic's private computation within resolve (a spider's step) needs no effect.
- **No ceremony.** The effect vocabulary stays small, and mechanic declarations stay module structure, not a
  registry. A coordination layer that costs more than it saves is not built (the primer's decision rule).
