# 27.2. Tick architecture (#1282)

Up: [27](27-rust-path.md#the-state-flip). Tracker: #1279. Inventory of today's tick:
[27.1](27.1-tick-mechanic-inventory.md). Corey's answers: [17.7](17.7-tick-resolution.md). The design debate that
settled the details: #1288 (ledger in comment 18000, confirmed in 18001). Resolution model: #1276, which this
document closes.

This is the governing design for the simulation tick. Every mechanic enters through it. It replaces the seven
phases that grew one mechanic at a time and their stops, resumes and "removed earlier this tick" checks. Built as
[Build approach](#build-approach) describes, it replaces the old tick in one cutover.

## Principles

- **Earliest consistent tick.** A thing happens at the earliest tick consistent with this model. No exception to
  the model is made for performance unless the player's experience truly depends on it (Corey, 17.7 follow-up 3).
- **Simultaneous resolution.** Everything a tick resolves reads one frozen state and is applied together. No
  outcome depends on the order actors, traps or items are visited in.
- **Nothing new is visible until the next tick**, except what an actor's own command creates in intake (A1).
- **Qualitative over exact equivalence.** Behaviour changes where this design says so. The old tick is a source
  for what must be covered, not a target to match.

## Stages

Each tick runs four stages (#1288 A1).

1. **Intake.** Validates each command in the inbound queue against the state before intake, and writes only:
   - carried events from T−1 that change tick-start attributes, such as the gladiator kill reward (level +1 up to
     4, max HP +20, HP +45, skill cooldown reset);
   - an actor's own equipment and aim: aim, slot selection, slot rearrangement, and a reload whose deadline has
     passed;
   - the deadlines and resource spends of accepted commands: weapon and skill cooldowns, ammo, reload start, a
     utility's charge (its heal or shield is an effect, merged in apply);
   - projectiles and hook tips created by commands, which take part in T's solve and sweep;
   - inputs to the solve: motor, boost, hook cancel, pulling hooks' tether shortening and revalidation, and the
     impulses queued by T−1.

   Manual drops, interaction, pickups, extraction and casts are validated here and carried to resolve as intents.
   **S0**, the state after intake, is frozen.
2. **Solve.** One batched Rapier step produces post-solve poses and swept paths.
3. **Resolve.** Reads S0's discrete state, the solved paths and the rewound view (R3). It emits events and effects
   and writes nothing. The framework enforces this.
4. **Apply.** Merges effects, settles conflicts and writes the next state, S1, in a fixed order ([Apply](#apply)).

Bots produce commands like players do, from the state before intake, which is T−1's applied state (R11). Today's
two calls a tick (27, D4) become one: phase 1's work moves to T−1's apply (respawns, arrivals) and to intake
(hook prepare, carried events). Timers stop being decremented at all ([State](#state)).

## Commands, events and effects

Three kinds of thing (#1288 A2; Corey, 17.7 follow-ups 1–2):
- **Command:** an intent, validated in intake. A rejected one-shot command emits a rejection event, so the client
  learns why. A held `attack` that loses to another weapon action emits none.
- **Event:** an immutable fact of tick T: a hit landed, a contact, a pulse, an elimination, a kill credited, an
  escape, a placement. Resolve and apply both produce events. **They are published only after apply commits**, in
  canonical order (A6), to the projection, the recording and the bots. A resolve event whose effect lost in apply
  (a pickup claim that lost its contest, say) is published as the outcome that happened, never as a success.
- **Effect:** a typed write to state, with one merge rule per target field:

| Merge class | Effects | Rule |
| --- | --- | --- |
| Additive | damage, heal and shield, impulse | summed; heals and shields first (clamped to their maximum), then damage from shield, then HP |
| Status | `ExtendStatus(kind, untilTick)`, `ClearStatus(kind)` | latest deadline wins; a clear outranks a same-tick extend of the same kind (firing breaks cloak) |
| Exclusive claim | pickup or transfer, extraction slot, placement, gate state | arbitrated in apply step 3 or 4 |
| Lifecycle | spawn, despawn, warp | applied in apply steps 4–5 |

The vocabulary stays this small. A new mechanic uses these classes. A new class needs a reason this document
records.

**The cascade rule.** Within T, only the fixed chain in [Apply](#apply) runs. Any other consequence of an event
goes onto T+1's inbound queue: the kill reward, a trap's reaction, anything that needs a new query. There is no
recursion within a tick.

## Apply

Apply runs in this order (#1288 A3):

1. **Merge** additive and status effects per target.
2. **Eliminations.** An actor whose HP reaches zero is eliminated. One kill-credit holder is drawn (A6 hash) from
   the sources of lethal hits, whether or not each source is still alive. Other hitters get assists. Mandatory
   death drops are requested.
3. **Exclusive claims, survivors only.** Survival is settled before anything is allocated (Corey, 17.7 follow-up
   8), so a contestant killed on the tick they extract does not escape.
   - **Extraction slots:** closest eligible contestant, then the A6 hash.
   - **Pickups:** all (claimant, item) pairs sorted by (claim class, distance, A6 hash). Explicit claims
     (interact, swap) come before automatic pickup. Each pair transfers what fits the claimant's remaining
     capacity and the item's remaining count, which covers partial stacks and magazines.
   - **Swaps:** a swap's outgoing drop is validated and its spot reserved when its pair is reached. If no spot or
     capacity exists, the swap fails and the ground item stays available to the next pair.
   - **Gates:** R8. A gate close commits here, before placement.
4. **Placement** of the remaining spawns, per R4: death drops, manual drops, respawns, arrivals, trap shots. Spots
   reserved by swaps are excluded.
5. **Removals and status changes**: escaped, eliminated, transit. Rapier bodies, gates and invalidated hooks are
   synchronized here, so S1 and the physics world agree.
6. **Deadlines** are written.
7. **T+1's carried events** are queued, then the terminal check runs (R12).

## State

(#1288 A4.)
- **Stored:** per-kind tables in the core, keyed by stable ID: actors, items, projectiles, hooks, gates, traps,
  stations. They follow [24.4](24.4-relational-data-model.md)'s relational model.
- **Timers are deadlines:** `readyAt`, `activeFrom`, `expiresAt`, as absolute ticks. Nothing is decremented per
  tick. An N-tick cooldown is `readyAt = setTick + N` and is ready when `T >= readyAt`.
- **Derived, never truth:** spatial indexes, occupancy, visibility, rewind history.
- **Shared:** the map and its static geometry, immutable for the match.
- **One copy.** No mirror. Per-tick cost follows the active set, never the map's size.

## Boundary

(#1288 A5; Corey, 17.7 follow-up 2.)
- **In:** T's inbound queue holds three kinds of item, all recorded:
  1. player and bot commands stamped T, under the existing stamp, acknowledgment and hold contract
     ([24](24-networking-privacy.md));
  2. events carried from T−1;
  3. observations: measured view lag, input lead, join, leave, dev teleport.

  Lag stays server-measured, but enters as a recorded observation and no longer as a write to player state
  between ticks (today `setViewLag`, `server/match.js`). A per-command view tick (#1282 N10) is deferred.
- **Out:** events, per-viewer projections, recording frames (S1 plus T's inbound queue plus apply's physics
  discontinuity markers), and snapshots on request. Until #1284 removes the mirror, apply also emits the change
  list Node's mirror applies: changed records whole, removed IDs, and events. It is one list, so the mirror's
  per-phase appliers and their ordering rules go.

**Wire and recording.** The nominated interaction target (R8) adds an optional `PlayerInput` field, which bumps
`WIRE_VERSION`. Observations recorded as commands change the recording schema ([26](26-recording-contract.md)).

## Determinism

(#1288 A6.)
- **One canonical order per kind,** everywhere:
  - actors by (kind, numeric stable ID), replacing both the string sort and roster order (D24);
  - traps by authored map index;
  - gates by authored gate index;
  - projectiles and ground items by numeric ID.
- **IDs are allocated only in apply,** in canonical event order.
- **Tie-breaks** use a stateless hash, `hash(matchSeed, tick, contestKey, entityId)`. Drop scatter phases use
  `hash(matchSeed, tick, "scatter", dropperId, slotOrFamily, copyIndex)`. Neither consumes the match RNG, so a
  refused plan never shifts a later one.
- **Publication** follows canonical order. Event retention is unchanged.

## Rules

Each rule below is agreed in #1288; the D-numbers are 27.1's rows.

- **Commands in one input record (R1; D05).** At most one weapon-slot action per tick, with precedence
  drop of the selected slot > reload > slot change > attack. Dropping another slot, or `dropAmmo` of another
  family, is independent. Within one family, `dropAmmo` beats reload. A skill is independent of weapon actions.
- **Newly active actors (R2; D01).** An actor activated in T's apply first spends input stamped T+1. Input
  stamped T for an inactive actor is discarded, never held. Held-input repeat starts after the first spent
  input.
- **Lag compensation (R3; D11, D13).** One query, `rewound(viewer, targetTick)` with
  `targetTick = T − clamp(viewLagTicks, 0, MAX_REWIND_TICKS)`. It returns target poses and gate states at
  `targetTick`; static geometry is current, and the caster's own origin is its post-solve pose.
  - It decides **eligibility** (range, arc, line of sight) for instant attacks (gladiator melee, Warden pulse)
    and interactions. **Contention** uses current post-solve positions.
  - It is captured after apply. Missing history falls back to the target's current pose.
  - Melee target ties use the A6 hash. The Warden is one pulse for now. Travel-time projectiles stay
    uncompensated (24).
- **Spawn and placement (R4; D02, D06, D18, D25).**
  - Physical bodies are placed without overlap. Query-only shapes (bullets, hook tips) may overlap.
  - Requests are ordered by a seeded permutation (A6 hash), then placed greedily at the nearest valid point within
    each kind's radius.
  - **Failure:** respawns and arrivals stay pending, with the actor inactive, and retry next tick. Manual drops
    and swaps are refused with a rejection event, and the item stays held.
  - **Death drops** are mandatory: they bypass ground capacity and fall back to the death origin when no clear
    point exists. This is the one exception to non-overlapping placement. The body still goes through admission
    (D25), and an item awaiting its body cannot be claimed.
  - Transit does not reserve its landing. Motor-surface and floor-drag overlaps use highest priority, then
    authored surface ID.
- **Physics cutoffs (R5; D07, D08, D22).**
  - Impulses from resolve feed T+1's solve. A mine blast reaches surviving bodies in S0, not same-tick death drops.
  - Warps (a transit landing, a teleport) commit in apply. T's queries use T's solved paths.
  - A hook tip that hits in T's resolve attaches and starts pulling in T's apply, and its rope acts in T+1's solve.
    `PHASE_PENDING` is retired.
  - A hook whose endpoint is eliminated or departs in T detaches in apply.
- **Projectiles (R6; D09).** `expiresAt = spawnTick + life − 1`, which keeps today's `life − 1` sweeps and so
  today's range. A projectile sweeps while `T < expiresAt` and is removed in the apply of its last sweep tick.
  - Command-fired projectiles and hook tips have `spawnTick = T`. Turret shots have `spawnTick = T + 1`.
  - Geometry wins an exact tie with an actor, and ties between actors use the A6 hash.
  - An actor eliminated in T still counts as first contact and consumes a one-hit projectile.
- **Casts (R7; D10).** Every accepted cast in T resolves against S0 and the solved paths, including a skill and an
  attack together, and including a caster killed in T. Their effects merge, so no order within the actor is
  needed. Stun on a lethal hit counts as applied, with `activeFrom = T + 1` (17.7, 17:47).
- **Interaction (R8; D13, D16, D17).**
  - `PlayerInput` may nominate a target ID. If it does, the server validates only that target (R3 eligibility,
    S0 availability) and rejects it on failure without falling through. Clients omit targets they know are
    ineligible.
  - With no nomination, eligible targets are ranked by **provisional** priority tiers (tier 1: extraction,
    charging start; tier 2: gates, rail transit, full-inventory swap), then distance, then the A6 hash. The tiers
    may be rearranged from feedback (Corey, 17.7, 18:14).
  - Opposing requests on one gate are an exclusive claim, decided by the A6 hash. Gate-close occupancy checks the
    post-solve poses of surviving, non-departed actors and dynamic props.
  - A key collected in T cannot pay for T's attempt. A failed attempt emits an event, and discovery learns the lock
    at T+1.
  - Explicit claims outrank automatic pickup.
- **Charge, detection and cloak (R9; D19).** Charging starts in T's apply, first progresses at T+1, and a charge
  completed in T first funds extraction at T+1. Active charging cancels in apply, without progress, on movement
  beyond jitter, lost reach or line of sight, extraction, transit or elimination. Sensors read S0's cloak and sneak
  and the post-solve position. A reveal applies in apply with `activeFrom = T + 1`.
- **Hazards and traps (R10; D20, D21, D22).**
  - Wall and area damage both apply and sum.
  - Traps read S0's deadlines and active targets and the post-solve positions. Nearest-target ties use the A6
    hash, and a trap never retargets within T.
  - A spider computes its step and grapple from its stepped pose inside its own resolve; other queries see it at
    S0, and its move commits in apply. Its grapple effect lands at the victim's post-solve pose, lethal or not.
  - Turret shots are placed in apply and first sweep at T+1.
- **Bots and cues (R11; D04, D26, D27).**
  - Intent reads the state before intake. What is observed in T first affects intent at T+1.
  - Discovery and the detour-budget stagger rotate the canonical order's starting point by tick, instead of using
    roster offsets.
  - Blocker distance ties use canonical entity order. Remembered loot and frontier ties use item ID or cell
    index, not insertion order.
  - A cue emitted in T is published in T's events and reaches bots at T+1.
- **Terminal, rewind and recording (R12; D23).** A started tick always completes. The time limit gates the next
  tick, and also ends the match at the close of the final one.
  - At the end of apply, if no slots remain, no contestant is active, or time is up, remaining contestants are
    stranded and their bodies removed.
  - Then, in order: the rewind frame is captured, discovery samples surviving active contestants, and the frame
    is recorded and the projections built.
  - Per-tick frame and latest-state delivery are unchanged.

## How a mechanic enters

(#1288 A7.) A mechanic declares:
- the commands it accepts and how intake validates them;
- whether it writes inputs to the solve;
- each query, and the view it reads: S0, solved paths, or rewound;
- the events it emits;
- its effects and their merge classes;
- the exclusive resources it claims;
- its deadlines and its spawns.

These declarations are the mechanic's module structure and its tests. They are not a registry or a framework of
their own, unless one is later shown to be needed ([DOOR](#door)).

## Test API

(#1288 A8.)
- A scenario builder arranges state. A test submits stamped commands, steps the tick, and asserts on the events
  first, then on the state.
- Resolve is testable as a pure function: (S0, solved paths, intents) → (events, effects).
- #1282's acceptance examples (comments 17961 and 17968, with 17.7's corrections) become tests.
- Test cost statements follow [31](31-verification.md#test-cost).

## Build approach

**Decided (Corey, 2026-11-22, 17.7 follow-ups 9–10): build dark, cut over once.**

1. **The new tick is new code in the core,** not wired into the game. It merges to `main` in pieces that compile
   and pass their own tests, written against the test API. `main` stays green for everyone else.
2. **The old tick is frozen and keeps the game playable.** It is not updated or compared against. It is kept only
   to check that everything it did has been accounted for. The feature freeze keeps everything else off it.
3. **An accounting ledger drives completeness.** Every mechanic in 27.1's census and every D-row maps to new code
   or to a recorded behaviour change. It lives in [Accounting](#accounting), and each build PR updates its rows.
4. **One cutover PR** switches the game to the new tick and deletes the old one. It also:
   - bumps `WIRE_VERSION` and the recording schema;
   - triages the old tests once, porting, rewriting or deleting each one (Corey, 2026-11-17, [17.4](17.4-live-service.md) #18);
   - re-baselines the frozen fixture once, deliberately, for the intended gameplay changes;
   - benches against [42.76](42.76-state-flip-benchmark.md), with a paired same-session baseline as
     [42.77](42.77-tick-inventory-checkpoint.md) requires.

This relaxes #1279's "the game stays playable throughout": `main` stays playable, on the old tick, until the
cutover. Comparing outputs would mostly flag the changes made on purpose, which is why the build does without it.

**Staging for #1283:**
- **3a. Framework.** The state tables, the stage runner and its read-only resolve, the effect classes and apply's
  order, the canonical orders and the hash, the inbound queue, and the test API.
- **3b. Mechanics, in groups.** Each group is a PR that updates its ledger rows:
  1. movement and solve inputs: motor, boost, hooks;
  2. projectiles and combat: fire, melee, Warden, Specter, damage, elimination, credit;
  3. items: drops, ammo, reload, pickups, swaps;
  4. interaction: gates, keys, extraction, charging, transit;
  5. hazards and traps;
  6. respawn, arrival and placement;
  7. terminal, rewind and discovery output.
- **3c. Output.** The change list for the mirror, recording frames, observations.
- **3d. Cutover.**

The framework (3a) is lead work. Mechanic groups can go to implementer workers with [32](32-delegation.md)
briefs.

### Framework entry point (3a)

[`rust/core/src/tick`](../rust/core/src/tick/mod.rs) is the native Rust entry point for the new tick.
`Scenario` seeds the tables and Rapier bodies. A match takes admitted stamped commands and observations,
and returns each completed tick's inbound records, solved paths and committed events. The adapter will supply
receive-side sequence, lead and supersession handling when it builds those records in 3c. The core spends one
command per active actor, updates acknowledgment on spend and repeats only held movement, aim and sneak.

Intake reads the pre-intake tables and plans its writes. Resolve borrows the post-intake tables and the paths from
one Rapier step. A single apply merges numeric and status effects, marks eliminations, passes survivors' claims
to the rule set, commits placements and lifecycle changes, writes deadlines, queues carried events, and checks
the terminal condition. Rules supply typed intents, claims and placement requests. Event publication and runtime
ID allocation use canonical keys even when arbitration visits placements in another order.

The native tests exercise these stage boundaries with a small rule set and real Rapier bodies. Mechanic rules
and their player-visible acceptance examples enter with 3b. Output adaptation enters in 3c.

### Movement and hooks (3b.1)

[`tick/movement.rs`](../rust/core/src/tick/movement.rs) builds motors from the actor's pre-solve position,
stamped or held input, and status deadlines. A ready Overdrive press sets its boost window and skill deadline
in intake and affects that same motor. Idle actors get bounded braking. Authored motor and drag rectangles use
the same priority and ID ordering. Each query considers local surface candidates from an index built at setup.

Intake cancels, revalidates and shortens existing tethers. A new tip has a command-local identity through its
first sweep, so it can hit in T. Apply gives a surviving hook its stable ID and commits it directly as pulling
when it hits. The first tether force is in T+1. A cap contest among eligible launch commands uses the A6 score
after intake releases have freed their places. [`tick/hook.rs`](../rust/core/src/tick/hook.rs) shares the swept
geometry query with the old tick. That query uses the native state's current gate rows and solved solid prop
poses for tip flight. Tether preparation uses pre-solve poses and the same solid geometry policy.

[`tick/solve.rs`](../rust/core/src/tick/solve.rs) feeds motors, impulses and bounded ropes to one Rapier batch.
It decodes paths, stable contact IDs and broken tethers. Apply drops hooks whose endpoints depart or relocate.

### Combat (3b.2)

[`tick/combat.rs`](../rust/core/src/tick/combat.rs) composes combat with movement and hooks. Intake spends a
round from an equipped firearm, sets its weapon deadline, and gives each pellet a command-local ordinal.
[`tick/projectile.rs`](../rust/core/src/tick/projectile.rs) sweeps both new and persistent projectiles against
shot-blocking geometry and solved actor paths. Apply allocates stable IDs to surviving launches in spread
order. A first hit consumes the projectile even if other effects eliminate that target in the same tick.

Melee and Warden use [`tick/rewind.rs`](../rust/core/src/tick/rewind.rs) for historical target poses and gate
states. Their origin is the caster's post-solve pose. Melee ranks eligible targets by current distance and
then the A6 score. Warden stun and Specter reveal start at T+1. Shooting clears cloak in apply.

[`tick/apply.rs`](../rust/core/src/tick/apply.rs) merges damage, records aggression and marks deaths before
claims. For a fatal merge, the A6 score draws credit from opposing or friendly player sources that dealt
positive damage to the victim in T. Other player hitters receive assists. The same ranking rule, with its own
contest key, selects a single aggressor for a target hit by several players. Credit can go to an eliminated
source. A credited gladiator's reward is carried to the next intake and can reset a skill before its command
is validated.

## DOOR

The direction follows the [DOOR primer](references/door-primer.md)'s ideals, as Corey asked on #1276. The primer
creates no requirements; this section records how this design draws on it.

- **System events versus model events.** The inbound queue admits system events (commands, observations) in
  order. Events are model events, published only after apply commits.
- **Bounded cascades.** The cascade rule fixes the one chain within a tick and sends everything else to T+1.
- **No two authoritative copies.** The mirror goes (#1284).
- **Determinism through ordered admission and controlled writers.** Resolve cannot write; one apply writes.
- **Data-oriented where the work is repeated.** Per-kind tables, the batched solve and projectile sweeps.
- **Relational where it's an association.** Ownership, carried items and hook endpoints, per 24.4.
- **Cohesive behaviour per mechanic.** Each mechanic is a module with its own declarations.

**Where DOOR cautions apply, and the guardrails here:**
- **The uniform pipeline needs a reason.** DOOR warns against making every mutation a command when it solves
  nothing. Here the reason is recorded: 27.1's 27 order-dependent rows and the flip's stops are exactly the
  ordering problems the primer names as justifying intents and a controlled writer.
- **Immediate results stay direct.** Intake writes directly where an actor's own command needs its result at once
  (aim, slots, spends), and a mechanic's private computation within resolve (a spider's step) needs no effect.
- **No ceremony.** The effect vocabulary stays small, and mechanic declarations stay module structure, not a
  registry. A coordination layer that costs more than it saves is not built (the primer's decision rule).
