# 42.62. Discovery in the Rust core: pack, run and unpack per sample (#1210)

Up: [42](42-performance-history.md). Design: [27](27-rust-path.md#the-state-flip), step 2 (D1). The rule is
`rust/core/src/discovery.rs`; `discover` in `shared/discovery.ts` packs what a sample reads near the eye, makes one
call through `shared/sight-core.ts`, and applies what it learned to the memory, which stays in JavaScript. Both
runs passed `characterization-physics` and its `-bots` variant unchanged.

## Finding

**Discovery costs about 14% less per tick, and the crossing is about 2% of its TypeScript cost.**

| Discovery | `sim.discovery` mean | p95 | Polygon or core sample | JavaScript around it | Whole tick mean |
| --- | ---: | ---: | ---: | ---: | ---: |
| TypeScript rule, core polygon | 0.413–0.416 ms | 0.755–0.785 ms | polygon 0.344–0.350 ms | 0.064–0.072 ms | 2.45–2.64 ms |
| Core sample | 0.349–0.382 ms | 0.676–0.774 ms | sample 0.313–0.328 ms | 0.037–0.054 ms | 2.38–2.63 ms |

- **The budget (42.58): crossing overhead at most 10% of the module's TypeScript cost per tick.** The TypeScript
  cost is the first row's 0.41 ms. The crossing is the input writes, 5.4–8.8 µs a tick (1.3–2.2%; timed in the
  last two runs), plus one call and one output view, each about 0.03 µs (42.58).
- **"JavaScript around it"** is the part of `sim.discovery` outside the core: in the first row, the rule itself
  (cells, beacons, roof tests, `litPoint`, item and door tests); in the second, the near-eye queries (`itemsNear`,
  `gatesNear`, the remembered items near the eye), the input writes and applying the result to the memory's sets
  and maps. Both rows do the queries and the memory writes.
- **The core sample is cheaper than the polygon it replaced**, though it also runs the rule: the polygon's points
  are no longer built into objects (about 22 µs a polygon, 42.58), and `litPoint` and the roof tests run in Rust.
- **Samples:** 0.73 per tick in both, each with line of sight (bots), and each built its polygon.
- **The whole tick** moves within its run-to-run spread, as in 42.61: discovery is about 15% of it.

**Packing follows the eye, not the map (#635).** A sample packs the items and doors within its reach, the
remembered items near the eye (`ItemMemory.near` and the power cells), and the seen flags of the reach window.
The map's cells, landmarks and roofs are uploaded once per map. **One exception, inherited from sight:** a sample
with line of sight writes the open mask of every gate on the map, as `visibilityPolygon` did before it (42.58's
"per-tick input writes"). It was one byte per gate. **Closed by #1214 stage 6a** (27): the core keeps a game's door
state, so a sample writes no mask ([42.74](42.74-door-state-core.md)).

## Method

- **The script.** `node tools/discovery/bench-discovery.mjs <root> <label>`: content-7, seed 4217, the default live
  size, bots; 1,000 ticks after 100 of warmup, three games per run, under the machine bench lock. It reads the
  profiler's `sim.discovery` per tick, and wraps the process's core binding to time the polygon (TypeScript rule)
  or the sample (core), and the sample's input writes.
- **Runs.** One baseline run on `forgejo/main` at 8ed51346 (the TypeScript rule), then three runs of the port, in
  sequence. The ranges are over the three games of the baseline run and the nine of the port's.
- Machine: Ryzen 9 5900X, Node 24.15.0, Windows 11, 2026-11-19.

## Limits

- **One baseline run.** Its three games agree within 1% on discovery, and the port's nine all beat them.
- **The profiler is on,** which adds its own `performance.now()` pairs to both rows alike.
- **One map size and content.** Larger maps change the reach window only where the eye is near an edge. The
  open-gate mask grew with the map's gates until #1214 stage 6a removed it.
- **Node only.** The client does not run discovery.
