# 42.57. The Rust edge's CPU in a live match (#1095)

Up: [42](42-performance-history.md). Design: [24.5](24.5-transport.md) stage 1. The probe before it, on the Node
addon, is [42.56](42.56-transport-probe.md).

## Finding

**The edge costs little.** A release build carried 1, 4 and 8 Chrome players on WebTransport through a live match
of the default room, every player walking. Its CPU, as a share of one core over 30 s:

| Sessions | Edge CPU | Share of one core |
| --- | --- | --- |
| 1 | 109 ms | 0.36% |
| 4 | 1,188 ms | 3.9% |
| 8 | 1,438 ms | 4.7% |

- **What it covers.** Stage 1 only: every message on one reliable stream, today's frames unchanged. Datagrams
  (stages 2 and 3) will change the per-packet work.
- **Its limits.** One run per count, on loopback. Frames grow as more players are in view, so cost per session is
  not constant, and 4 against 8 is within run-to-run noise. The question it answers is whether the edge is a cost
  to plan around at a LAN host's scale: it is not.

## Method

- **Environment.** The development machine (Windows 11), Node 24, headless Chrome through Playwright, and the edge
  built with `cargo build --release`. 2026-11-17.
- **The run.** A server with `edgeLink: 0` and rooms on the host thread. The edge was spawned with `--port 0`, and
  every page was opened with `?transport=wt`, so none could fall back. The owner started the match, and every page
  then held D.
- **CPU.** The edge process's `TotalProcessorTime` was read before and after 30 s.
- **The script.** It was an ad-hoc script outside the repository, built on `tests/edge.browser.mjs`'s setup. Rerun
  the same way, at a scale #907 asks about, before planning capacity on these numbers.
