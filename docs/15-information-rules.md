# 15. Information rules

What a viewer may know is a gameplay rule, not a rendering detail. F-09 and F-10
in [13](13-accepted-features.md) govern viewport-wide sight and remembered gates.
The mechanism that enforces these rules is in [24](24-networking-privacy.md).

The server uses a bounded potential radius for transport; it is not a rendered circular fog boundary.

The server sends each player the state that could become relevant within the configured visibility radius, plus revealed information. The client applies actual line of sight using the same shared obstacle geometry. Static terrain remains drawn and falls into shadow; actors, pickups, projectiles, and transient effects are withheld when they are not visible. A directed spectator/presenter feed permits omniscient viewing and must not be available to a player holding a slot. Its presentation also supports following in a player's sight (F-19); the mode and transition policy is in [24](24-networking-privacy.md). The dev view is the one deliberate exception: a development tool, offered only when the server is started with a `DEV_TOOLS` policy that permits it ([24](24-networking-privacy.md#dev-view)), and then to a player as well. A server started without one offers it to nobody.

Player projections must not include private inventory, ability timers, bot status, path state, input bookkeeping, RNG state, or replay internals. A live projection may be narrower than the recorded frame but must never change values it does include. Tests must compare live projections against the recording field by field.

Camera coverage is capped at 2,400 x 1,600 world units, and the server's potential-visibility radius includes its diagonal plus a 250-unit margin. The sight polygon covers the viewport rather than imposing a circular cutoff. Obstacles conceal dynamic actors, including allies, except explicit gladiator sensor/scan reveals. Static geometry stays visible with shade. Gate memory is local historical presentation; authoritative collision uses actual gate state. This is not a production anti-cheat system: potential state and actual gates remain available to a modified client within the existing trust model.

Contestants know only the map geometry and features they have discovered (#275); gladiators have full map access. The contestant minimap reflects this by clipping terrain to discovered coarse cells and drawing stations, chargers, and exits only when discovered (#274), while gladiators and directed viewers retain full map access. The server authoritatively tracks coarse grid discovery (192 world units, 4x4 map cells) for every active contestant, sampling every 10 ticks staggered by player (`shared/discovery.ts`). What is learned splits by kind (17.3 #16): **world geometry** is learned from the view window, so every coarse cell whose centre lies within the largest client viewport (2400 × 1600, `DISCOVERY_VIEW`) around the contestant is discovered, through walls and roofs; **dynamic state** (loot, and in time traps and interactables' state) needs line of sight. Chargers, stations and exits count as discovered once their grid cell is. Chargers, transit stations and the exit carry a beacon: each one's own cell is discovered from within 4,000 units (`BEACON_RADIUS`) regardless of walls and roofs, which reveals the landmark and not the way to it (#230). Discovery is private to each contestant, projected only in their own player projection via keyframe-then-changes deltas, and omitted from replay recordings where it can be reconstructed by a pure fold over recorded frames.

Heard gunfire (#684, [14](14-match-rules.md#heard-gunfire)) is the one kind of dynamic information that passes walls and roofs, and it reveals an area, not an actor: a hearer learns the centre of the coarse discovery cell a shot came from, for a few seconds. It is private to the hearer, projected only in their own player projection (`heard`, each cue's cell centre and the ticks it was heard and fades), never in another player's record, and never in a directed, spectator or dev view, which, as with discovery, do not recreate a player's private history. It stays out of snapshots and recordings: a shot's projectiles and positions are recorded, so a reader can approximate the cues, but not exactly, since hearers' positions mid-tick are not.

Contestant bots follow the same rule as people (#230). A bot decides from its discovery memory: chargers and the exit only once discovered, and cells and loot only as it has had them in line of sight (the visibility polygon out to 1,200 units, with roofs concealing interiors from outside), sampled with discovery. It remembers an item where it last saw it and forgets it once it sees that spot empty, so it may walk to a cell someone else has taken. When it knows of nothing it needs, it explores the frontier of the cells it has *seen* (`memory.seen`), since a cell the view window has discovered may still hide loot. Each bot's memory is its own; bots share nothing. A bot also remembers each door as it last observed it, in line of sight or by trying it, and every cell its view window has covered, void or not (`memory.surveyed`): what navigation's knowledge filter plans with ([22.6.2](22.6.2-knowledge-and-doors.md#knowledge-and-optimistic-planning), #423; no production bot reads them yet). The remembered items, doors and cells, like discovery itself, stay out of snapshots, recordings and every projection. Gladiator bots keep full map access. With `content-1`, which has no discovery, bots keep whole-map knowledge, as the frozen characterization traces recorded.
