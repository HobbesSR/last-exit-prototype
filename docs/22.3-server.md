# 22.3. Server

Back to [22](22-ownership.md).

## Server

Server ownership is explicit: `server/match.js` is the application's sole mutable simulation access, through join/resume/choose/leave/input/advance/end operations and detached snapshot/identity/map queries. `room-directory.js` owns which rooms exist ([22.5](22.5-lobbies-and-matchmaking.md)): the eight-room cap, creating a room (its map promised by the worker), matchmaking, the listing behind `GET /api/rooms` (rooms not yet started that are matchmade or named, or every open room under `DEV_TOOLS=all`), and room names, unique among open rooms (17.4 #9). It never touches a room: it reads the room service's `summaries()`, plain data (id, name, kind, phase, whether the map is ready, size, and players and open places by role), and answers a matchmaking player with a room id, which the room service then admits them to like any join. The room service is the host: it owns room admission, sessions, command queues, the pre-start phase, match lifecycle and tick debt. Sessions supply delivery and close callbacks; they are ordinary objects without WebSocket dependencies. Delivery says whether a payload is droppable, which only state frames are, and the transport decides whether a backed-up socket skips it ([24](24-networking-privacy.md#dev-view)). The room service also owns a room's dev pause. `room-views.js` owns lobby broadcasts, bounded spectator history and per-view payload reuse. `scheduler.js` owns elapsed-time wakeups. `map-generator.js` owns the worker thread (`map-worker.js`) that generates live maps, so the directory's `createRoom` never stalls other rooms. The room service's `makeRoom` takes the map, a promise of it, or nothing (generated inline, as the fake-clock tests do), and the room exists at once (#258). Until the map arrives a room has seats but no match: `match.js`'s `createLobby` is the same roster from the same content, and join, resume, choose (a change of role or kit before the start, #235) and leave are recorded as commands exactly as they are later. When the map arrives the room builds the match and replays those commands into it with `seat`, in order; joining takes no randomness, so the seats are the ones live joins would have given and the recording, which starts at the start, is unchanged. Each session that holds no place then gets `ready` with its map and state; players stay in the waiting yard (below). A start pressed before then is held and happens on arrival, and a matchmade countdown waits for it. A generation failure is reported, the room's sessions are told and released, and the room is removed; closing the server is not a failure. `room.ready` settles when the room has its match or has been given up, for tests and benchmarks to await. Until the start a room also holds `room.waiting`, the waiting yard (#236, [22.5](22.5-lobbies-and-matchmaking.md#before-the-match-starts)): `shared/simulation/waiting.ts` over the fixed map in `shared/waiting-yard.ts`. Join and resume put a player there with their input started afresh, since a resumed connection numbers its inputs from zero even while the old one is still attached; choose changes them in place, keeping their queue; and leave takes them out; a player's `input` before the start goes to it, never to `room.inputs`; and `advance` steps it on its own tick debt and sends each player their `state` frame of it. At the start it is dropped and each player is sent `ready` with the match map and their state. `shared-assets.js` owns delivery of the shared modules to the browser, and is the only server module outside replay storage permitted to read files. `latency.js` owns round-trip measurement per session: it stamps and times its own tokens, and exposes the figure as a bound rather than a client-supplied fact. `match.js` converts that into the simulation's view-lag, so the application reports what it observed and the simulation decides how much rewind it will grant. `websocket.js` owns origins, socket limits and connection events; `protocol.js` owns envelope decoding, rate-window arithmetic, HTTP seed (random when absent), room-name and zone-size validation, the sizes being those `map/live.ts` offers, and the `DEV_TOOLS` policy values ([24](24-networking-privacy.md#dev-view)); the room service applies the policy at admission, and `room-views.js` gives dev sessions the undelayed directed payload. Simulation continues to own state-dependent input validation, and owns the per-player queue a tick spends exactly one input from.

`replay-writer.js` owns gzip, per-frame JSON serialization, bounded buffering, hashing and stream completion. It receives header/frame/command values, never rooms. `replay-store.js` owns filesystem paths, archive metadata and publication. Rooms depend on writer append/failure/abort/finalize operations; backpressure is not a scheduling input. The filesystem adapter supplies a download path only to `http-api.js`, preserving Express's existing file delivery, headers and range behavior; a remote storage adapter would replace this delivery edge as well as storage, without affecting room or match code. No storage product has been selected.

Shutdown is an explicitly owned asynchronous operation. Logical match completion and archive publication are separate: the room service tracks outstanding finalizations even after a room is retired, and `close()` awaits them. Repeated writer/service/server close calls share completion. Server shutdown stops admission and timers before awaiting storage. Rooms finalize concurrently with a five-second deadline, so a stalled adapter cannot block shutdown indefinitely. Replay failure sends a typed `replay-status` message rather than a connection error or saved replay; gameplay continues. The original shutdown race fix and the later storage-failure policy are separate checkpoints.

Empty live rooms retain a 30-second reconnect grace, then finalize a replay with an abandoned event and stop simulation. A viewer—including an authorized spectator—keeps a room live. Raw frame timestamps replace Phaser-smoothed delta for diagnostics and client benchmarks. The bounded always-on client samples can be downloaded without owner credentials or a player list. Profiler per-frame call rates now use the same rolling window as timing samples.

The existing `createArenaServer().rooms` surface retains `room.game` for scenario setup and benchmarks. It is a deliberately retained diagnostic escape hatch, not production process isolation; server application and transport modules are prohibited from using it by boundary tests. Timers, sessions and storage can be replaced with fake time, peers and writers in lifecycle tests. See [41](41-roadmap.md) for follow-on priorities and [17](17-open-questions.md) for batched live-service policy questions. New gameplay direction is recorded as F-11 through F-18 in [13](13-accepted-features.md) and remains separate from this behavior-preserving extraction.
