# 22.3. Server

Back to [22](22-ownership.md).

Every welcome and ready names the room's `contentId` and its `presentation`
descriptor, a recording header carries the descriptor once, and
`GET /api/client-config` serves deploy defaults and limits from their owners.
The contract is [22.7](22.7-content-and-presentation.md).

## Server

Physics match construction cooperates with the host event loop (#842).
`server/match.js` supplies `setImmediate` checkpoints to the portable physics
factory: movement geometry is prepared in chunks before initial discovery, and
construction yields after each existing 512-body static commit and between major
initialization phases. These are preparation checkpoints, never simulation steps;
body admission order and commit boundaries stay unchanged. The room service
keeps the match private until its factory resolves, replays accumulated lobby
commands before adoption, and disposes a completed match if its room closed or
retired meanwhile. Shutdown still awaits pending factories.
Private preparation also warms the initial published ground-item spatial grid,
bot gate lookups, and closed-gate sweep buckets (#1086). Ground records are
published before indexing so the first query need not migrate loose records.
These caches consume no RNG and never step the world. Shared/browser factories
without cooperative preparation retain lazy construction. Readiness waits on the
same factory; no extra lifecycle gate is introduced. Every factory, cooperative
or not, builds Rapier's broad phase with one statics-only native step before any
moving body is admitted ([29.1](29.1-physics-design.md#ownership), #1087), so the
first tick no longer pays for it. State-dependent bot searches and other
first-use work still run during ticks.

The same private preparation builds both static swept-query indexes (#908),
yielding every 128 obstacles or shapes. It reuses the physics geometry before
the native admission sort: sweep candidates retain source order, while native
bodies retain ID order. Both complete indexes are published against the exact
match map object before readiness. Shared/browser callers without cooperative
preparation retain lazy indexes. Gates remain separately indexed and their open
state is read at query time.
Pooled maps also go through this preparation; the create response need not wait
for match readiness, just as with a map arriving from the generator. Cooperative
map payload preparation also finishes before readiness. `server/map-payload.js`
copies and serializes the explicitly static fields into detached immutable data,
yielding after batches of 128 array records and between fields. The cache belongs
to one match and is released on disposal; once disposed, `payloadMap` refuses
calls with `'match disposed'`, while ordinary writable map queries (`map()`)
and final detached frames retain their readable contract. An individual unusually large record can
still block a preparation batch. The extra static copy and JSON consume memory
in exchange for avoiding repeated whole-map work.

Once its match is prepared, a room opens the match's recording and adopts the match when
the writer has taken in the header, which carries the map, bounded at five seconds (#1088,
[26](26-recording-contract.md#bounded-recording)). Readiness therefore includes compressing the
header, so the start's first ticks never wait behind it. A room that never starts discards the
recording without a file or an error.

Welcomes, ready messages and recording startup use `match.payloadMap`: cached
static fields plus published current items/gates, or the selected historical
frame's items/gates for spectators. The list shells and traps are detached;
published item/gate records are immutable. Public maps remove private prop
authoring and all traps, while recording headers retain their full source map.
The complete immutable map object and its JSON are reused when the same item and
gate payloads recur; their cached JSON is checked so mutable synthetic inputs
cannot return stale data. Unknown map fields are copied and encoded afresh and
warn once per field outside production; a new static field must join the
explicit allowlist only after its ownership is established. Dynamic item/gate
records that are not already deeply frozen are cloned and frozen. Fixed fields
are pinned at preparation, so a future gameplay mutation to them must revise
this contract. `stringifyWithMap` handles a prepared map directly or at the
envelope's top-level `map` property; other shapes use ordinary `JSON.stringify`.
It preserves ordinary JSON field order and formats for these plain-data envelopes.
All preparation remains private, and the existing pending-factory lifecycle
handles closure, failure and queued lobby commands. Welcome/start delivery
remains synchronous at the existing boundary. Every match uses prepared
map payloads. Preparation adds no worker, shared mutable memory or runtime map
generation of its own. Final envelope assembly, encoding/transport and first physics
step can still impose synchronous work within the room; preparation alone does not
establish startup isolation, which each room's own thread provides (below, #1089).

## Room threads

Each room runs on its own worker thread (#1089; Corey, 17.4 #13). `server/room-thread.js` is the host's
side of a room and `server/room-worker.js` the thread: it runs the room lifecycle (`room.js`) with its
match, waiting yard, its own scheduler and tick debt (catch-up and `MAX_CATCHUP` move with the room), and
its recording worker, which is therefore a child of the room's thread. The host thread keeps sessions,
sockets, protocol validation, latency pings, the directory, the map generators and the pool. So one room's
preparation, first Rapier step or catch-up can delay neither another room's ticks nor its delivery.
The same interface is where a room host in another process would attach; that, and where client sockets
would then terminate, is proposed in [28.1](28.1-deployment-topology.md).

- **Inbound** commands, inputs, leaves, refusals and latency cross as plain messages in the order the host
  received them, which keeps command order, including a resume's takeover. A join is routed to the room at
  once, so what the session sends next follows it; the room answers it later (`joined`), and a refusal
  frees the session again.
- **Outbound** events cross in batches, in the order the room produced them (deliveries, closes, join
  answers, readiness, finalization, disposal, errors), once per turn of the room's loop. Each distinct
  payload is encoded once to UTF-8 bytes and transferred; a WebSocket session (`bytes: true`) sends those
  bytes as a text frame, and other sessions are given them decoded, once per payload. Welcome-before-state
  holds because the room produces both, in order.
- **Drops.** Whether a droppable state frame is skipped is decided in the room's thread against the socket
  backlog (`buffered()`) the host reports after each batch, plus what the room has sent since, so the room
  knows exactly which keyframes each client holds ([24](24-networking-privacy.md#layered-frames)). The
  host delivers what the room sends without dropping it again. A socket reported over the limit gets no
  state frames, so no delivery prompts its next report: the host re-reads every such socket on each wake
  and reports it as it drains.
- **Maps** cross as bytes (`server/map-pack.js`): the map worker V8-serializes the map with its portal
  graph and transfers that buffer and the packed free-space tiles; the generator and pool hold them
  packed; the room's thread unpacks them. The host never decodes a map, whose object graph costs
  150–200 ms to decode at 36x18. A plain map (a test's) is packed by the host. A room created with no map
  generates its own, in its own thread.
- **Directory and health** read each room's latest `summary()` and `metrics()`, which the room reports when
  they change; until its first report a room is the empty lobby it was created as. A room makes its last report
  before it is disposed, so the host can total a retired room's `fast` message counts. A player join still in
  flight is taken off the reported open places, so matchmaking never sends two players for one last place.
- **Recording** goes to the same archive: the room's thread writes with `fileReplayWriters` over the file
  store's directory (`threadOptions`), and the host's store learns of each publication (`published`), so
  `GET /api/replays` lists it. Shutdown awaits each room's close, and with it its finalization, as before.
- **Failure.** A room thread that dies unasked is reported; its sessions are told the arena stopped and the
  room is removed.
- **Profiling** is switched in every room's thread with the host's (`setProfiling`). Each thread keeps its
  own series; the host asks for them on demand (`roomProfiles()`, answered within two seconds or left out)
  (#1115). `GET /api/profile` reports the host thread's `series` and each threaded room's under
  `roomProfiles` (`id`, `frames`, `effectiveHz`, `series`), and its top-level `effectiveHz` combines every
  thread's `sim.tickPacing` weighted by samples, as one shared series did for rooms run on the host. The
  periodic console summary prints the host's table, then each room's. Frame series stay per thread: they
  are never summed across rooms.

`createRoomService({ threads: false })` keeps every room on the host thread, ticked by the host's scheduler.
That is the fallback, the fake-clock tests' host (fake time, injected writers and match factories cannot
cross a thread) and the one `rooms` exposes live rooms through, for `room.game`. `createArenaServer` runs
rooms on threads unless given `roomThreads: false`; the tests and tools that reach into a live room pass
that. A process host, if #907 chooses one, is another implementation of the same handle. The eight-room
cap is therefore rooms per host process, not rooms on one loop ([22.5](22.5-lobbies-and-matchmaking.md)).

## Ownership

Server ownership is explicit: `server/match.js` is the application's sole mutable simulation access, through join/resume/choose/leave/input/advance/end operations and detached snapshot/identity/map queries. `room-directory.js` owns which rooms exist ([22.5](22.5-lobbies-and-matchmaking.md)): the eight-room cap, creating a room (its map promised by the worker), matchmaking, the listing behind `GET /api/rooms` (rooms not yet started that are matchmade or named, or every open room under `DEV_TOOLS=all`), and room names, unique among open rooms (17.4 #9). It never touches a room: `makeRoom` and `directory.createRoom` return only plain room descriptors (`{ id, ownerKey, seed, size, name, ready }`), the directory reads the host's `summaries()` (id, name, kind, phase, whether the map is ready, size, and players and open places by role), and answers a matchmaking player with a room id, which the room service then admits them to like any join. `server/room-service.js` is the room host (#1078): it mints each room's id and owner key, for inline and threaded rooms alike (#1187), and owns sessions, WebSocket/protocol validation (`acceptClientMessage`), RTT latency pings (`latency.js`), scheduling/tick dispatch across rooms run on its own thread (each threaded room schedules itself, above), and answering HTTP health and profile counts through `metrics()` (live and empty-live room counts, and the `fast` messages sent since the process started, rooms retired since included ([24.5](24.5-transport.md#stage-3s-contracts) "Overflow"); plain numbers) so `http-api.js` never reads its room map (`rooms`, kept as a diagnostic escape hatch for tests and benchmarks). `server/room.js` owns the single-room Colyseus-shaped lifecycle (`onCreate`, `onJoin`, `onLeave`, `onMessage`, `onInvalidMessage`, `onDispose`) behind a plain-data / serialized-payload boundary: deferred map adoption (`adoptMap`/`failMap`), admission, resumes, command queues, the pre-start waiting yard and its handoff to the match, historical spectator projection and keyframe delivery, recording lifecycle, and `summary()`/`metrics()` reporting. Sessions supply delivery and close callbacks; they are ordinary objects without WebSocket dependencies. Delivery says whether a payload is droppable, which only state frames are, and the transport decides whether a backed-up socket skips it and reports whether it sent ([24](24-networking-privacy.md#dev-view)). `room.js` also owns a room's dev pause. `room-views.js` owns lobby broadcasts, bounded spectator history, per-view payload reuse, each view's layer and discovery encoders (every room starts with them, from `viewEncoders`), and which keyframes each session has been delivered ([24](24-networking-privacy.md#layered-frames)). It also owns how a session is sent match frames (`deliversFast`): a player session with datagrams gets fast state on them against its own acknowledged history, and the slow layers on its stream ([24.5](24.5-transport.md#stage-3s-contracts)). `scheduler.js` owns elapsed-time wakeups. `map-generator.js` owns the worker thread (`map-worker.js`) that generates live maps, so the directory's `createRoom` never stalls other rooms; the worker also posts the map's portal graph and the free-space tiles bots would otherwise build on their first plans, all packed (`map-pack.js`), and whichever thread runs the room unpacks the map and attaches them ([22.6.3](22.6.3-bot-adoption.md#bot-adoption-stage-4)). `map-pool.js` owns maps generated ahead of need (#266, 17.4 #10): a few per size, each with a fresh random seed, refilled one at a time on a second generator so a seeded room's request never queues behind it. The directory gives a room that names no seed a pooled map and its seed, and generates on demand for a named seed or an empty pool. The pool is in memory only, so a restart (the only way new generator or content code arrives) empties it. `createArenaServer` keeps none unless `mapPool` is given; the command-line server passes `MAP_POOL`, default 2, and `/api/health` reports what is ready by size. The room service's `makeRoom` takes the map, a promise of it, or nothing (generated inline, as the fake-clock tests do), and the room exists at once (#258). Until the map arrives a room has seats but no match: `match.js`'s `createLobby` is the same roster from the same content, and join, resume, choose (a change of role or kit before the start, #235) and leave are recorded as commands exactly as they are later. When the map arrives the room builds the match and replays those commands into it with `seat`, in order; joining takes no randomness, so the seats are the ones live joins would have given and the recording, which starts at the start, is unchanged. Each session that holds no place then gets `ready` with its map and state; players stay in the waiting yard (below). A start pressed before then is held and happens on arrival, and a matchmade countdown waits for it. A generation failure is reported, the room's sessions are told and released, and the room is removed; closing the server is not a failure. `room.ready` settles when the room has its match or has been given up, for tests and benchmarks to await. Until the start a room also holds `room.waiting`, the waiting yard (#236, [22.5](22.5-lobbies-and-matchmaking.md#before-the-match-starts)): `shared/simulation/waiting.ts` over the fixed map in `shared/waiting-yard.ts`. Join and resume put a player there with their input started afresh, since a resumed connection numbers its inputs from zero even while the old one is still attached; choose changes them in place, keeping their queue; and leave takes them out; a player's `input` before the start goes to it, never to `room.inputs`; and `advance` steps it on its own tick debt and sends each player their `state` frame of it. At the start it is dropped and each player is sent `ready` with the match map and their state. `shared-assets.js` owns delivery of the shared modules to the browser. `vendor-modules.js` owns the other half of that asset delivery: when a `DEV_TOOLS` policy is set, it wraps CommonJS packages imported by bare name (`sat` in shared modules, `pathfinding` in dev tools) as single ES modules, reading their manifests and sources from `node_modules`. These two asset modules are the only server modules outside replay storage permitted to read files; `tests/server-boundaries.test.js` holds that allowlist. `latency.js` owns round-trip measurement per session: it stamps and times its own tokens, one outstanding at a time, and exposes the figure as a bound rather than a client-supplied fact. A session is pinged at most once a second, and not again until its last token comes back: an unanswered ping is waiting behind a backlog, and more of them would arrive, and be echoed, as a burst (#1095). `match.js` converts that into the simulation's view-lag, so the application reports what it observed and the simulation decides how much rewind it will grant. `edge-link.js` owns the loopback link to `last-exit-edge`, origin/transport handoff from the edge, each session's backlog and datagram/stream capability as the edge reports it, close codes/reasons, connection events and rate limiting ([24.5](24.5-transport.md#stage-1s-contracts)); `shared/protocol.ts` owns the transport-free wire protocol (`WIRE_VERSION`, message types, HTTP endpoints, limits, `DEV_TOOLS` policy values, and inbound message validation), and `server/protocol.js` adds per-session reject counting/rate-limited logging (`acceptClientMessage`) plus HTTP seed (random when absent), room-name and zone-size validation, the sizes being those `map/live.ts` offers ([24](24-networking-privacy.md#wire-protocol-and-middleware-boundary)); the room service applies the policy at admission, and `room-views.js` gives dev sessions the undelayed directed payload. Simulation continues to own state-dependent input validation, and owns the per-player queue a tick spends exactly one input from.

`replay-writer.js` owns changed-field JSON serialization, bounded byte admission, worker lifecycle and completion. It receives header/frame/command values, never rooms. Its `replay-worker.js` owns frame assembly, UTF-8 encoding, hashing, gzip and the production output stream (#728). Injected Writable outputs use a bounded acknowledged compressed-chunk bridge ([26](26-recording-contract.md)). `replay-store.js` owns filesystem paths, archive metadata and publication. Rooms depend on writer append/failure/abort/finalize operations; backpressure is not a scheduling input. The filesystem adapter supplies a download path only to `http-api.js`, preserving Express's existing file delivery, headers and range behavior; a remote storage adapter would replace this delivery edge as well as storage, without affecting room or match code. No storage product has been selected.

Shutdown is an explicitly owned asynchronous operation. Logical match completion and archive publication are separate: the room service tracks outstanding finalizations even after a room is retired, and `close()` awaits them. Repeated writer/service/server close calls share completion. Server shutdown stops admission and timers before awaiting storage. Rooms finalize concurrently with a five-second deadline, so a stalled adapter cannot block shutdown indefinitely. Replay failure sends a typed `replay-status` message rather than a connection error or saved replay; gameplay continues. The original shutdown race fix and the later storage-failure policy are separate checkpoints.

Empty live rooms retain a 30-second reconnect grace, then finalize a replay with an abandoned event and stop simulation. A viewer—including an authorized spectator—keeps a room live. Raw frame timestamps replace Phaser-smoothed delta for diagnostics and client benchmarks. The bounded always-on client samples can be downloaded without owner credentials or a player list. Profiler per-frame call rates now use the same rolling window as timing samples.

The existing `createArenaServer().rooms` surface retains `room.game` for scenario setup and benchmarks. It is a deliberately retained diagnostic escape hatch, not production process isolation; server application and transport modules are prohibited from using it by boundary tests. Timers, sessions and storage can be replaced with fake time, peers and writers in lifecycle tests. See [41](41-roadmap.md) for follow-on priorities and [17](17-open-questions.md) for batched live-service policy questions. New gameplay direction is recorded as F-11 through F-18 in [13](13-accepted-features.md) and remains separate from this behavior-preserving extraction.
