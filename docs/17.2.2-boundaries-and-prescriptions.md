# 17.2.2. Reachability, boundaries and prescriptions

Up: [17.2](17.2-map-questions.md). Load only the related parts needed for the task.

### Answers

**Reachability.** Must a hunter reach everything?
  - (2026-09-27) "Everything must be reachable by a hunter so we are pessimistic about passablility."
  - (2026-09-27) "remember we ignore gaps."

**What does `open` guarantee?**
  - (2026-09-27) "Open is a special class of region." "Every cell in the regions formed by open cells must be passable as well as every internal segment of those regions. Addressing the open regions may ultimately use a decomposer and microgenerator that enforces its special requirements, but there is a notion that it is a privileged region class."

**Saving a map.**
  - (2026-09-27) "Can we not make the interior generation essentially a function of a seed, a library, and generation algorithm? And can we not make the objects saveable separably and compoundly as needed?"

**Region boundary openings.** Who states which boundary segments are passable, and what does a builder owe?
  - (2026-09-27) "We may require tile makers to declare passable segments between cells of different regions, i.e. on the perimiter of regions. It's the tile designer's job to mark internal as passable. For convenience, we may make perimeter segments default to passable with explicit nonpassable indicators."
  - (2026-09-27) "just because something isn't marked passable doesn't mean it won't be passable. It just means we can prove its passable."
  - (2026-09-27) "segment passability isn't really enforced in any way, save through the geometry that builders create within their regions. Now we might at some point want to say we want explicit nonpassable and that is a directive that builders must honor, but I don't want that to be another constraint because all builders work on the honor system, and I'd prefer them to honor passable than try to honor multiple objectives."
  - (2026-09-27) "the whole idea is we can trust that any passable perimiter segment in a aggregate region is reachable through passable segments."
  - (2026-09-27) "passable segments must all be part of a chain of perimeter segments on the region large enough to be passable for hunters."
  - (2026-09-28) "there was talk about segments being explicitly impassable on the perimeter of regions, without prescribing a segment object like wall or fence, as a directive to the region builder to make its placed geometry make that segment impassable, and I decided I don't want to make builders, which already work on the honor system, to have to solve for two external objectives at the same time as part of their pinky promise contract, so I suggested they would be, at best, if at all, architectural suggestions for the builers."
  - (2026-10-05, issue #241) "I'd like to start working on the tile sets / set pieces so that they are less generous in their passability by making more segments explicitly not passable. [...] Perimeter Any segments should default to passable and take on explicit passable or not passable traits of the adjacent tile's shared segment. The primary concern here then is that passability checking after laying a tile has to be done after the segment properties are derived."
  - (2026-10-05, issue #243) "As a game design choice, builders should attempt to use space adjacent to segments that are marked as not passable (or not known passable). There isn't a requirement that these actually be unpassable [...] there is no requirement to enforce this, but these are big clues to builders that the tile designer wants this part of the perimeter to be occupied and frequently truly not passable."
  - (2026-10-08) "Yes any + any is passable. I'm not sure my direction contradicts the previous call. The hint is not a requirement. But it is an opportunity most regions should want to take advantage of as a rule of thumb. If there were a map designer role, it would be part of the art direction or similar guidance. And to facilitate it, we might add some standard tools to the SDK to help builder algorithm writers leverage the hints."
    - Reading: the 2026-09-27/28 answers rejected an impassable *requirement*; the hint is the "architectural suggestion" they left open. Recorded in 52 and 16; built by #286 (mechanism) and #287 (brief and SDK helpers).

**Segment prescriptions.** What does a segment carry?
  - (2026-09-27) "we have for segments cell adjacency requirement for each side, a geometry prescription, and passability prescription. And there are Any DNC modes and stuff." "It can be confusing since some things can imply other things and we accept don't care on some dimensions. So I guess it's just important we distinguish that a segment has that set of prescriptions, which different labels specify directly and indirectly."
  - (2026-09-27) "yes hunters can break fences."
  - (2026-09-28) "Perhaps what's best is to have open / default / any pass down as deep as possible if that information is pertinent (along with the assumption of what it implies if that choice is also needed)"
  - (2026-09-28) "The passability requirement is something that must be matched, either with a corresponding passability or any (and it might be derived), and a "macro" geometry directive, that prescribes something placed not by a builder (which I'm beginning to regret even allowing as a way for macro to prescribe specifics of geometry placement but I just can't write off just yet) like walls and fences, the former creating a derived not-passable conclusion, and the latter deriving a passable conclusion. And so I guess there is also a difference between the declaritive nature at the tile layer, and the knowledge layer derived after solving after valid placements."
  - (2026-09-28) On whether macro geometry directives survive: "I'm going to say no. I'll add them back in (this affects set pieces and tile designs we already have)."
  - (2026-11-06, in chat with Claude, #761) Asked whether passability should constrain tile placement: "any matches with anything, otherwise like with like (should we expand from passable and hint options). Unstated segments are supposed to default to passable internally and I believe hint on internal region perimeters."
    - Reading: where two tiles meet, `any` fits any value, and otherwise `passable` must face `passable` and a hint must face a hint. Any value added later matches only itself. This restates the 2026-09-28 "must be matched" answer.
    - **Not implemented.** Placement still treats passability as unable to conflict: in 51.4's table, `passable` on either side wins. Claude found no answer choosing that rule.
  - (2026-11-06, follow-up) "unstated default to passable is for internal segments on the perimiter of two different region types, and for segments on the perimiter of tiles. [...] I think all this work should move together. As far is internal segments within a region and not along its perimeter, my understanding is their passability traits don't come into question. And these are authoring and storage conveniences."
  - (2026-11-06, correcting the tile-edge case) "on tile perimeters it should default to any not passable, and any<->any defaults to passable."
    - Reading: an unstated segment between two different regions inside a tile is `passable`. An unstated tile edge is `any`, so it matches anything, and `any` meeting `any` is passable (51.4). These are authoring and storage defaults, as in the 2026-09-27 "default to passable with explicit nonpassable indicators". They supersede the first message's "hint on internal region perimeters". Segments inside one region have no passability question.
    - **Not implemented.** Today an unstated segment carries nothing (51.4). At 36 wide, 4,386 unstated segments between two regions inside tiles would become guarantees under this default (Claude's count on #688's `size-36-1`). No tile edge is unstated today.
    - The matching rule, this default and the content batch (#838) move together.
  - (2026-11-06, clarifying) "segments between distinct different regions in the tile get passable, the rest remain unstated, and I'm not sure what mechanism would query their passability anyway once regions are aggregated"
    - An unstated segment with one region on both sides stays unstated, and nothing reads it. A tile edge that two `any` sides resolve to passable inside one aggregated region is different: 20.6 makes it an internal guaranteed run with clear margins (16,689 such segments at 36 wide; most of the 42.34 "strip" category).
  - (2026-11-06, deciding that case) "I guess the any<->any default to passable should only be decided after aggregation, which I think nothing prevents it being delayed until then. At that point perimiter segments become passable and internal segments become unstated."
    - Reading: `any` meeting `any` resolves after regions are aggregated. On a region's perimeter it becomes passable, a guarantee and so part of a portal. Inside one region it becomes unstated, with no internal guaranteed run and no 20.6 strip. A segment explicitly authored `passable` inside a region is still an internal guaranteed run (20.6). Aggregation groups cells by class alone (51.5), so the delay changes no region. Part of the same batch; not implemented.
